UE5 异步 AddToWorld 跨帧 —— SplineMesh 共享顶点工厂「先发布后初始化」竞态与两层修复竞态分析与两层修复

作者：张建国（ZXB）
日期：2026-10-16
涉及模块：Engine/Components, Engine/StaticMesh, Engine/Streaming, RenderCore/RenderingThread
关键技术：AsyncAddToWorld 并行建 proxy · 非阻塞取消跨帧 · FRenderCommandList 命令录制 · 共享资源发布/初始化竞态
**一句话**：Epic 原版 `USplineMeshComponent::InitVertexFactory` 先「发布共享指针」、再在渲染线程「初始化资源」，两者之间存在窗口；项目的非阻塞取消让后台任务跨帧，使另一个 worker 的渲染命令排到本帧 `FScene::Update` 之后 —— 渲染线程于是在窗口内读到了那个指针，触发 `FMeshBatch was not properly setup` ensure。
**修复**：两层，各自独立有效、各带 CVar、可单独回退。第一层把「发布」挪到初始化之后（治本点）；第二层让这批渲染命令抢占命令流位置（治面）。
**验证**：插桩 `Sleep(0.02f)` 后三轮实测 —— 两层都关 → 复现 6 次；只开第一层 / 只开第二层 → 均 0 次，且复现现场与 bug 单记录逐字符一致。

1. 现象与根因判定

报错样本（同一断言在两条 bug 单上分别出现，main@1110360 与 release@1162595）： 
FMeshBatch was not properly setup. Mesh has an uninitialized vertex factory!
  VertexFactory[Name: FSplineMeshVertexFactory, Initialized: 0]
  PrimitiveSceneProxy[Level: /Game/Maps/Rush/RUSH_03_Main/_Generated_/2QKNKSTP02KN1T9GKLNTNB8GO,
                      Owner: Blockout_Tube_C_UAID_ACB4803EB66C53DA02_25c32625080ab041_1433571598,
                      Resource: SM_Blockout_Box]
Callstack: FScene::Update -> FPrimitiveSceneInfo::AddStaticMeshes (ParallelFor)
           -> FStaticMeshSceneProxy::DrawStaticElements -> FBatchingSPDI::DrawMesh -> FMeshBatch::Validate
断言位置 SceneManagement.cpp:1979（跨 1972-1979 的 ensureMsgf，MSVC 报宏末行）。

现场是一根由多段 SplineMesh 拼成的 Blockout 管道，所有段共用 SM_Blockout_Box。main 与 release 各出现 1 次，属低概率偶发，集中在关卡首次流入时。

根因链路：三个条件叠加

#条件位置 / 证据
①共享资源懒创建（先发布后初始化）Epic 原版，项目未改 —— SplineMeshComponent.cpp:368-393
②worker 线程并行建 proxyCL 371998 合入 FAsyncRegisterLevelContext，DefaultEngine.ini 开 LevelStreaming.AsyncRegisterLevelContext.Enabled=1（每批 16 个组件）
③非阻塞取消 → 任务跨帧CL 894515（MergeTest）→ 917608（合 main）；release 经 CL 990998 才拿到 —— World.cpp 时间片用完只调 CancelRunningAsyncTasks() 设标志，不再等 worker
只有 ①② 不会出问题：原版 5.6 在时间片用完时会等任务结束，所有渲染命令都在本帧渲染前入队，最多是两个线程同时 new 造成泄漏（= UE-389807）。
③ 是必要的第三环：游戏线程带着在途任务离开，才让 worker 的命令可能排到本帧渲染之后。

2. 缺陷本体：共享顶点工厂的创建—发布—初始化三步

主角是 USplineMeshComponent::InitVertexFactory（SplineMeshComponent.cpp:320），它在 proxy 构造时被调用 —— 调用点见 SplineMeshSceneProxy.cpp:92 与 SplineMeshSceneProxy.cpp:95。

它写的共享指针是 FStaticMeshVertexFactories::SplineVertexFactory（StaticMeshResources.h:670，override 色版本在 StaticMeshResources.h:672），宿主是 UStaticMesh 的 RenderData —— 同一张 mesh 的所有 spline 段共用一份。渲染线程侧读它的地方在 SplineMeshSceneProxy.cpp:110 与 SplineMeshSceneProxy.cpp:386。

「创建 — 发布 — 初始化」四步：SplineMeshComponent.cpp:368 判空 → SplineMeshComponent.cpp:374 new → SplineMeshComponent.cpp:377 / SplineMeshComponent.cpp:381 写共享指针（发布）→ SplineMeshComponent.cpp:386 ENQUEUE 初始化。窗口在第 3 步与第 4 步之间。

3. 出错时序：两个 Worker 走一遍

决定性的是编号 3~8：GT「带着在途任务」离开 → B 的 AddPrimitiveCommand 排到了本帧渲染之后，而 A 的初始化命令还在窗口里没入队。

4. 第一层修复：把发布挪到初始化之后

开关：r.SplineMesh.InitVertexFactoryOnRenderThread（默认 1，声明在 SplineMeshComponent.cpp:52；置 0 完全走原版逻辑），改动见 SplineMeshComponent.cpp:343-364。

正确性要点：每个 proxy 都在它自己的 AddPrimitiveCommand 之前、同一线程入队这条命令，所以被渲染时 VF 必已初始化。归功于「判空 / new / SetData / InitResource / 发布」全部收敛在渲染线程的同一条命令里，别的线程永远看不到中间态。
副产品：并发 new 造成的顶点工厂泄漏（UE-389807）一并消除 —— 创建点唯一了。

5. 第二层修复：异步任务专属的渲染命令列表

开关 LevelStreaming.AsyncRegisterLevelContext.RecordRenderCommands（默认 1，AsyncRegisterLevelContext.cpp:44）。任务在 Launch 时建列表并立即 Submit() 占位（AsyncRegisterLevelContext.cpp:428），任务体用 FRecordScope 绑定（AsyncRegisterLevelContext.cpp:437）；ParallelFor 的每个子任务一个子列表（AsyncRegisterLevelContext.cpp:601-606），因为 worker 不继承 TLS。

这里最容易推错的一点：第二层不是靠「列表内 A 的 init 与 B 的 AddPrimitive 谁先谁后」救的。AddPrimitiveCommand 只是把 primitive 加进待处理队列，真正读 VF 的 DrawStaticElements 发生在 FScene::Update。只要保证整批命令都在 FScene::Update 之前执行完，列表内的相对顺序就不影响结果 —— 而「占位」恰好保证了这一点。
代价（如实列出）：RT 在占位处会等列表关闭。任务正常跑完时列表已 Close，零等待；任务跨帧（被取消）时 RT 要等剩余部分，量级约为「当前批次剩余的处理时间」（ms 级）。对比改动前，这是把「GT 等一整批」换成了「RT 等剩余」。

6. 为什么只有 SplineMesh 中招：同类风险判据

出问题需要三个条件同时成立（①共享 ②组件期懒创建 ③发布/初始化分离），再叠加 worker 并发与跨帧才真的炸。

普通 FStaticMeshVertexFactories 的 VF 虽然也是共享的，但它在资产加载期就由 FStaticMeshVertexFactories::InitResources 一次性建好（StaticMesh.cpp:1190-1197）—— 那时组件还没建 proxy，没有并发读者；而且它用 BeginInitResource 把发布与初始化绑在同一步。SplineVertexFactory 则是「资产级共享 + 组件级懒创建」的混合形态。

已确认的第二例：WidgetComponent BodySetup（bug 1255826 / CL 1124021，2026-09-10）—— 那次改为「只允许真正的 GT 创建 + 批内去重」。
但批内去重救不了本单：它防的是「同一个组件被处理两次」，管不了「不同组件共用同一份资源」。release@1162595 已含该 CL 仍复现。

排查判据：在 CreateSceneProxy 可达路径上找同时满足这三条的代码 ——

if (SharedThing) return;              // 1. 判空
SharedThing = new ...;                // 2. 写【跨组件共享】的指针
ENQUEUE_RENDER_COMMAND(...)(          // 3. 初始化放到别的线程、滞后于发布
    [&]{ Thing->InitResource(...); });

重点是看指针的归属：是 this->成员（组件私有 → 安全）还是 SomeAsset->RenderData->...（资产共享 → 危险）。

8. 配套改动与已知取舍

8.1 释放路径同步挪到渲染线程

FStaticMeshVertexFactories::ReleaseResources（StaticMesh.cpp:1199）。为什么必须改：指针改由 RT 写之后，GT 上 if (SplineVertexFactory) 可能读到空而跳过释放；随后 RT 的 init 建出 VF 却没人释放 → 析构时 delete 一个已初始化资源 → Fatal A FRenderResource was deleted without being released first!（RenderResource.cpp:248-258）。

已知取舍（空命令）：改法是把判空挪进一条无条件 ENQUEUE 的渲染命令（StaticMesh.cpp:1208）。增量核算：
· 用过 spline 的 mesh：原版 ≤2 条 → 现在 1 条（合并处理两个指针），−1；
· 没用过 spline 的 mesh：原版 0 条 → 现在 1 条，+1。
调用点在 per-LOD 循环里（StaticMesh.cpp:2737 与 StaticMesh.cpp:2076 两处），一次卸载 N 张 mesh × M 个 LOD 就是 N×M 条，其中多数空跑，量级 < 1ms、一次性、不在热路径。

为什么不能简单地「只针对 SplineVertexFactory」：判据必须 GT 可见，而指针由 RT 写。曾考虑加 std::atomic<bool> 门控，但 FStaticMeshVertexFactories 被放进 TArray（StaticMeshResources.h:703 / StaticMeshResources.h:770），而 atomic 不可拷贝，加进去 TArray 直接编译不过。若将来确要优化，正确做法是把标志放在 UStaticMesh 上、且必须在「入队侧」置位（在 RT 建完才置位会留下「已入队未执行」的窗口，又变回漏释放）。

8.2 流送通知移出录制范围（锁环）

第二层引入了一个新的等待关系：RT 会等 worker 关闭列表。而 worker 在录制范围内取 StreamingManagerTexture 的锁（StreamingManagerTexture.cpp:1567），GT 侧持同一把锁并调 FlushRenderingCommands（StreamingManagerTexture.cpp:2491-2520）—— 形成 GT 持锁 → RT 等列表关闭 → worker 等该锁 的环。

解法：把 SceneProxy 创建后的流送通知挪到 FRecordScope 生命周期之外（新增 FAddPrimitivesTask::NotifyStreaming，AsyncRegisterLevelContext.cpp:538；调用点 AsyncRegisterLevelContext.cpp:441）。不是挪出 worker 线程 —— 流送时机不变，只是让 RT 在 root Close() 那刻就解套。传参用 RenderCommandList ? &ComponentsToNotify : nullptr，保证 cvar=0 时行为与改动前逐字等价。

残余风险：CreateRenderState_Concurrent fallback 分支里 SkinnedMeshComponent::InitLODInfos 的 FlushRenderingCommands 无法用同一手法拆解（该分支必须在录制范围内），低概率，接受并观察。

9. 排错记录与方法论

9.1 跑测抓出的真 bug：并发 Add 导致 double free

现象：首次跑测 262s 崩溃，EXCEPTION_ACCESS_VIOLATION writing address 0x8，调用栈全在本次改动的代码上。
根因：锁环修复时我用 TArray<..., FConcurrentLinearArrayAllocator> 做 ParallelFor 的多 worker 收集器 —— 而 FConcurrentLinearArrayAllocator 的 Concurrent 指的是「用并发线性分配器分配」，不是「并发安全」。其 ResizeAllocation 里 Data = Realloc(Data, ...) 全程无锁，两个 worker 同时 Add 会 use-after-free + double free；0x8 正是 TArray::ArrayNum 的字段偏移。
修法：改用 TQueue<UPrimitiveComponent*, EQueueMode::Mpsc>（多生产者单消费者）。注意 TQueue::Dequeue 是非 const 方法，写成 NotifyStreaming(const TQueue<...>&) 会编译失败。
它的隐蔽性：这个 bug 逃过了 p4 diff hunk 复核、两树逐字比对、声明/定义/调用三方自查、编译通过 —— 全绿，然后实机 262 秒炸。静态验证测的全是「一致性与可编译性」，没有一环测运行时正确性。

9.2 方法论点

点说明
内容一致性 ≠ 可编译性在不能编译的工作区（无 UBT）改代码，p4 diff 再干净也只证明「写进去了」。本次因在能编译的树重编才暴露 .h 声明漏同步（error C2661/C2511），否则会随 CL 一起提交。
自查要双向只查「新类型出现了没」不够，还要查「旧类型清干净了没」。第二次编译失败正是因为 .cpp 里两处 Execute 定义签名漏改。
「Concurrent」不是线程安全承诺UE 类型名里的 Concurrent / Async / LockFree 描述的是策略，用前读实现的分配/回收路径。
原版怎么用 ≠ 你可以怎么用沿用类型却换使用模式（只读 → 并发写入）是典型陷阱。
审计的范围决定它的保证专项审计 agent 查的是「是否自锁」，不覆盖「数据竞争」。其结论「主路径无等待」为真，但不能证明「没有数据竞争」。
