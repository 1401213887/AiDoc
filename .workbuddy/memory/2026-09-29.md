### 核心结论（源码逐行验证，全部带 file:line）

| | stat unit → GPU Time | stat gpu → [TOTAL] |
|---|---|---|
| 口径 | 帧跨度（帧首戳 → 帧末戳） | 插桩 pass 的 exclusive 之和 |
| 含 GPU 空转 | 含 | 不含 |
| 含未插桩工作 | 含 | 不含 |

- **两者不是同一个量的两种算法，是两个不同的量。** 差值 ≈ 空转 + 未插桩工作。
- **本 fork 编的是旧 profiler**（`RHI.Build.cs:16` → `RHI_NEW_GPU_PROFILER=0`）。新版里两者同源（`GPUProfiler.cpp:1365-1370` 同取 `WholeFrameUnion`）本该相等；旧版走两条独立通路。
- **「切新 profiler 让两者同源」在 Android Vulkan 上走不通**：`VulkanContext.h:304-305` 的 `RegisterGPUWork` / `RegisterGPUDispatch` 是 `checkNoEntry()` 的 stub（`// @todo - new gpu profiler`），而这两个函数渲染器每帧都调 → 开了必崩。旁证：VulkanRHI 里 `FRHIBreadcrumbAllocator` / `FTimestampStream` 零命中。

### 本轮核实的关键事实

- **stat unit 链路**：`UnrealClient.cpp:392-394`（取值 + `0.9/0.1` EMA 平滑）→ `VulkanCommands.cpp:1369`（返回 `GGPUFrameTime`）→ `VulkanQuery.cpp:394-410`（`FrameTiming` 帧首/帧末两点之差）。帧首戳落点 `VulkanRHI.cpp:471`，帧末戳 `:1263`（present 之前），下一帧帧首 `:1273`。
- **stat gpu 链路**：`[TOTAL]` = `GPUProfiler.cpp:22` 定义的 `Stat_GPU_Total`；唯一写入 `GPUProfiler.cpp:33` ← `RealtimeGPUProfiler.cpp:515`，其 `TotalUs += ExclusiveTimeUs`（`:488`）是**无条件**的，所以 `r.GPUStatsChildTimesIncluded`（`:487`）只改每行 pass 显示，**不改 [TOTAL]**。
- **exclusive 是减法算的**：`:451-452` 取 inclusive，`:461` 减掉子节点 inclusive。这个减法只在事件严格树形嵌套时成立 —— 这是负值的来源。
- **Android 默认关**：`AndroidApplication.cpp:19` 默认 0；还要硬件 `timestampComputeAndGraphics == VK_TRUE`（`VulkanUtil.cpp:44`）。必须走启动期 `-dpcvars=`，运行期下发无效（全局量只在 RHI 初始化赋值一次）。
- **拼错名静默失效**：`ConfigUtilities.cpp:375/378` —— 不存在的 CVar 名只造 dummy，不报错。本项目包体写的是 `r.Vulkan.SupportsTimestampQueries`（应为 `r.Android.`），实测真名一直是 `false`，该次启动 7 处 dummy。
- **业界口径**（联网核实）：Epic 官方移动优化文档明确「大部分移动设备不直接支持 stat GPU」；CVar 隐藏的原因是 **Vulkan timestamp query 开销高**；TB(D)R 上 **render pass 内部的时间戳不可靠，最小可信粒度是一个 RenderPass**。

### 实测证据（本机）

- **开关 A/B（OPPO PMA110）**：摘掉 `-dpcvars=r.Android.SupportsTimestampQueries=1` 重启 → `stat gpu` 表格完全空白、`stat unit` 的 `GPU Time:` 有标题无数字；装回参数重启 → 完整表格 `[TOTAL] 11.00 ms`。**因果链实测成立。**
- **稳定性（小米 12S，同一静止画面三次连采）**：[TOTAL] 12.74 → 14.90 → 19.87（**+56%**）；`Mobile Scene Render` Average 抖 +71%，且其 **Min 恒为负**（−3.39 / −3.23 / −3.22）。而叶子 pass 稳定（Basepass ±0.05、VHM_CS ±0.01）。
- **自洽性**：各 pass 行 Average 之和 = 10.99 vs [TOTAL] = 11.00（差 0.01 = 四舍五入）→ **错不在汇总，在上游父项测量本身**。

### 踩的坑

1. **「铁证」被自己的 A/B 推翻**：验证过程中我把启动日志 `LogVulkanRHI: Display: - Max Descriptor Sets Bound 7, Timestamps 1` 当成「timestamp 已打开」的硬证据。翻改动前的 backup 日志比对后发现**那行改动前也是 1** —— 它是 Vulkan device limits 字段，与这个 CVar 无关。
   - **方法论**：凡是「配置生效」类判据，必须**拿改动前后的同一日志比对**再下结论；单看当前日志里的某一行，很容易把常量当变量。
2. **预处理分支要先画结构再读代码**：`GPUProfiler.cpp` 有 `#if (RHI_NEW_GPU_PROFILER == 0)`（140）… `#else`（704）… `#endif`（1704）。我引用的 `FGPUProfilerSink_StatSystem`（754-1373）落在 **`#else`（新 profiler）分支里，本 fork 根本没编译**。差点把「没编进去的代码」当成「当前在跑的代码」来推理。用 `grep -n "^#if\|^#else\|^#endif"` 先打预处理地图，几十秒的事。
3. **孤儿引用一次性冒出 17 处**：代码块里用 `// :488` 这种「同文件续写」的写法，校验脚本扫 `\`:\d+\`` 时全部命中。skill §3.1 明令严禁 —— **每一处都要带完整文件名**。已全部补全（`// RealtimeGPUProfiler.cpp:488` 等）。
4. **`RHI.Build.cs` 被自己的校验正则误报**：文件名校验正则 `[A-Za-z0-9_]+\.cs` 不含点，把 `RHI.Build.cs` 截成 `Build.cs` 报「FILE NOT FOUND」。**断言失败时先怀疑断言、再怀疑文档**（skill §3.2 原话，这次真的撞上）。
5. **写文档要写全路径族，不能只写 basename**：引用里用 `UnrealClient.cpp:392` 这种 basename 是可读的，但 `UnrealClient.cpp` / `UnrealClient.h` 同名不同目录，核对时得靠文件名映射表 —— 已在 §9 参考章列出全路径。

6. **★ 代码块「浅字压浅底」—— 沿用既有 CSS 时的必踩坑（波哥直接指出"代码看不清了"）**：
   沿用 VHM 那份的 CSS 时，`code{background:var(--code-bg)}` 里 `--code-bg` 是**浅色** `#f2f4f7`，而 `pre{color:#dfe6ee}` 是**浅色字**。
   原样式表是按 `<pre>` 里放**纯文本**写的；我按习惯写成了 `<pre><code>…</code></pre>` ——
   于是 `<code>` 自己刷了一层浅底、文字又继承浅色 → **浅字压浅底，整段代码看不见**；
   而 `.c` 注释色 `#7f8c9b`（偏深）反而在浅底上显得清楚，形成"只有注释能读"的诡异效果。
   - **修法**（一行）：`pre code{background:none; padding:0; border-radius:0; color:inherit; font-size:inherit; font-family:inherit}`
   - **方法论**：**沿用他人 CSS 时，样式表是按什么 DOM 结构写的，就得按什么结构写。** 想改结构（加嵌套标签）必须同步补一条覆盖规则。
   - **判据只能靠渲染**：纯审 CSS 时 `pre{color:#dfe6ee}` 看着完全正确，看不出问题。**是 headless Chrome 渲染后才暴露的**。
   - 顺手核了 AiDoc 全部 HTML：只有本文件同时用「浅底 `--code-bg` + `<pre><code>`」，**别的文档不受影响**。
   - 同时把注释色 `#7f8c9b` → `#94a7ba`，深底上更清楚。

### 待确认项

- **TB(D)R 在 render pass 内时间戳会被逐 tile 覆盖** 这条：Vulkan 规范里只明确禁止在 **QCOM per-tile execution mode** 下写 timestamp，**没有**通用条文覆盖所有 TB(D)R 设备。目前是「社区 / 驱动工程师说法 + 本机观测吻合」，**未做对照实验**（例如把某个 scope 的时间戳挪到 render pass 之外再测）。已在文档 §6 和证据等级声明里标注。
- **timestamp query 的开销数值**：Epic 说「开销高、部分设备会被拖慢」，但具体多少**本机没标定**。
- **该不该给 Vulkan 补新 profiler 的 breadcrumb 时间戳管线** —— 属引擎级开发，未评估工作量。
