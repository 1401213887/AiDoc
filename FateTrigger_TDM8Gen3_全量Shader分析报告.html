⚠️ 归因口径：一个 Draw 同时绑 VS+PS，其 GPU 耗时会同时计入 VS 行和 PS 行，所以各行 sum_ms 相加会超过帧总时——这是"每个 shader 的工作量权重"，不是互斥的帧时间切分。校验：VS 合计 5.81ms / PS 合计 5.81ms / CS 合计 0.38ms（CS 与帧概况的 27 dispatch≈0.37ms 吻合）。绝对耗时仍以 Snapdragon Profiler 真机为准。

三、关键发现

🔴 头号 Shader 级瓶颈：DeferredShading Cloud PS（1.43ms，GPR=44）

修正后的真·头号热点，也是全帧唯一的"寄存器型"瓶颈。24988 条指令、GPR=44 把 occupancy 压到 25%、exposed long latency 45.6%。典型"高 GPR → 低 occupancy → 延迟暴露"链条，也是全帧 GPR 最高的 shader。优化：降 GPR（拆 shader / 缩 live range / half 化 7971 条 32-bit ALU）+ 降 raymarch 步数 / 半分辨率。

🔴 次热点：ShadowProjection PS（0.811ms，访存/依赖链 bound）

阴影投影 PS：occupancy=100% 但 exposed long latency=50.1%、GPR=12——并发已拉满仍掩盖不住延迟，属访存/依赖链 bound，不是寄存器问题。优化：降 SMRT 采样数 / MaxRayCount、收紧 FadeDistance 提前剔除、页表查询局部性优化。

🟡 普遍现象：69 个访存型 shader，以 BasePass 高频 material VS 为主

全帧 69 个 shader 都是"occupancy 已满 100~200% 但延迟仍暴露"的访存型。其中累计耗时较高的是 BasePass / DepthPrepass 的高频 material VS（如 00000d94 ×176、另有 ×60、×40 复用），单个很轻、靠高复用累计。共性优化是减少纹理/buffer 访问次数、提升访存局部性，并合批降低 draw 数，而非动寄存器。（与上面 ShadowProjection 同为"访存型"，但根因不同：那个是单次重的全屏大 PS，这里是单次轻、靠数量堆起来的 material shader，优化抓手也不同——故分列。）

🟢 健康面：140/218 健康，全帧零 spill；CS 整体很轻

64% 的 shader AOC 判定健康；无任何 GPR spill。修正后 全部 Compute 累计仅 0.38ms（与帧概况 27 个 dispatch≈0.37ms 吻合），CS 不是本帧瓶颈。TAA/Tonemap/GTAO 等后处理寄存器与 occupancy 正常，耗时主要是填充率/几何吞吐。

方法论价值：全量去重 + 按累计耗时归因，仍能区分"单次重的大 shader"与"单次轻但高频的 material shader"两类目标（如 BasePass 的 ×176 VS）。本次还暴露并修正了一个真实数据错误——初版把 Draw 上残留绑定的 CS 误算进 used_by，导致虚假"头号 CS"；修正后已与帧 dispatch 总耗时严格对账。
