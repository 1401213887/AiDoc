一、核心结论速览

渲染策略

  • 前向渲染，画质切换不改管线
  • 仅 5 个 Pass，无 SSR/SSAO/Bloom/DOF
  • Vulkan PreRotation 优化（竖屏物理朝向）

资产策略

  • 4K Atlas 共用所有场景物件贴图
  • 角色/武器: BaseColor + Normal + RMA
  • 地形使用 SVT（非 RVT）

预算/Format

  • SceneColor R11G11B10 HDR
  • BackBuffer R10G10B10A2
  • ShadowDepth 3 级 CSM 1024²
总体取舍
1080P 渲染分辨率对带宽和后处理压力很大，三角洲的策略是砍掉绝大部分后处理，仅保留 EyeAdaptation + Tonemap，把性能预算让给场景密度与角色精度。

二、双管线架构（GDC 2024 披露）

重要修正
本文档前面"前向渲染管线"的描述对应的是截帧设备所在的档位（iQoo 11 上当时跑的就是前向档）。根据 GDC 2024 官方演讲，三角洲实际是 多平台分级管线：高端走延迟，其他走前向。画质等级切换不会跨管线切换，只在同一管线内调参数。
平台档位 渲染管线 关键技术 说明
PC Deferred G-Buffer + GTAO + DFAO 多光源 / 屏幕空间特效自由
高端移动设备（旗舰机） Mobile Deferred Vulkan Subpass + On-chip G-Buffer G-Buffer 全程留在 tile memory，不写主存
中低端移动设备 Forward PreZ + Forward Basepass 本文档截帧分析对应此档位
极低配设备 Forward + 退化路径 不用 VT / 不用贴花 / 1m → 2m 地形 splat map 简化为顶点单层，回退 ID Map 方法

统一资产、不重做美术 —— 虚拟材质系统

为了让美术一份资源跑全平台，团队实现了 虚拟材质系统（Virtual Material System）：

  • 编辑器中存储不同平台/不同质量级别的基础材质模板
  • 实例化为 虚拟材质实例，分配给共享模型组件的材质槽
  • 提供 解耦资源与着色器、纹理通道重映射、多平台多画质资源配置能力
  • 批处理前自动检查参数、纹理格式、Lightmap、阴影投射、IBL 一致性

Mobile Deferred 的核心：Subpass 让 G-Buffer 不离开 tile memory

RenderPass {
    Subpass 1 (Geometry):
        ✏️  写 G-Buffer 到 on-chip tile memory
        ❌  不写回 DRAM

    Subpass 2 (Lighting):
        📥  从 on-chip 直接读 G-Buffer
        ✅  零带宽
        📤  输出最终 SceneColor
}

限制：Subpass 只能读当前像素的 G-Buffer，不能采邻域 → SSAO/SSR 这类需要邻域的特效要么单独 Pass，要么干脆不做。这也解释了为什么三角洲移动端后处理这么少。

三、前向管线截帧详解（5 Pass）

下文为前向档位（iQoo 11 截帧）的实际渲染流程，高端机的延迟管线流程见上一节。

ShadowDepth · 阴影深度

3 级 CSM 1024 × 1024 / 级
  • 第 1 级覆盖 15–20m（近景细节）
  • 第 2 级覆盖 80–100m（中景）
  • 第 3 级 200m+，仅大型物体投影

Forward Basepass · 主着色

PreZPass + Basepass SceneColor R11G11B10 HDR

PreZPass：只画 Masked 材质（主要是植被），减少后续 Basepass 的 OverDraw。

Basepass 渲染顺序（前到后，借助早期 Z 拒绝）：

  1. 1P 枪械（最近，最先写 Z）
  2. 1P 人物
  3. 场景物件 Opaque → Masked
  4. 半透明（最后画）

EyeAdaptation · PS 阶段

下采样 → 198 × 90

把 SceneColor 下采样到 198×90 的小图，作为下一 Pass 计算亮度的输入。

EyeAdaptation · CS 阶段

Compute Shader

基于上一阶段的小图，用 CS 计算场景亮度系数（曝光值），供 Tonemap 使用。

Tonemap + UI · 直出 BackBuffer

BackBuffer R10G10B10A2 Tonemap 与 UI 混合

Tonemap 直接写到 BackBuffer，跳过中间 RT；之后逐个绘制 UI。

值得关注的工程取舍
Tonemap 直接写入 BackBuffer = 省一次全屏 RT 拷贝，是移动端非常激进的省带宽手法；代价是 UI 必须严格画在 Tonemap 之后，无法再做基于 SceneColor 的后处理。

四、VT Pass 通道重排（OnePass / Subpass 优化）

三角洲没有把主管线做成 OnePass，但在地形 VT (Virtual Texture) 的 Page 绘制阶段，狠用了 Subpass / FrameBuffer Fetch 思想做通道重排，是这套技术体系最有亮点的工程创新之一。

原始问题：3 张 RT 才装得下 8 通道数据

地形 VT 的 Page 需要：BaseColor RGB + Normal XY + Roughness + Metallic + AO = 8 通道。

按理 2 张 RGBA RT 就够，但贴花要 Alpha Blend → A 通道被透明度占用 → 实际数据只能放 RGB → 必须 3 张 RT。

  • 绘制阶段：3 张 RT 内存大、带宽高、写入次数多
  • 压缩阶段：3 次采样 读取带宽高

Combine Pass 优化（基于 OnePass / Subpass 思想）

绘制阶段 (Subpass 1):
    3 张 RT 写到 on-chip tile memory
        ↓
Combine Pass (Subpass 2) — 关键创新点
    通过 GL_EXT_shader_framebuffer_fetch / Vulkan input attachment
    从 on-chip 读 3 张 RT
    通道重排：释放 A 通道，每张 RT 装满 RGBA
    输出 2 张 RT
        ↓
压缩阶段:
    读 2 张 RT → 2 次采样

📊 通道布局可视化（直观对照）

收益与代价

阶段原始方案优化后收益
绘制阶段3 张 RT2 张 RT内存 -33%、写入次数和带宽降低
压缩阶段读 3 RT × 3 采样读 2 RT × 2 采样读取带宽 -33%、采样次数降低
支持的混合方式Opaque / Mask / Blend仅 Opaque + Alpha Mask失去原生半透明支持

⚠️ 容易混淆的关键点：失去的是哪一层"半透明"？

最常见的误解
看到"失去半透明支持"很容易以为：Combine Pass 让 Decal 之间的边缘变硬。
这是错的。VT 体系里其实有两层 Alpha 语义，被打掉的不是你以为的那一层。

✅ 没失去：Decal 之间的内部混合

道路 → 水渍叠加 → 裂纹叠加，这些贴花层之间的 Alpha Blend 完全保留。

原因：所有 Decal 都是在 绘制阶段（Combine Pass 之前）正常用硬件 Alpha Blend 画进 RT 的，A 通道一直在当透明度用。Decal 之间的过渡是平滑的。

❌ 失去了：VT Page 整体 vs 地形原始材质的混合

Combine Pass 把 A 通道腾出来塞数据后，VT Page 对外不再带 Alpha 通道。

后果：地形 Basepass 采样这张 VT Page 时，无法通过 Alpha 知道"这块 VT 区域应该 30% 覆盖度透出地形"，只能用 Alpha Mask（discard）做 0/1 二值判断 → VT 覆盖区域和非覆盖区域的边界变硬。

两层 Alpha 的完整流程图

─────────────────────────────────────────────────────────
阶段 1：VT Page 内部绘制（Render 阶段）
─────────────────────────────────────────────────────────
  Step1.1  画地形底层材质（草/土/岩）
  Step1.2  画 Decal 1（道路）— Alpha Blend ✅
  Step1.3  画 Decal 2（水渍叠加）— Alpha Blend ✅
  Step1.4  画 Decal 3...

  最终 RT 状态：
    RT1 = [BC.R | BC.G | BC.B | A=Page整体不透明度]
    RT2 = [N.X  | N.Y  | Ro   | A=Page整体不透明度]
    RT3 = [Me   | AO   | -    | A=Page整体不透明度]

─────────────────────────────────────────────────────────
阶段 2：Combine Pass — 通道重排（关键变化点）
─────────────────────────────────────────────────────────
  ❗ 把 A 通道里的"VT Page 整体不透明度"丢弃
  把 8 个数据通道塞满 2 张 RT 的所有 RGBA：

    RT_out1 = [BC.R | BC.G | BC.B | N.X]   ← A 通道塞数据
    RT_out2 = [N.Y  | Ro   | Me   | AO]    ← A 通道塞数据

─────────────────────────────────────────────────────────
阶段 3：地形 Basepass 采样 VT Page
─────────────────────────────────────────────────────────
  采样到 (BC, N, Ro, Me, AO) — 没有 Alpha
  ↓
  无法做 lerp(地形原始, VT采样, A) 的平滑混合
  ↓
  只能用 Alpha Mask (discard) 二值判断 VT 覆盖区域 → 边界变硬
举例理解

假设 VT Page 中间画了一个圆形水坑，圆外是"空"：

  • 原始流程：Page 圆外 A=0 → 地形 Basepass lerp 时透出地形原始材质 ✅
  • Combine Pass 后：A 被数据占用 → 圆外的"空"也被当合法 RGB 数据 ❌ → 必须用 discard 告诉 GPU "这区域走地形原始材质" → discard 是 0/1 二值 → 圆形边界一刀切硬边
如何弥补：Stipple Alpha Mask 软化"VT 覆盖边界"
在纹理空间上用 0/1 分布密度的 Alpha Mask 模拟透明度：覆盖度高的像素 1 多、覆盖度低的像素 0 多。
注意范围：补的是"VT Page 整体覆盖区域 vs 非覆盖区域"的边界（也就是 VT Page 边缘），不是补 Decal 之间的过渡。Decal 内部混合一直是真正的 Alpha Blend，本来就平滑。
因为 VT Page 像素密度高，stipple 颗粒肉眼几乎看不出，足以替代绝大部分半透明需求。
保底方案：极少数确实需要半透时
保留优化版原始方案，利用移动端低成本的 On-Chip Fetch（片上读取，不走外部带宽）把 3 张 RT 在片上合成 2 张 RT 后再送入压缩阶段，压缩阶段读取带宽仍然降低 33%。

GDC 2024 原文引用

"针对移动端，我们可以对虚拟纹理通道中使用的渲染目标进行优化。我们希望在虚拟纹理中使用 2 张纹理，并将通道进行合并，以此减少基础通道中的采样次数。但由于我们对贴花使用了阿尔法混合，所以在渲染虚拟纹理页面时，仍然需要将不透明度作为阿尔法通道。在此之后，我们使用一个子通道(sub pass)或者帧缓冲区提取(frame buffer fetch)操作，将通道重新排列成理想的形式。"
— GDC 2024《三角洲行动》跨平台技术演讲

七、地形（SVT / Clipmap）

方案选择：使用 SVT (Sampler Virtual Texture)，未使用 RVT（截帧未发现 RVT 相关 DC）。

规模：40 块地形 × 2048 面 = 约 8 万面，精度 约 1 米 / 格。

资源规格用途
地形高度图 + 法线 SVT 1024 × 1024，32 × 32 个 Tile，R8G8B8A8_UNORM 仅在 VS 中使用（顶点偏移 + 法线）
LandscapeLightMap 2048 × 2048 ASTC_UNORM 全地图烘焙好的 AO + Shadow
PageTable 1024 × 1024 R16_UINT SVT 主页表
PageTable Indirection 8 × 8 R16G16B16A16 间接采样 PageTable，标识自适应材质层 ID
PhysicalTexture × 2 5544 × 5544（21 × 21 个 Page，ASTC_UNORM） SVT 的实际像素仓库
远景地形 HLOD 整块 3000 面 替代远处 SVT 计算
隐藏巧思
路面没有独立 Mesh —— 直接用地形渲染。这意味着路面纹理混合也走地形材质层，省下大量 Drawcall。

GDC 2025 续作：Clipmap + 自适应动态纹理数组

  • Clipmap Splat ID Map：根据相机位置动态加载周边高精度，远处用低精度
  • 自适应动态纹理数组：32 种材质入库，运行时只占 8 种内存（按需加载，填充数组空隙）
  • Clipmap Texture Streaming：把大纹理内存从 133MB → 不到 2MB（约 1%）
  • Whole Scene VT Renderer：取代每区块独立 VT renderer，减少 Actor 数量、缓解卡顿
  • 3D Decal 立体贴花：模仿 Fortnite 思路，用 Z-Scale 远→近从 0 渐变到 1，移动端低成本 Tessellation 替代方案

十、关键启示与可借鉴方向

① 后处理的极端节流

1080P 移动端跑前向渲染，只保留 EyeAdaptation+Tonemap，无 SSR / SSAO / Bloom / DOF / Motion Blur。Tonemap 直写 BackBuffer 又省一次全屏拷贝。
启示：在带宽约束下，可考虑用更高质量的 Material/Lightmap 工作流来"假装"后处理效果（贴花 AO、烘焙 Bloom）。

② 阴影预算严苛分级

3 级 CSM 1024²，第 3 级仅大型物体投影 —— 明确按距离裁掉小物件投影。
启示：远景阴影投影列表通过物件 Bounds + Tag 过滤即可大幅省时。

③ 共用 Atlas 是 Drawcall 杀手锏

整栋房屋 4 DC、11 个 POI 地基零新贴图、大部分场景物件共享 2 张 4K 图。
启示：早期资产生产规范要强制共用图集，配合 PrebuildAtlas/Toolchain 自动化检查。

④ Normal 贴图通道复用

R/G = 法线 XY，B = Roughness（猜测），A = Mask —— 1 张图承担 4 种数据。
启示：移动端材质层标准化 RMA + 副通道压缩，是省内存最快的工程化手段。

⑤ 地形选 SVT、不做路面 Mesh

SVT 配合自适应材质层 ID（PageTableIndirection）、远景 HLOD、路面用地形渲染替代独立 Mesh。
启示：路面是开放世界 DC 大头之一，把路面"画"进地形材质层可大幅减少 DC 与重复几何。

⑥ Vulkan PreRotation 几乎是必选

避免 Android 系统因屏幕旋转再做一次合成。
启示：所有手游横/竖屏切换前都应确认是否启用 PreRotation，移动端节省可见。

⑦ 反射用低精度 Cubemap + 缓存

角色武器全用 64²×6 ReflectionCaptureTexture，且不每帧重建。
启示：手游对反射精度的容忍度比预想高，缓存 + 低分辨率 cubemap 已经够用。

⑧ 用 Subpass / FrameBuffer Fetch 做"通道重排"是手游 OnePass 思想的精髓

三角洲 VT Pass 的 Combine Pass 不是为了"减 Pass 数"，而是为了把多张 RT 在 on-chip 内重新打包成更紧凑的格式，节省内存、写入次数、带宽和后续采样次数。
启示：当一个 Pass 的输出受到外部约束（比如 Alpha Blend 占用 A 通道）导致 RT 数膨胀时，下一个 Pass 立即用 framebuffer fetch 做 channel repack，是手游优化里"几乎免费的高收益操作"。

⑨ 双管线分级 + 虚拟材质系统是端手一体的标准答卷

美术做一份资源，靠虚拟材质系统映射到不同平台的不同管线（前向 / 延迟），不同档位差异化只在参数而不是算法。
启示：一旦项目要做端手一体，材质系统必须先做平台抽象层，否则后期重做美术成本巨大。
