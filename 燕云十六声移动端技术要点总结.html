一、核心结论速览

渲染策略

  • 移动端 Mobile Deferred + Subpass（Vulkan）
  • 低端机回退 Forward
  • 大世界异步流送，无明显 loading

核心技术

  • 水墨美学：色彩偏柔，描边细而不锐利
  • 地形 GPU Driven + Virtual Texture
  • 大量自然要素（雨、雪、雾、风）

预算/Format

  • SceneColor R11G11B10
  • G-Buffer 仅在 tile memory（Subpass）
  • Shadow 2~3 级 CSM
燕云的工程定位
网易 Messiah 引擎是为"跨端开放世界"准备的，目标对标手游、PC、主机统一发版。燕云十六声是 Messiah 在大世界品类的代表作之一，移动端走 Mobile Deferred 路径 是关键决策——这与三角洲移动端的高端档思路一致。

三、Pass 顺序与 RT

Pass 1 · ShadowMap

3 级 CSM（高档），分辨率 1024² ~ 2048²。低档 2 级 1024²。

Pass 2 · GBuffer（tile memory）

Mobile Deferred 在 Subpass 内写 GBuffer 不写主存。GBuffer Format 高度精简（B8G8R8A8 + R10G10B10A2）。

Pass 3 · Lighting（tile memory 直读）

主光 + 静态局部光。无 SSAO / SSR（移动端）。

Pass 4 · Sky / Atmosphere

大气散射 LUT，远景体积云。

Pass 5 · Translucency

水、特效、雨/雪粒子。

Pass 6 · PostProcess

Bloom + Tonemap + 色调（中国风偏柔的色彩曲线）。

三·补 Mobile Deferred 管线深度解析

为什么燕云敢上 Mobile Deferred
传统 Deferred 在移动端最大的问题是 GBuffer 带宽——3~4 张 RT 反复写回主存（DDR），手机带宽和发热都顶不住。燕云走的是 Vulkan/Metal Subpass 路径，让 GBuffer 全程留在 Tile Memory（片上 SRAM）里，Lighting 直接从 tile 读，三张 GBuffer 不写主存。这条路只在 Tile-Based Deferred Rendering（TBDR / TBR）架构上跑得通——也就是 PowerVR、Adreno、Mali、Apple GPU。

1. Tile Memory 与 Subpass 的关系

移动 GPU 把屏幕划分成 16×16 或 32×32 的 tile，每个 tile 单独进 SRAM 处理。Subpass 的核心约定：

  • 同一个 RenderPass 内的多个 Subpass 共享同一块 tile memory
  • Subpass 之间用 VK_ATTACHMENT_LOAD_OP_LOAD 不需要回主存——这是 InputAttachment 机制
  • 只有进入下一个 RenderPass 或 STORE_OP_STORE 时，才会真正写回 DDR

燕云一个 frame 在主场景的 RenderPass 大致是：GBuffer → Lighting → Sky → Translucency 全部塞在一个 RenderPass 的 4 个 Subpass 里，只在最后把 SceneColor（R11G11B10，4 byte/px）写回主存。

2. GBuffer 布局（精简版）

SlotFormatRGBAbytes/px
RT0 AlbedoB8G8R8A8Albedo.rAlbedo.gAlbedo.bOcclusion4
RT1 NormalR10G10B10A2NxNyNzShadingModel(2bit)4
RT2 MaterialB8G8R8A8MetallicRoughnessSpecularCustom4
DepthD24S8深度 + Stencil（用于光照分类）4
SceneColorR11G11B10Lighting 输出，唯一写回主存的 RT4

合计 tile 占用约 20 byte/px。Adreno 740 单 tile SRAM 约 1MB，能容纳 32×32 tile 下的全部 GBuffer + Depth + SceneColor，不会发生 tile spilling（一旦 spill 性能立刻崩盘）。

为什么不用 GBuffer 压缩（Octahedron Normal、YCoCg Albedo）
Tile memory 模式下，GBuffer 不进 DDR，压缩节省的是 0 带宽，反而增加 encode/decode ALU 开销。所以燕云没像 UE 桌面 Deferred 那样搞复杂的 packing，直接用最朴素的 B8G8R8A8 + R10G10B10A2。

3. Lighting Subpass 的细节

  • 主光（Sun）：1 个全屏 Quad，直读 tile 内 GBuffer，CSM 采样 + PBR 计算
  • 局部光：用 Stencil 分类（按 ShadingModel 的 2bit 标记）+ 光体积 mesh（球/锥）减少 overdraw
  • 没有 Clustered Lighting：燕云的局部光数量受控（每屏 8~16 个动态光），传统 Light Volume 已够用，避免 compute shader 在低端机上的开销
  • 无 SSAO / SSR：因为这两个都需要从主存读 Depth/Normal，破坏 Subpass 链；改用 baked AO + Cubemap Reflection

4. ShadowMap 必须在 RenderPass 之外

ShadowMap 是独立 RenderPass，原因有两个：

  • Shadow 的 viewport 和主相机不同，不能塞进同一个 tile 划分
  • Lighting Subpass 需要把 Shadow Texture 作为普通 SampledImage 读取（不是 InputAttachment），所以 Shadow 必须先 STORE 出来

燕云的 Shadow 走法：CSM 3 级（高档）/2 级（低档），每级分辨率 1K~2K，异步预读 + 帧间 cache——静态阴影一帧只更新一级，动态部分单独维护 Receiver Mask。

5. 与 Forward 路径的对比

对比项Mobile Deferred + Subpass传统 Forward / Forward+
动态光支持几十个，光体积剔除高效每物体 4~8 个，超出需 Clustered
带宽（每像素）≈4 byte 写（仅 SceneColor）≈4 byte 写（HDR Color）
Tile 占用≈20 byte/px（GBuffer 全在 tile）≈8 byte/px（仅 Color+Depth）
Shader 复杂度Lighting 集中，Material Shader 简单每个材质都要做全套光照
MSAA不支持（GBuffer MSAA 成本爆炸）支持 2x/4x
半透明必须独立 Forward Pass原生支持
分档下限需 Vulkan 1.1+ / Metal 2.0+ 且支持 InputAttachmentOpenGL ES 3.0 即可

6. 低端机回退 Forward 的触发

  • 设备黑名单：Mali-G57 以下、Adreno 620 以下、不支持 Vulkan 1.1 或不开启 SubpassDescription
  • 降级后差异：动态光从"任意数量"降到"每物体 2 主光"；体积云换贴图；雾从 volumetric 降到 distance fog
  • 美术资源不变：GBuffer 模式和 Forward 模式共用同一套材质，仅 shader 走分支编译（USE_DEFERRED 宏）

8. 常见踩坑

  • Subpass 链一旦中断带宽就爆：调试时插一个 readback、或者错误地把 RT 标记成 STORE，整帧带宽立刻翻 3 倍
  • InputAttachment 读取限制：只能读当前像素位置（不能像 texture 那样偏移采样），所以 SSR/SSAO 无法做
  • Tile size 自适应：GBuffer 越大，GPU 自动选越小的 tile（如 16×16），fragment 数量翻倍，得做平衡
  • RGB10A2 Normal 精度：水面、丝绸等高光物体在低光照下能看出色阶——燕云在材质上做了 dithering 缓解
  • 半透明不能进 Subpass 链：必须在 Lighting 完成后独立 Forward Pass，否则会和 GBuffer 写冲突

四、大世界场景

地形

  • GPU Driven Heightmap，所有地形 Patch 由 GPU 决定 LOD
  • SVT 多层贴图（草、土、石、雪等 6+ 层）
  • Decal 大量使用，地表脚印/痕迹/血迹
  • 移动端低档退化为静态 Mesh Patch + 单层贴图

建筑

  • 古风木构建筑，多 Mesh 拼接
  • Atlas 共享贴图，大量复用
  • 室内"假"光影：Light Probe + 局部 Cubemap，无实时 GI

植被

  • 近：完整 Mesh + 风动顶点偏移
  • 中：LOD 简化 + Billboard 树叶
  • 远：Imposter（多角度烘焙）
  • "竹林"是燕云特色，密集竹竿用 Mesh Instancing 大批量绘制

HLOD

  • 整片山谷烘焙为单 Mesh + 4K Atlas
  • 切换距离按机型分档
  • HLOD 之间过渡用 dither fade

天气是核心卖点
燕云十六声主打"国风四时风物"，天气 + 季节 + 时间是核心体验。技术上需要大量动态系统。
系统实现移动端代价
大气散射预计算 LUT，运行时采样低
体积云Ray March（PC）/ 贴图近似（移动）中
雨粒子 + 屏幕空间湿度（高档）中

雾Distance Fog + Volumetric Light Shaft（高档）高

六、水体与笔触感

  • 湖面：Gerstner 波 + 屏幕空间反射（高档）
  • 河流：Flow Map 控制水流方向
  • 水墨笔触：水边 Foam 用噪声贴图模拟"晕染"，与一般 SSR 水边白沫不同
  • 角色入水：动态 RT 写入 displacement，移动端简化为单点扰动

七、武侠战斗特效

  • 剑光 Trail：Mesh Trail + 流光贴图，飘逸感是核心，避免硬边
  • 气功 / 内力：屏幕空间扭曲 + 浅色调 Glow，类似"内功波"
  • 轻功：高速移动时全屏 Vignette 扩张 + 速度线（轻量，非绝区零式漫画风）
  • 命中冲击：屏幕震动 + Bloom 暴增，配合武侠"击中要害"的爽感

八、移动端性能策略

分档

  • 低/中/高/超高，旗舰机推 60/120 fps
  • 低档关 SSR/SSAO/体积云/动态雪 → 改为静态贴图
  • 超高档对标 PC 中档

开放世界 streaming

  • 分块 1km × 1km，前后各 2 块预读
  • 角色队伍 + NPC 资源 LRU 缓存
  • 纹理 Mip Streaming，距离决定 Mip 上限

带宽与发热

  • SceneColor R11G11B10 + GBuffer 不写主存（Subpass）
  • RDG Pass 合并，减少切换次数
  • 5 分钟后温度高自动降分辨率（DRS）

九、关键启示

对开放世界手游

  1. Mobile Deferred + Subpass 是高画质开放世界的最优解
  2. SVT + GPU Driven 地形是大世界标配
  3. Imposter + HLOD 解决远景植被和建筑

对国风/写实项目

  1. 水墨美学的关键是"边缘晕染"，不是高分辨率
  2. 天气系统应分档实现，避免低端机被"四时风物"压垮
  3. 战斗特效要"飘"不要"硬"，Trail 与 Glow 是核心
