1. 结论速览（TL;DR）

一句话定义 GPUScene 是 CPU 端场景数据在 GPU 上的镜像：把每个 Primitive / Instance 的着色器参数（变换、Bounds、Flags、Lightmap 索引…）打包进全局 GPU Buffer，让 顶点工厂按 ID 索引取数、让 Compute Shader 在 GPU 上做剔除，从而同时干掉两条 CPU 侧瓶颈——每图元一次 UBO 绑定的 draw call 开销与 CPU 逐实例剔除开销。

2. GPUScene 要解决什么问题

2.1 GPUScene 之前的做法

UE4 早期（约 4.22 新网格绘制管线之前），每个 Primitive 渲染时需要在 CPU 侧单独绑定自己的 Uniform Buffer（per-primitive UBO），一个静态网格 = 一次 draw call 的完整 setup。要把 1000 个同材质的石头画出来，就是 1000 次 DrawIndexed 的 CPU 开销。

当时的实例化只有两条路：

  • ISM/HISM：组件级实例化，需要显式使用 UInstancedStaticMeshComponent，且实例数据走专用顶点流（InstanceOriginBuffer / InstanceTransformBuffer / InstanceLightmapBuffer…）。
  • 手动合并：美术/TA 把相同物体合并成一个 mesh，用顶点色或 UV 区分位置。

2.2 GPUScene 带来的三个转变

注意：GPUScene 不是「省带宽」的技术，而是「省 CPU」的技术 它把数据从「每图元一次小 UBO 绑定」换成「一个大 SSBO/Texture 随机读」。GPU 侧的随机访存成本是上升的（对 cache 不友好），换来的是 CPU 提交成本与剔除成本的大幅下降。在移动端这个取舍常常不划算——这正是 Mobile 走 UBO 常量展开、甚至在 Proxy 层直接退回 PrimitiveUB 的原因（见第 8 章）。

3. 全局架构与数据流

关键设计点：Buffer 是「每 Scene 一份」，不是 per-View 所有 RDG 操作都带 RDG_GPU_MASK_SCOPE(All) GPUScene.cpp:959,1996，说明这份数据在异步计算/图形队列间共享。双目（InstancedStereo / MultiView）共用同一份 GPUScene 数据，视图差异通过 per-view 的 SceneUniformBuffer 与动态图元收集器体现，而不是复制 Buffer。这避免了「视图数 × 场景数据」的内存翻倍。

4. 数据结构详解

4.1 Buffer 家族全景（C++ 侧）

4.2 Primitive 数据布局（46 × float4）

Primitive 是 GPUScene 的根节点——Instance 通过 InstanceSceneDataOffset 挂到 Primitive 上，所有 Instance 共享 Primitive 的材质、Bounds、Lightmap 索引等。

4.3 Instance 数据布局（SoA）

SoA 是 Instance 数据的关键设计 与 Primitive 的 AoS（每图元一整块 736 B）不同，Instance 采用 Structure of Arrays：数据按「列」拆开存放，索引公式是
element(slot, instanceId) = SlotIndex × SOAStride + InstanceId　SceneData.ush:1211、GPUSceneWriter.ush:25
⚠ 别把 SOAStride 当成 3 或 4：它是实例容量——buffer 能容纳的实例总数向上取 2 的幂，同时也是相邻两个 slot 之间相隔的 float4 数　GPUScene.h:343、GPUScene.cpp:1047。而 3 / 4 是 slot 的个数（压缩 / 非压缩），两者相乘才是 buffer 的总 float4 数。
举例：若 SOAStride = 8、3 个 slot，则实例 5 的 slot1 落在第 1 × 8 + 5 = 13 个 float4；整个 buffer 共 8 × 3 = 24 个 float4（384 B）。
最硬的证据在扩容逻辑里：buffer 尺寸变化需要重建时，拷贝是按 slot 分段做的（循环 NumArrays 次逐段搬移，而不是一次连续拷贝）——这正是 SoA 结构的直接体现　UnifiedBuffer.cpp:667-678。
这样做的好处是：InstanceCulling 的 Compute Shader 按 instanceId 并行遍历时，同一个 thread group 内的线程读的是同一段连续的地址（读 slot0 时全组连续，读 slot1 时也全组连续），coalescing（访存合并：同一个 warp 内 32 个线程在一次访存指令中的地址若连续，硬件会把它们合并成少数几次内存事务，而非逐线程发 32 次）近乎完美。若是 AoS，相邻线程会以 48 B 的步长跳着读，一个 128 B cache line 只能覆盖 2~3 个线程。

为什么要压缩 Instance 变换？

压缩变换 FCompressedTransform2 用「八面体编码旋转 + 共享指数压缩缩放」把 3×4 矩阵压到 2 个 float4：

  • 旋转：用 2 个 16 位整数做八面体（octahedral）编码，误差约 0.1°——对于实例级旋转完全够用（对比 Primitive 级的 LWC 精度需求）。
  • 缩放：与平移共享一个指数，即 Scale 与 Translation 使用同一量级，牺牲极端非均匀缩放的精度。
  • 收益：48 B vs 64 B，省 25% 带宽。实例数上百万时这是显著的。

是否启用由平台 DDSPI 决定：FDataDrivenShaderPlatformInfo::GetSupportSceneDataCompressedTransforms() InstanceUniformShaderParameters.cpp:8-23。本分叉还加了 GR_COMPRESSE_WORLD_MATRIX 宏（SceneData.ush:1219）进一步定制了这条路径。

勘误：网上流传的「VisibilityId 32 位（高 16 位视锥/低 16 位遮挡）」在本版本源码中不存在 该说法把「Primitive 的 VisibilityFlags（16 位，表示在哪些 View 类型中可见）」误当成了「Instance 的逐 View/逐遮挡体剔除结果位图」。本版本中：
• Primitive slot[0].w 的高 16 位 = VisibilityFlags（视图类型可见性，不是剔除结果）SceneData.ush:491-495
• Instance 侧没有 VisibilityId 字段，可见性由 INSTANCE_SCENE_DATA_FLAG_HIDDEN + GPU InstanceCulling 的 InstanceIdsBuffer 输出承担。
同时，本仓库中也搜不到这些网上常见的 API 名：DispatchCullingComputeShader()、r.GPUScene.DistanceCull、VisibilityFlagsBuffer。详见第 10 章勘误。

4.4 InstancePayload — 为什么要把数据「拆出去」

Payload 是一个变长的、与可见性解耦的旁路数据区。之所以不把所有这些字段都塞进 instance 那一小块，原因有三：

  1. 体积差异极大：一个普通静态实例可能只有 3 float4；但带 GPU 蒙皮 + 每实例 CustomData + Lightmap UVBias + 局部 Bounds 的实例可能要 10+ float4。固定 stride 会让所有实例为最坏情况买单。
  2. 更新频率不同：Prev 变换（DynamicData）每帧都可能变，而 SkinningData 很少变。分离存储让上传能按需增量。
  3. 可见性与属性的解耦（最关键）：同一个实例在 View A 可见、在 View B 被 HZB 剔除，这不需要重写 payload——payload 是「这个实例是什么」，可见性是「这个 View 要不要画它」。两者彻底分离，才让 GPU 剔除结果可以直接局部化在 per-View 的 InstanceIdsBuffer 中。

PrevLocalToWorld 的三种来源（很值得记住） 注意：Prev 变换并非「上一帧矩阵」直接存在 instance slot 里，而是按需放在 Payload 的 DynamicData 段，靠 Flag HAS_DYNAMIC_DATA 标记 SceneData.ush:1079。着色器取它时有三条路 SceneData.ush:1299-1332：
① 有 HAS_DYNAMIC_DATA → 从 Payload 解压出 PrevLocalToRelativeWorld，再经 MakeDFMatrix(PositionHigh, …) 还原成世界矩阵（实例自己动过）；
② 没有 → 用 mul(LocalToRelativeWorld, PrimitiveData.WorldToPreviousWorld) 推导——即「实例自身没动，但它的 Primitive（如挂在动态 Actor 上）动过」。
后者是非常聪明的优化：一个移动父 Actor 下的 1000 个静态实例，不需要为每个实例存一份 Prev 变换。
③ 移动端 UBO 路径且未启用 Instance Culling → 整个 InstanceData 直接从 Primitive 填充，PrevLocalToWorld = Primitive.PreviousLocalToWorld SceneData.ush:1411、SceneData.ush:1480。

5. 数据是怎么上到 GPU 的

5.1 GPU 端写入（Deferred GPU Write）

有一类数据 CPU 根本拿不到，只能在 GPU 上算完再写回 GPUScene。按「写完的时机」分成两条通道，这个区分是本节最要紧的一点：

  • 通道 A：上传期立即写（DataWriterGPUPass = None，默认值）。在 UploadDynamicPrimitiveShaderDataForViewInternal 里当场执行，所以PrePass 之前就已就绪。实例：PCG 程序化实例 PCGInstanceDataInterface.cpp:255-287。
  • 通道 B：延迟到 post-opaque 才写（= PostOpaqueRendering）。注册进 DeferredGPUWritePassDelegates[]，等不透明渲染与 FX 都走完再统一写，所以落在 PrePass 之后。实例：Niagara 低延迟半透明粒子网格 NiagaraRendererMeshes.cpp:1303-1305。
  • 在 GPU 上做的还有「反算」：给出 LocalToWorld 后，WorldToLocal 需要求逆；Prev 相关矩阵需要帧间推导——这些放 GPU 算更划算，能避免回读。
// GPUSceneWriter.ush 的开头就显式声明：本次编译要写全局场景数据
#define USE_GLOBAL_GPU_SCENE_DATA_RW 1

// 写入 instance 的压缩变换（编码 octahedral 旋转 + 共享指数缩放）
WriteInstanceLocalToRelativeWorld(...)   // GPUSceneWriter.ush:89-108
WriteInstanceLocalToWorld(...)           // GPUSceneWriter.ush:121-126  做 WS → LWC 相对化
InitializeInstanceSceneData(...)         // GPUSceneWriter.ush:134-154  与 CPU BuildInternal 对齐

这些写操作被组织成「延迟 GPU 写 pass」：调用方注册委托 + 目标 pass 枚举，由 ExecuteDeferredGPUWritePass() 在合适的时机统一 dispatch GPUScene.cpp:2292-2336，并通过 View.GPUSceneViewId 匹配 per-View 数据 GPUScene.cpp:1879,2322。

写入 pass 枚举（EGPUSceneGPUWritePass） 本分叉（5.5.4）里只有 两档：None = -1 与 PostOpaqueRendering，定义于 GPUSceneWriter.h:43-52。语义是：None = 上传时就写（或压根没有 GPU 写入需求）；PostOpaqueRendering = 等不透明渲染与 FX 的 post-opaque update 都做完再写。
唯一执行点是 ExecuteDeferredGPUWritePass() GPUScene.cpp:2292，在不透明渲染之后被调用 DeferredShadingRenderer.cpp:3930；一旦本帧真的写了数据，紧接着重跑一轮实例剔除 DeferredShadingRenderer.cpp:3932——新写入的实例此前从未参与剔除，后续 pass（半透明等）必须能看见它们。
注册时还有个防呆：若目标时机「本帧已经过去了」（GPUWritePass <= LastDeferredGPUWritePass），就不再延后、当场立即执行 GPUScene.cpp:1870-1878。
⚠️ 网上不少资料（含本文早期版本）把枚举写成 None → PostInitViews → PostPrepass → Num——本仓库没有这两个值。全文检索 PostInitViews / PostPrepass 只命中 FXSystem 的同名方法 FXSystem.h:247（GPU 粒子模拟的推进入口），与 GPUScene 写入时机无关，照那个名单去找代码会找不到。

5.2 为什么 PrePass 之后还会冒出动态图元？

这不是特例，而是设计上的必然：主上传固定在帧初做一次（上图 ①② 之前），而那之后的三类「生产者」天然晚于它，数据根本还不存在。

晚到的生产者为什么晚（而不是「顺手漏了」）证据
阴影视图的动态图元动态阴影 setup 排在 PrePass 之后（:2708 > :2578）。每个阴影视图自带一个 collector，要在这里才 Commit 并上传自己的动态图元DeferredShadingRenderer.cpp:2708、ShadowRendering.h:874、ShadowSetup.cpp:7616-7645
Niagara GPU 粒子网格粒子模拟推进发生在 post-opaque 的 FX 阶段；实例数量都来自 GPU buffer（GPUParticleCountBuffer），CPU 此刻一无所有，所以只能挂延迟写入DeferredShadingRenderer.cpp:3925、NiagaraRendererMeshes.cpp:1256、NiagaraRendererMeshes.cpp:1303-1305
View elements / PDIInitViews 期间才生成（调试绘制、光源影响域可视化等），走 per-view collector，在 InitViews 内上传DynamicPrimitiveDrawing.h:20、DeferredShadingRenderer.cpp:2107

引擎自己把这条因果关系写在注释里，GPUScene.h:370-373：

// Buffers used by GPU-Scene, since they can be resized during updates AND the render passes must retain the
// right copy (this is chiefly because the init of shadow views after pre-pass means we need to be able to set
// up GPU-Scene before pre-pass, but then may discover new primitives etc. As there is no way to know how many
// dynamic primitives will turn up after Pre-pass, we can't guarantee a resize won't happen).
连带的两个设计后果 ① 写完必须补偿剔除。ExecuteDeferredGPUWritePass 返回「本帧是否真的写了」；为真则紧接着 BeginDeferredCulling 再跑一轮 DeferredShadingRenderer.cpp:3930-3933——新写入的实例此前从未被剔除过，不重跑，后续 pass（半透明等）就看不见它们。这也正是剔除要用「延迟编排」而不能一股脑 dispatch 的原因。
② 早先的 pass 必须留住旧 buffer 视图。既然 PrePass 之后还可能 resize，RDG 注册结果就被缓存成 CachedRegisteredBuffers，并在每次上传后刷新 GPUScene.cpp:1100-1106，保证「先注册的 pass 拿旧的那一版、后到的写入拿新的那一版」，两边都对。

6. 自动合批（Auto Instance / Dynamic Instancing）原理

6.1 合批发生在哪一步

UE 5.x 里已经没有 bAutoInstance 之类的标志了（我全文检索未找到），取而代之的是 StateBucket（状态桶）+ Dynamic Instancing 机制：

6.2 合批后，每个实例怎么找到自己的数据

合批解决的是「一次 draw 画多个实例」，但着色器还需要知道「我现在画的是第几个实例」。UE 的答案是一条专用顶点流属性：InstanceIdOffset（顶点流本身的机制见下节 6.3）。注意这里有三步，中间夹着一层容易漏看的间接寻址。

// 顶点工厂侧：InstanceIdOffset 声明为顶点流属性（步进率 0 = 整个 draw 一个常量）
// VertexFactoryCommon.ush:34（ATTRIBUTE 编号随 VF 而异，LocalVertexFactory 用 13）
uint InstanceIdOffset : ATTRIBUTE13;
uint DrawInstanceId  : SV_InstanceID;

// 着色器侧（SceneData.ush:1394-1468）
GetSceneDataIntermediates(InstanceIdOffset, DrawInstanceId)
{
    // 第 1 步：本 draw 在「紧凑可见实例清单」里的起始下标 + 本次绘制序号
    InstanceIdLoadIndex = InstanceIdOffset + DrawInstanceId;    // SceneData.ush:1425

    // 第 2 步：查表并解包，得到真正的 GPUScene 实例 ID
    const uint PackedId = InstanceCulling.InstanceIdsBuffer[InstanceIdLoadIndex];  // :1452
    UnpackInstanceCullingOutput(PackedId, InstanceId, ViewIndex, CullingFlags);    // :1454

    // 第 3 步：用真正的 InstanceId 去搬实例数据
    InstanceData = GetInstanceSceneData(InstanceId, Scene.GPUScene.InstanceDataSOAStride);  // :1462
}
InstanceIdLoadIndex 到底是什么 —— 它是一层间接寻址，通常不等于 InstanceId
  • 它索引的不是 InstanceSceneData，而是 InstanceIdsBuffer —— 剔除阶段（BuildInstanceDrawCommands）用原子累加紧凑写下的「可见实例清单」BuildInstanceDrawCommands.usf:118
  • 表里存的也不是裸 ID，而是 PackedId：低 24 位是 InstanceId │ 接着 4 位 CullingFlags │ 高位 ViewIndex SceneData.ush:1359-1372
  • 解包出来的 InstanceId 才是 GPUScene 的全局物理槽位（24 位，上限 224 = 16,777,216 个实例 SceneDefinitions.h:14），用它去 SoA buffer 寻址
为什么非要这一层？因为剔除是并行的、可见性事先未知，InstanceSceneData 里装的是全部实例（含已被剔掉的），不连续、不紧凑。而要让 DrawIndexedIndirect 一次画完 N 个可见实例，就必须先把它们按剔除结果紧凑地誊到另一张表上 —— InstanceIdLoadIndex 就是这张表的下标。

什么时候两者相等？这取决于顶点流里 InstanceIdOffset 的最高位 —— 它不只是偏移，还兼任「身份标志」（SceneData.ush:1434-1456）：

6.3 顶点流（Vertex Stream）到底是什么

6.2 说「InstanceIdOffset 来自顶点流」，但这条流本身值得单独讲清楚 —— 它是 IA（Input Assembler）阶段的输入源，机制比多数人以为的更朴素：它不是「一条数据」，而是「一个槽位的绑定关系」。

所以最终实例索引是两条路各出一半：InstanceIdOffset 来自顶点流（per-draw 常量），DrawInstanceId 来自 SV_InstanceID（硬件按 InstanceCount 自动生成 0…N-1）。两边相加才是 InstanceIdLoadIndex（见 6.2）。

顺带：BuildMeshDrawCommandPrimitiveIdBuffer 里那个按 InstanceFactor 复制多份的循环 MeshDrawCommands.cpp:692-696 带有 //@todo - refactor into instance step rate in the RHI，说明这是尚未重构完的旧机制。

7. InstanceCulling 原理

7.1 为什么要把剔除搬到 GPU

CPU 剔除的问题不是「算法慢」，而是规模：每帧对 10 万个实例做一次 matrix/bounds 变换 + 视锥平面测试，即使每次只要 100 ns，也是 10 ms 级别的开销，而且这是串行占满一个核的成本。传统做法还要把结果从 CPU 传到 GPU（每帧几 MB 的可见列表）。

GPU 剔除的价值在于：剔除所用的 Bounds、变换、Flags 本来就已经在 GPUScene 里了，不需要额外传输；剔除结果直接落在 GPU 的 indirect args 里，完全不需要回读 CPU。

8. PC / Mobile 差异对比

先立结论：移动端不是「缩小版 PC」，而是「另一条数据通路」 PC 用 SSBO / Texture2D 动态索引；移动端 ES3_1 走 Primitive UBO 常量展开（UniformView 路径），并且在 Proxy 层面直接把 bSupportsGPUScene 置为 false 回退到 per-primitive uniform buffer。两者的数据布局、访存模型、可用特性都不同。

8.1 开关判定链

8.2 数据通路对比（核心差异）

为什么移动端要用 UBO 而不是 SSBO？ 移动端 GPU（尤其早期的 Mali/Adreno）对 SSBO 随机读的支持与性能参差不齐：SSBO 读会走通用数据通路、消耗 L2 带宽，且很多驱动对「顶点着色器里做结构化缓冲动态索引」优化不佳。
而 UBO 走的是 constant cache（通过 uniform 加载路径），很多移动 GPU 有专门的常量缓存，读 UBO 不走 L1/L2 数据带宽。用「每 draw 把所需数据写进 UBO 的一段」换取常量缓存的高效访问，是移动端的常见取舍。
代价是 UBO 大小受限（Mobile 端 primitive 512 B / instance 256 B 的滑动窗口），一旦一个 draw 涉及的图元/实例超过窗口就要分批——这也是移动端 auto-instance 批次不能无限大的根本原因。

8.4 移动端实战注意

给移动端项目的三条建议 1) GPUScene 在移动端的收益来源与 PC 不同。PC 上它省的是「draw call 提交 + CPU 剔除」；移动端走 UBO 后省的是「per-primitive 绑定的 CPU 开销」，但不省带宽，甚至可能因为 UBO 每 draw 重填而增加 CPU 侧的填充成本。
2) r.Mobile.SupportGPUScene 是 ECVF_ReadOnly，改了要重编 shader（Shader Key 中含 MobGPUSc，见 Shader.cpp:1956-1964）。所以它是「项目级决策」，不是运行时开关。
3) 社区反馈：移动端 GPUScene 的驱动兼容性风险不低。UE 官方论坛有开发者报告在部分 Android 设备上出现「场景变空」或静态网格位置错误，并指出问题出在 UBO 路径而非 GPUScene 本身（见第 10 章来源）。如果项目要用，建议按设备/驱动白名单 + 兜底开关推进，而不是全局默认开启。

10. 网络资料勘误

我在检索过程中发现，中文社区关于 GPUScene 的若干「高赞文章」存在与源码不符甚至疑似虚构 API 的内容。为避免误导，逐条列出：

网络说法源码事实判定
「InstanceSceneDataBuffer 中的 VisibilityID 是 32 位整数，高 16 位存 View Frustum Culling 结果（每 View 一 bit），低 16 位存 Occlusion Culling 结果」 本版本 Instance 数据没有 VisibilityId 字段。只有 Primitive slot[0].w 的高 16 位是 VisibilityFlags，语义是「在哪些 View 类型中可见」（如 VISIBLE_IN_GAME / VISIBLE_IN_EDITOR），不是剔除结果位图。逐 View 剔除结果存在于 InstanceCulling 的 InstanceIdsBuffer，是「可见实例列表」而非位掩码 ❌ 不存在
「FGPUScene::DispatchCullingComputeShader()」 本仓库 GPUScene.h/.cpp 中无此函数。剔除 dispatch 在 FInstanceCullingContext::BuildRenderingCommands → ProcessBatched 里完成 ❌ 疑似虚构
「r.GPUScene.DistanceCull / r.GPUScene.DistanceCullMaxDistance」 本仓库 GPUScene 相关 CVar 只有 7 个（见第 11 章），无 DistanceCull。实例距离剔除由 r.CullInstances 控制，且参数来自 Primitive 的 DrawDistanceSq，不是全局 CVar ❌ 不存在

「PC 端 PrimitiveSceneData stride = 42」 本版本 PRIMITIVE_SCENE_DATA_STRIDE = 46（SceneDefinitions.h:90）。42 可能是更早版本（5.0/5.1 时代）的数字 ⚠ 版本差异

11.4 调试建议路径

  1. 确认 GPUScene 是否生效：看 UseGPUScene() 的返回；用 r.GPUScene.DebugMode 可视化。
  2. 怀疑合批失效：r.MeshDrawCommands.LogDynamicInstancingStats 1，对比 InstanceCount 与 DrawCall 数；若某个 Mesh 完全没合批，先看它的 VF 是否支持 instance data（GetPrimitiveIdStreamIndex()）。
  3. 怀疑剔除过头（物体消失）：依次关 r.CullInstances → r.InstanceCulling.OcclusionCull → r.HZB.IndirectDraw，定位是哪一级误剔。特别注意移动端 HZB/UBO 的驱动兼容性。
  4. 怀疑数据不同步/花屏：临时开 r.GPUScene.UploadEveryFrame 1 验证。若开了就正常，说明问题在增量上传的 dirty 追踪（检查是否漏标 AddPrimitiveToUpdate），而不是数据布局。
  5. 移动端崩溃（GPU Pagefault）：本分叉已有先例——把 Primitive/Payload 从 Buffer 改成 Texture2D 就是为修这个（见第 9 章）。若遇到同类崩溃，PRIMITIVE_DATA_USE_TEXTURE 是既有的参考解法。

附：一页总结

数据结构：记住三个数字
46 — Primitive 的 float4 数（736 B），按 PersistentPrimitiveIndex 直索引，稀疏有洞
3 / 4 — 每实例的 slot 个数（压缩 3 / 非压缩 4，48 / 64 B），SoA 列式布局；SOAStride 是实例容量，不等于这个数
512 / 256 — 移动端 UBO 路径的 primitive / instance stride（字节）
合批：一句话
状态桶哈希相同 → 复用同一条 MeshDrawCommand 并累加 NumInstances；实例数据靠 InstanceIdOffset + SV_InstanceID 从全局 GPUScene 取。
UE4 → UE5 的质变：从「组件内实例化」到「跨组件自动实例化」。
InstanceCulling：一句话
延迟收集批次 → GPU CS 逐实例剔除（视锥/距离/屏幕尺寸/HZB）→ 原子累加 indirect args → 零回读提交。
默认只开视锥+距离+屏幕尺寸；遮挡剔除默认关闭。
PC vs Mobile：一句话
PC 走 SSBO 动态索引（容量大、吃 L2）；Mobile 走 UBO 常量展开（走常量缓存、受容量限制），且 Proxy 层强制降级、Compaction/顺序保持被禁。
移动端不是缩小版 PC，是另一条通路。
