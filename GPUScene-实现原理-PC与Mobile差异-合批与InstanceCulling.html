02动机：为什么必须有 GPUScene

2.1 没有 GPUScene 的世界

传统路径下，每个绘制物体都有自己的一份 Primitive 常量（LocalToWorld、Bounds、Flags…），走的是「一次 draw 绑一个 UBO」的模型。这直接导致两件事：

  • CPU 侧：每次 draw 都要在渲染线程/RHI 线程写入并绑定一次 UBO，绘制数一多就是瓶颈。
  • 无法合批：两个物体哪怕网格、材质、状态完全一样，只要 Primitive 数据不同，就不能合并成一次 instanced draw——因为 shader 只有一个 Primitive 槽位。

2.2 GPUScene 的三步解法

  1. 数据池化：把全部 Primitive / Instance 数据放进几条大缓冲，CPU 只维护「哪一段归谁」。
  2. ID 化：每次 draw 不再传整个 Primitive 结构，而是传一个 PrimitiveId（实例则是 InstanceId），shader 自己索引。
  3. 可剔除化：ID 列表可以在 GPU 上被并行地剔除、紧凑化，剔除结果直接喂给 Indirect Draw——这正是 InstanceCulling 存在的前提。

引擎自己在源码里把这件事写得很直白：

// SceneData.ush:51-55（逐字符照录；第 51 行在源码中就是一行，此处不折行）

注意最后一行 GR：本分叉在官方注释下追加了自研说明——这句话本身就是「PC 走 scene-wide buffer、Mobile 走 single Primitive UBO」这个二元结构的第一手证据 SceneData.ush:51-55。

2.3 关键设计取舍：为什么 Mobile 不直接用 SSBO

这是全文最重要的一条设计意图。移动端的 GPU 在「uniform buffer 读取」路径上通常有专用硬件，比 structured buffer 随机读更快、更省带宽。引擎因此做了一条分叉：

// RenderUtils.cpp:488-491
RENDERCORE_API bool PlatformGPUSceneUsesUniformBufferView(const FStaticShaderPlatform Platform)
{
    return IsMobilePlatform(Platform) && FDataDrivenShaderPlatformInfo::GetSupportsUniformBufferObjects(Platform);
}

Android 的 DDSPI 里 bSupportsUniformBufferObjects = true Android/DataDrivenPlatformInfo.ini:75，于是所有 Android 设备都走 UniformBufferView 路径；Windows 虽然也声明支持 UBO，但 IsMobilePlatform 为假，仍走 SSBO。

代价：批大小被 uniform buffer 的 16KB 硬上限锁死
走 UBO 路径后，一批实例的数据必须能塞进一个 uniform buffer。PLATFORM_MAX_UNIFORM_BUFFER_RANGE 定义为 16u*1024u，全仓库只有这一处定义（无平台覆盖）HAL/Platform.h:640-641。于是批大小 = 16384 / 每条实例步长。这就是后文 32/64 两套上限的全部来历。

5.2 为什么要 SOA：不是炫技，是剔除带宽

把实例数据「按槽位拆成多条数组」而不是「每个实例一整块」，换来的收益是：

  • 剔除阶段只读 slot 0。视锥/遮挡剔除只需要 PrimitiveId + Flags，而这两样都在 slot 0 里 SceneData.ush:1026-1030。SOA 让「读 100 万个实例的 slot 0」变成一次连续读，而不是跳着读 100 万条 64 字节记录。这是 SOA 最直接的设计意图。
  • 压缩路径可跳过无用槽位。压缩时变换只占 2 个 slot，非压缩占 3 个；SOA 下两者只是数组条数不同，寻址公式不变。

代价是同一个实例的数据被拆散在三处，「一个实例 = 连续 64 字节」这个直觉不再成立——这是读这份代码最容易犯的错。

		}
		return UploadData + ElementIndex * NumBytesPerElement;

调用点 GPUScene.cpp:1453 传的第二个参数正是 SOA 目标下标 RefIndex * SOAStride + InstanceSceneDataOffset + InstanceIndex → DstIndex = SOA目标下标 × 1 + 0。

两条路径的 CPU 写法不同（一个 Add 整个数组、一个 Set_GetRef 逐元素），却被 shader 里同一行统一吃下。

附：Size 是「线程数」，别当成「每线程字节数」

这个 shader 里有两个数很容易混，含义完全不同：

量PrimitiveInstance / Payload含义
Size（= NumThreadsPerScatter）461每条散射记录占多少线程
NumBytesPerThread1616每线程搬多少字节

关系是 Size = NumBytesPerElement / NumBytesPerThread（UnifiedBuffer.cpp:743）——Primitive 的 46 是「736 字节 ÷ 16 字节/线程」，是线程数不是字节数。

那每线程到底搬多少字节？取决于 RESOURCE_TYPE

这个 CS 有 4 个可编译分支，每线程的搬运单位并不统一：

RESOURCE_TYPE取数代码每线程字节
FLOAT4_BUFFER (0)DstBuffer[DstIndex] = UploadStructuredBuffer4x[SrcIndex]16
STRUCTURED_BUFFER (1)STRUCTURED_BUFFER_ACCESS(...) —— 按 STRUCTURED_ELEMENT_SIZE 宏展开4 / 8 / 16 / 32
UINT_BUFFER (2)Load(SrcIndex * 4) / Store(DstIndex * 4)4 ← 不是 float4
UINT4_ALIGNED_BUFFER (3)Load4(SrcIndex * 16) / Store4(DstIndex * 16)16

STRUCTURED_BUFFER 那档之所以可变，是因为 STRUCTURED_BUFFER_ACCESS 是按元素宽度展开的宏：

GPUScene 一定落在 16 字节那条，有两条独立保证：

① 目标 buffer 本身就是 float4 数组。GPUScene 的 4 条 structured buffer 全由 ResizeStructuredBufferIfNeeded / ResizeStructuredBufferSOAIfNeeded 创建，而它们硬编码 16 字节元素：

{

所以 GetStructuredBufferElementSize（UnifiedBuffer.cpp:347-355）拿到的一定是 Uint4，宏展开成 ##4x，即 StructuredBuffer<uint4>。

那条 checkf 说明了一切
GetStructuredBufferElementSize 里有："Unsupported structured buffer BytesPerElement size (%d) ... supported sizes are 4,8,16,32." —— 元素宽只允许 4/8/16/32 字节。也就是说「736 字节一个元素」这种 buffer 压根建不出来，必须先化成 16 字节元素 × 46 倍元素数。

② GPUScene 传的 NumBytesPerElement 都是 16 的倍数，故 NumBytesPerThread 必为 16（UnifiedBuffer.cpp:742）：Primitive 传 736（46×16）、Instance / Payload 传 sizeof(FVector4f) = 16。

→ 实际走 RESOURCE_TYPE_STRUCTURED_BUFFER + STRUCTURED_ELEMENT_SIZE_UINT4，每线程搬一个 uint4 = 16 字节 = 一个 float4。但这是 GPUScene 的实际情况，不是这个 shader 的普遍性质。

08InstanceCulling 深度剖析

8.1 它解决的问题

InitViews 阶段 CPU 已经做过一次剔除（视锥 / 距离 / 遮挡），但那只针对「整个 Primitive」。一旦一个 Primitive 带几千个实例（HISM 植被），Primitive 级剔除的粒度就不够了——框住整片森林的包围盒一定与视锥相交，全部实例都会被提交，白白绘制。

// InstanceCullingContext.cpp:316-346（逐字符照录）
void FInstanceCullingContext::AddInstancesToDrawCommand(uint32 IndirectArgsOffset, int32 InstanceDataOffset, uint32 RunOffset, uint32 NumInstances, EInstanceFlags InstanceFlags, uint32 AdditionalCustomCullingFlags)
{
	checkSlow(InstanceDataOffset >= 0);

	const bool bDynamicInstanceDataOffset = EnumHasAnyFlags(InstanceFlags, EInstanceFlags::DynamicInstanceDataOffset);
	const bool bPreserveInstanceOrder = EnumHasAnyFlags(InstanceFlags, EInstanceFlags::PreserveInstanceOrder);
	const bool bForceInstanceCulling = EnumHasAnyFlags(InstanceFlags, EInstanceFlags::ForceInstanceCulling);	

	uint32 Payload = (bDynamicInstanceDataOffset ? INSTANCE_CULLING_DYNAMIC_INSTANCE_DATA_OFFSET_BIT_MASK : 0U);
	if (bPreserveInstanceOrder)
	{
		checkSlow(!EnumHasAnyFlags(Flags, EInstanceCullingFlags::NoInstanceOrderPreservation)); // this should have already been handled

		// We need to provide full payload data for these instances
		// NOTE: The extended payload data flag is in the lowest bit instead of the highest because the payload is not a full dword, see FInstanceCullingLoadBalancerBase::PackItem
		Payload |= (INSTANCE_CULLING_PRESERVE_INSTANCE_ORDER_BIT_MASK | (uint32(PayloadData.Num()) << INSTANCE_CULLING_PAYLOAD_NUM_COMMON_BITS));
		PayloadData.Emplace(bDynamicInstanceDataOffset, IndirectArgsOffset, InstanceDataOffset, RunOffset, DrawCommandCompactionData.Num());
	}
	else
	{
		// Conserve space by packing the relevant payload information into the dword
		Payload |= (IndirectArgsOffset << INSTANCE_CULLING_PAYLOAD_NUM_COMMON_BITS);
	}

	// We special-case the single-instance (i.e., regular primitives) as they don't need culling (again), except where explicitly specified.
	// In actual fact this is not 100% true because dynamic path primitives may not have been culled.
	EBatchProcessingMode Mode = (NumInstances == 1 && !bForceInstanceCulling) ? SingleInstanceProcessingMode : EBatchProcessingMode::Generic;
	// ImposterProxy System:[yinnhaowang]:[MODIFY]
	LoadBalancers[uint32(Mode)]->Add(uint32(InstanceDataOffset), NumInstances, Payload, AdditionalCustomCullingFlags);
	TotalInstances += NumInstances;
}
环节说明

管线选择(NumInstances == 1 && !bForceInstanceCulling) ? SingleInstanceProcessingMode : Generic —— 单实例默认走 UnCulled（CPU 已剔过）
入队LoadBalancers[Mode]->Add(InstanceDataOffset, NumInstances, Payload, AdditionalCustomCullingFlags)，同时 TotalInstances += NumInstances

void FInstanceCullingContext::AddInstancesToDrawCommand(uint32 IndirectArgsOffset, int32 InstanceDataOffset, uint32 RunOffset, uint32 NumInstances, EInstanceFlags InstanceFlags, uint32 MaxBatchSize, uint32 AdditionalCustomCullingFlags)
{
	// Batching is disabled or first run of instances fit into batch size
	if (MaxBatchSize == MAX_uint32 || (NumInstances <= MaxBatchSize && RunOffset == 0))
	{
		// ImposterProxy System:[yinnhaowang]:[MODIFY]
		AddInstancesToDrawCommand(IndirectArgsOffset, InstanceDataOffset, RunOffset, NumInstances, InstanceFlags, AdditionalCustomCullingFlags);
		return;
	}
			
	// In case we are adding more than one instance run 
	// we will need to append instances to a last batch until its full
	if (RunOffset > 0 && NumInstances > 0)
	{
		uint32 NumInstancesInBatch = RunOffset % MaxBatchSize;
		if (NumInstancesInBatch > 0)
		{
			NumInstancesInBatch = FMath::Min(MaxBatchSize - NumInstancesInBatch, NumInstances);
			// appending to a last batch
			IndirectArgsOffset = (IndirectArgs.Num() - 1);
			// ImposterProxy System:[yinnhaowang]:[MODIFY]
			AddInstancesToDrawCommand(IndirectArgsOffset, InstanceDataOffset, RunOffset, NumInstancesInBatch, InstanceFlags, AdditionalCustomCullingFlags);
			InstanceDataOffset += NumInstancesInBatch;
			NumInstances -= NumInstancesInBatch;
		}
	}

	// Split rest of the instances into batches
	if (NumInstances > 0)
	{
		uint32 NumBatches = FMath::DivideAndRoundUp(NumInstances, MaxBatchSize);
		FMeshDrawCommandInfo& RESTRICT DrawCmd = MeshDrawCommandInfos.Last();
		FRHIDrawIndexedIndirectParameters LastIndirectArgs = IndirectArgs.Last();
		uint32 LastCommandDesc = DrawCommandDescs.Last();
		uint32 NumViews = ViewIds.Num();

		for (uint32 BatchIdx = 0; BatchIdx < NumBatches; BatchIdx++)
		{
			uint32 NumInstancesInBatch = FMath::Min(MaxBatchSize, NumInstances);

			if (RunOffset > 0 || BatchIdx != 0)
			{
				DrawCommandDescs.Add(LastCommandDesc);
				IndirectArgsOffset = IndirectArgs.Add(LastIndirectArgs);
				InstanceIdOffsets.Add(GetInstanceIdNumElements());
				DrawCmd.NumBatches++;
			}
			// ImposterProxy System:[yinnhaowang]:[MODIFY]
			AddInstancesToDrawCommand(IndirectArgsOffset, InstanceDataOffset, RunOffset, NumInstancesInBatch, InstanceFlags, AdditionalCustomCullingFlags);

		}

  1. 快路径（:352）：MaxBatchSize == MAX_uint32 || (NumInstances <= MaxBatchSize && RunOffset == 0) → 直接透传。PC 永远走这条。
  2. 填满上一批（:361-374）：NumInstancesInBatch = RunOffset % MaxBatchSize，若 > 0 则 IndirectArgsOffset = (IndirectArgs.Num() - 1) —— 追加到最后一条计划，把上一条的残余空间填满。
  3. 切分（:377-401）：NumBatches = DivideAndRoundUp(NumInstances, MaxBatchSize)；每个额外批复制上一条的 DrawCommandDescs / IndirectArgs，追加 InstanceIdOffsets，并 DrawCmd.NumBatches++。
为什么「填满上一批」这一步是必要的
一个 Primitive 的实例可能被上一次调用拆到一半。若不回填，上一批会留下空洞 —— 而 UBO 窗口是按 stride 连续排布的，空洞会让后续所有实例的偏移算错。所以必须先补满，再从整批边界开始切。

8.8 Shader：LoadBalancer 如何把变长工作装进 64 线程组

要解决的问题：一条 draw 可能 1 个实例，另一条 10000 个。若「一条 draw 一个 group」，前者浪费 63 个线程、后者装不下。

解法：把一个 group 切成若干「item」，每个 item 是一段实例区间，所有 item 的实例数之和恰好填满 64。

CPU 侧的切分（InstanceCullingLoadBalancer.h:130-171）

// InstanceCullingLoadBalancer.h:138-171（逐字符照录）
	void Add(uint32 InstanceDataOffset, uint32 NumInstanceDataEntries, uint32 Payload, uint32 AdditionalCustomCullingFlags = 0)
	{
		uint32 InstancesAdded = 0;
		while (InstancesAdded < NumInstanceDataEntries)
		{
			uint32 MaxInstancesThisBatch = ThreadGroupSize - CurrentBatchPrefixSum;

			if (MaxInstancesThisBatch > 0)
			{
				const uint32 NumInstancesThisItem = FMath::Min(MaxInstancesThisBatch, NumInstanceDataEntries - InstancesAdded);

				Items.Add(PackItem(InstanceDataOffset + InstancesAdded, NumInstancesThisItem, Payload, CurrentBatchPrefixSum, AdditionalCustomCullingFlags));
				if (CurrentBatchNumItems * PrefixBits < sizeof(CurrentBatchPackedPrefixSum) * 8U)
				{
					CurrentBatchPackedPrefixSum |= CurrentBatchPackedPrefixSum << (PrefixBits * CurrentBatchNumItems);
				}
				CurrentBatchNumItems += 1U;
				InstancesAdded += NumInstancesThisItem;
				CurrentBatchPrefixSum += NumInstancesThisItem;

			}

			// Flush batch if it is not possible to add any more items (for one of the reasons)
			if (MaxInstancesThisBatch <= 0U || CurrentBatchPrefixSum >= ThreadGroupSize)
			{
				Batches.Add(PackBatch(CurrentBatchFirstItem, CurrentBatchNumItems));
				CurrentBatchFirstItem = uint32(Items.Num());
				CurrentBatchPrefixSum = 0u;
				CurrentBatchNumItems = 0U;
				CurrentBatchPackedPrefixSum = 0U;
			}
		}
		TotalInstances += InstancesAdded;
	}

8.12 Shader：紧凑化两阶段（Compaction）

为什么需要：§8.10 的原子加让可见实例在输出缓冲里乱序。对半透明叠加等需要保持绘制顺序的材质不行，所以要在实例 ID 层面「挤出空洞、压缩成连续」。

为什么分两阶段：要先知道「每个 block 有多少可见实例」才能算目标偏移（Phase 1），然后才能搬（Phase 2）。

 * CalculateCompactBlockInstanceOffsets
 *
 * Compaction phase 1 - Generate output offsets of "blocks" of source instance IDs such that all valid IDs will be compacted for
 * the draw comand. Each thread group in this dispatch aligns with a single draw command. It uses a hybrid of parallelization and
 * serialization to calculate the compact output offsets in the instance ID buffer in a way that doesn't require multiple dispatches.
 */
// CompactVisibleInstances.usf:34-81（逐字符照录）
[numthreads(NUM_THREADS_PER_GROUP, 1, 1)]
void CalculateCompactBlockInstanceOffsetsCS(uint3 GroupId : SV_GroupID, uint GroupThreadIndex : SV_GroupIndex)
{
	const uint DrawCommandIndex = GetUnWrappedDispatchGroupId(GroupId);
	const FDrawCommandCompactionData DrawCommandData = UnpackDrawCommandCompactionData(DrawCommandCompactionData[DrawCommandIndex]);
	const uint BlockOffset = DrawCommandData.BlockOffset;
	const uint NumBlocksInDrawCommand = GetCompactionBlockCount(DrawCommandData.NumInstances);
	const uint NumWorkIterations = ((NumBlocksInDrawCommand - 1U) / NUM_THREADS_PER_GROUP) + 1U;

	uint CurInstanceOffset = 0;
	uint CurDrawCommandBlockIndex = 0;
	for (uint IterIndex = 0; IterIndex < NumWorkIterations; ++IterIndex)
	{
		const uint DrawCommandBlockIndex = CurDrawCommandBlockIndex + GroupThreadIndex;
		const uint GlobalBlockIndex = DrawCommandData.BlockOffset + DrawCommandBlockIndex;

		uint BlockInstanceDestCount = 0;
		BRANCH
		if (DrawCommandBlockIndex < NumBlocksInDrawCommand)
		{
			BlockInstanceDestCount = BlockInstanceCounts[GlobalBlockIndex];
		}

		uint PrefixSum, GroupSum;
	#if COMPACTION_USES_WAVE_OPS
		PrefixSum = WavePrefixSum(BlockInstanceDestCount);
		GroupSum = WaveActiveSum(BlockInstanceDestCount);
	#else
		PrefixSum = ThreadGroupPrefixSum(BlockInstanceDestCount, GroupThreadIndex, GroupSum);
	#endif // COMPACTION_USES_WAVE_OPS
		
		// Write out the instance offsets
		BRANCH
		if (DrawCommandBlockIndex < NumBlocksInDrawCommand)
		{
			BlockDestInstanceOffsetsOut[GlobalBlockIndex] = CurInstanceOffset + PrefixSum;
		}

		CurInstanceOffset += GroupSum;
		CurDrawCommandBlockIndex += NUM_THREADS_PER_GROUP;
	}

	if (GroupThreadIndex == 0)
	{
		// Set the final indirect arg instance count
		DrawIndirectArgsBufferOut[DrawCommandData.IndirectArgIndex * INDIRECT_ARGS_NUM_WORDS + 1] = CurInstanceOffset;
	}
}

	const uint DrawCommandBlockIndex = GlobalBlockIndex - DrawCommandData.BlockOffset;

	const uint BlockSrcInstanceCount = min(DrawCommandData.NumInstances * DrawCommandData.NumViews - DrawCommandBlockIndex * MaxInstancesPerBlock, MaxInstancesPerBlock);

8.22 延迟剔除：Manager 与 MergedContext

前面 §8.3–§8.7 讲的是「一个 pass 的一次剔除」。但一帧里有十几个 mesh pass（DepthPass / BasePass / CSM / Translucency / Decal…），如果每个都独立发 dispatch、独立建 buffer，小 dispatch 和 buffer 分配的开销会失控。FInstanceCullingManager + FInstanceCullingMergedContext 就是为解决这件事而存在的。

为什么必须「延迟」

BuildRenderingCommands 在主渲染 setup 阶段被各 mesh pass 逐个调用，但此刻每个 pass 的可见 draw command 还没算完（并行的 MDC setup task 还在跑），indirect args / instance id buffer 的尺寸未知。
延迟的本质：RDG setup 阶段只登记 batch、建「尺寸由回调决定」的 buffer；真正的合并计算推到 RDG Execute/Drain 时刻。

9.8 三问：为什么 AoS？为什么直接是数据？为什么 UBO？

先说清楚哪部分是源码事实、哪部分是推断
引擎对此没有留下任何解释性注释。我找过的位置：RenderUtils.h/.cpp、RHIDefinitions.h、ShaderParameterMetadata.h、InstanceCullingContext.h/.cpp、SceneData.ush、SceneDataMobileLoader/Writer.ush、MeshDrawCommands.cpp、ShaderBaseClasses.cpp。
找到的原文全是「是什么」：RHIDefinitions.h:645 / ShaderParameterMetadata.h:159 都只写 "This struct is a view into uniform buffer object, on platforms that support UBO"；InstanceCullingContext.cpp:1865 写 "UniformBufferView suplies instance data through global UB binding"。下面每一条我都标注了性质。

① 为什么 AoS —— 机制推论

代码事实：移动端寻址 DrawInstanceId × STRIDE + DataIdx（SceneDataMobileLoader.ush:16）；PC 是 slot × SOAStride + InstanceId（SceneData.ush:1211）。

推论：UBO 一次 draw 只能设一个 dynamic offset（MeshPassProcessor.cpp:1777），即只能圈定一个连续的 16 KB 窗口（VulkanPipelineState.h:139）。要让窗口内第 i 个实例可算，数据必须满足 base + i×stride —— 这正是 AoS 的定义。SOA 的 slot×SOAStride + InstanceId 在一段连续窗口里根本表达不出来（同一实例的 3~4 段散在窗口不同位置，不同实例又交错）。

顺带的代价（代码有明文）：批上限 64/32（InstanceCullingContext.cpp:1631-1632）、// UniformBufferView path does not support merging ISM draws atm（InstanceCullingContext.cpp:1649）。

② 为什么直接是数据，不是索引 —— 机制推论

代码事实：剔除 CS 在 UBO 路径写 WriteDataUBO(InstanceIdsBufferOutMobile, ...)（BuildInstanceDrawCommands.usf:114），PC 的 #else 写 InstanceIdsBufferOut[Offset] = PackedId（BuildInstanceDrawCommands.usf:118）。

推论：若 UBO 里放索引，VS 还得再读一次 InstanceIdsBuffer —— 那是一次 SSBO 读，而这条路径存在的意义恰恰是不做 SSBO 随机读（见 ③）。放索引 = 绕一圈回到原点，还多付一次窗口绑定。另一条约束来自 ①：窗口是 AoS 连续的，本来就得装数据。

③ 为什么 UBO 不是 SSBO —— 部分为源码事实

代码事实：

  • 分支显式绑定 ES3.1：PLATFORM_USES_PRIMITIVE_UBO = ... && FEATURE_LEVEL == FEATURE_LEVEL_ES3_1（SceneData.ush:40）
  • 启用条件是平台能力位，iOS 有 SSBO 能力也不用（见 §9.6）
  • VS 在 Android ES3.1 上读不了 SSBO —— 见下面的引擎原注释与兜底分支

9.9 网络检索：关于「为什么移动端用 UBO」的外部资料与勘误

网络给出的三条主要理由

  1. 顶点着色器读不了 SSBO（不是慢，是没有）。ARM 官方论坛确认 GLES 上 Mali 不能含只读 buffer / SSBO，Mali-G78 的 GL_MAX_VERTEX_SHADER_STORAGE_BLOCKS 返回 0；ARM 回复「GLES 做不了 Read-Only buffer，Vulkan 才有 Read-Only SSBO，所以这是 GLES 独有问题」。
  2. UBO 有硬件快路径。Khronos wiki："SSBO access, all things being equal, will likely be slower than UBO access… At the very least, UBOs will be no slower than SSBOs." ARM/Adreno 会把 uniform load 提到标量前导（scalar preamble），在 draw 前跑一次存进专用 constant 寄存器；SSBO 没有这种 uniform 语义。

9.10 移动端 GPUScene 的存储形态：仍然是 SSBO，UBO 只是取数通道

13一页总结

一句话

GPUScene 把「每个物体的着色参数」从「逐 draw 绑定」改造成「全局池化 + ID 索引」，这是合批能成立的前提；而 InstanceCulling 在此基础上把剔除粒度从 Primitive 下沉到 Instance，并让 GPU 直接产出 Indirect Draw 参数。PC 用 SSBO + SOA，移动端用 Uniform Buffer + AOS——后者的批大小被 16 KB UBO 上限锁死在 64/32。

五条必须记住的事实

先有池化，才有合批与剔除（别把三者并列）

合批和 GPU 剔除常被当成 GPUScene 的「功能」，但它们其实是池化的下游。对照 §9.13 的回落路径可以看出因果：

没有 GPUScene有 GPUScene
数据组织每条 draw 一份 Primitive 常量（checkf 强制必须有，ShaderBaseClasses.cpp:622-634）一份全局池 + 一个 ID
实例数据从 Primitive 复制，InstanceId = 0（1 draw = 1 实例）SceneData.ush:1474-1487InstanceId 独立寻址（1 draw = N 实例）
剔除粒度CPU / Primitive 级GPU / 实例级

因果链是单向的：

// 本文归纳，非源码原文
数据池化（一份全局池 + ID 索引）
        ↓ 才可能
把「状态相同但 Primitive 不同」的 draw 合并  ← 否则每条 draw 的常量各不相同，合不了
        ↓ 才可能
在 GPU 上按实例并行剔除并产出 Indirect Args  ← 否则没有可寻址的实例 ID 列表

所以 InstanceCulling 不是 GPUScene 的功能，而是 GPUScene 的消费者；合批同理。这是读这套代码时最容易倒置的一层关系。

  1. 切换点只有一个：PlatformGPUSceneUsesUniformBufferView = IsMobilePlatform && SupportsUniformBufferObjects RenderUtils.cpp:488-491。整条 PC/Mobile 分叉都从这里分出去。
  2. 两种布局的寻址公式互不通用：SOA 是 slot×SOAStride + InstanceId，AOS 是 DrawInstanceId×stride + idx。混用必错。
  3. SOAStride 是「实例容量」不是「每实例 float4 数」，且是 2 的幂 GPUScene.cpp:1047-1054。
  4. 批上限 64/32 全部来自 16 KB：16384/256 与 16384/512。PC 不拆分正说明它是 UBO 约束而非算法约束。
  5. InstanceIdOffsetBuffer 有三重身份：CPU 上传的数据、剔除 CS 的读源、VS 的 PrimitiveId 顶点流。判据是「Buffer 还是 RWBuffer」+「绑到哪个槽」。

三个易踩的坑

  • 宏名近似但语义无关：USE_INSTANCE_CULLING（VF 能力）≠ USE_INSTANCE_CULLING_DATA（编译目标）≠ SHADER_USES_PRIMITIVE_UBO（移动端 UBO 路径）。
  • 「3 还是 4 个 float4」取决于是否含头 slot：含头是 3/4 InstanceUniformShaderParameters.h:74-75，不含头是 2/3 SceneData.ush:115-119。
  • 本仓库是分叉：多处 #if 1 硬开了官方 #else 分支；FCompressedTransform2、GR_USE_INSTANCE、FPackedItem 第三字段都是自研，官方资料里没有。

还有两处「源码现状」值得单独记住

  • InstanceCullingContext.cpp:1659 的 bCanCompactCurrentCommand 判据行被注释掉 → r.InstancedStaticMeshes.DynamicInstancing 当前是 dead code。
  • SceneDefinitions.h:87 的 NOTE: Out of flags → Primitive 数据 flag 已用满 31 位，再加标志位必须另起炉灶（这正是 GR 自研 visibility flag 单独占 16 位的原因）。
