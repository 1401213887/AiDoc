UE5 Android UI 纹理内存优化：非 4 对齐导致的压缩失效

Unreal Engine 5.5（S1Game / Android Vulkan）大厅运行时内存从 2698.55 MB 收敛到约 1.6～1.8 GB 的完整排查与实施记录。核心结论：纹理 1955.6 MB 里有 1122.7 MB 不是"贴图太多"，而是贴图尺寸不是 4 的倍数，导致引擎强制关闭块压缩、以未压缩 32bpp 驻留。 处理 516 个资产（三个 P4 CL），预估节省 约 1340 MB。

第 8 章补充了 LLM 实测归因：稳态三项（纹理、UObject、代码段）占 65%； 峰值高出稳态的 1602 MB 与常驻资源无关，来自纹理解码、GPU 上传、文件读取与 GPU 后备内存四个加载期临时缓冲。

工具链：memreport -full · DumpLLM -CSV · stat LLMFULL · rhi.DumpResourceMemory CSV · Unreal MCP（execute_python）· P4 1239353 / 1239799 / 1239904

1结论与关键数据

大厅纹理 1955.6 MB 里有 1122.7 MB 不是"贴图太多"，而是"贴图没被压缩"——因为尺寸不是 4 的倍数。LLM 实测已确认：纹理、UObject、代码段三项占稳态内存 65%，峰值缺口则来自加载期临时缓冲。

三批资产处理后，纹理口径从约 1955.6 MB 降到约 663 MB；大厅稳态内存理论上限从 2698.55 MB 降到 1358 MB，考虑口径重叠后实际预期落在 1.6～1.75 GB。

2运行时内存怎么量：三层口径

进程 RSS 判预算，LLM 判类别，memreport 与资源 CSV 判具体资产。三者口径互相重叠，不能相加。

口径提示：本章示例数字取自未开 LLM 的原始报告（15:33 那次）；第 8 章是开 -LLM 后的实测（RSS 2828.07 MB，含 LLM 自身开销 288.7 MB）。两批数字不可直接比较。

2.1 进程口径（判断预算）

Windows 上 FPlatformMemory::GetStats() 的 UsedPhysical 取的是 WorkingSetSize，UsedVirtual 取的是 PagefileUsage（即 commit charge， 不是虚拟地址空间大小），见 WindowsPlatformMemory.cpp:466。

Android 上 UsedPhysical 来自 /proc/self/status 的 VmRSS， PeakUsedPhysical 来自 VmHWM，见 AndroidPlatformMemory.cpp:266。 UsedVirtual 对应 VmSize，不要当实际占用看。

Platform Memory Stats for Android

Physical Memory: 8640.35 MB used,  2535.75 MB free, 11176.10 MB total

2.2 分配器口径（判断碎片与缓存）

FMallocBinned2 的报告给出向 OS 的真实申请量：Small Pool 897.9 MB + Large Pool 590.5 MB， 总计 1560.5 MB，其中 342.9 MB 是空闲缓存页——释放的内存在这里挂着，RSS 不会立刻下降。

2.3 资源口径（定位到资产）

rhi.DumpResourceMemory all -csvfile 输出逐资源 CSV（本次 34941 条，合计 2233.2 MB）， 是唯一能按名字、尺寸、格式、流送标记筛选的清单。

口径陷阱：1560.5 MB（分配器）+ 1955.6 MB（纹理）= 3516 MB，超过 RSS 2698.55 MB。 说明纹理与堆统计存在重叠（部分 RHI 分配经过 UE 分配器）。所以"贴图少 1 GB"不等于"RSS 少 1 GB"。

3memreport -full 到底列了什么

它不是"一个内存数字"，而是按 ini 脚本执行的一次取证快照：先 GC，再逐条 dump 到文本文件。

3.1 执行方式

命令会先转成延迟命令 MemReportDeferred，在帧末执行，顺序是 FlushAsyncLoading() → CollectGarbage() → FlushRenderingCommands() （UnrealEngine.cpp:8033），因此结果是GC 之后的存活对象，不是峰值。

输出落在 FPaths::ProfilingDir() + "MemReports/"（UnrealEngine.cpp:8043）， 子目录名由 MapName-Platform-MM.DD-HH.MM.SS 组成（ProfilingHelpers.cpp:166）， 每次执行一个新目录，便于跨场景对比。

3.2 内容由 ini 决定

-full 会把 profile 名置为 FULL，读取 [MemReportFullCommands] （UnrealEngine.cpp:8016-8024）；不带参数读 [MemReportCommands]。 两段的定义分别在 BaseEngine.ini:2264 与 BaseEngine.ini:2301。

本次执行了 45 条命令、报告 14896 行、2.67 MB，实测耗时约 6 秒：

分组命令产出
进程与底层Mem FromReport平台内存、Binned2 分配器、FMemStack、FPageAllocator、NameTable、AssetRegistry、全部 memory 类 stat
RHI 资源rhi.DumpMemory、rhi.DumpResourceMemory + 19 条 summary按类型汇总 + Lumen/Nanite/Shadow/GPUScene/各类 VB·IB 分项
资产清单listTextures、listStaticMeshes、obj list逐资产：尺寸、格式、LODGroup、流送、mips

注意：本次 LLMSnapshot 段落为空。该命令只调 PublishDataSingleFrame()，且帮助文本明确要求 -llmdisableautopublish （LowLevelMemTracker.cpp:974-980）；LLM 未开启时自然没有输出。

4LLM 是什么、能看什么、Android 上为什么默认没开

LLM = Low-Level Memory Tracker，按"分配来源 + 标签"给内存分类；它不告诉你调用栈，也不等于进程占用。

``` LLM 的两级 tracker： Default ← FMemory::Malloc 的分配（纹理 / UObject / 渲染目标…），子集 Platform ← 更底层的 OS 分配（含 Binned2 内部池） ，超集 两者有包含关系，不能相加。 ```

4.1 控制台命令

stat LLM          分类摘要
stat LLMFULL      完整标签
stat LLMPlatform  平台层分配
stat LLMOverhead  LLM 自身开销

-LLMCSV           逐行写 CSV 到 Saved/Profiling/LLM/（LowLevelMemTracker.cpp:6578）

本分支的写盘间隔默认是 1 秒（LowLevelMemTracker.cpp:956）， 比 Epic 文档写的 5 秒更密，短促峰值更容易被采到。

4.2 为什么 Android 真机上没开

引擎有两处会让 LLM 默认开启的定制，但都带条件：

#if UE_BUILD_DEVELOPMENT && UE_GAME && PLATFORM_DESKTOP   // LowLevelMemTracker.cpp:2426
    bShouldDisable = false;   // Windows / Mac 的 Development 游戏包默认开
#endif

PLATFORM_DESKTOP 在 Android 上为假，所以真机 Development 包仍然需要显式加 -LLM。 本次包的启动命令行里没有该参数，这就是 LLMSnapshot 为空、stat LLMFULL 无法分类的直接原因。

4.3 逐资产标签在本分支不可用

LLM_ALLOW_ASSETS_TAGS 被固定为 0（LowLevelMemTracker.h:37）， 此时传 -llmtagsets=Assets 只会得到一条警告 （LowLevelMemTracker.cpp:2526），不会有逐资产统计。要开启必须改这个宏并重新编译引擎。

不要手动定义 ENABLE_LOW_LEVEL_MEM_TRACKER：它现在是派生宏 （LowLevelMemTracker.h:21），直接定义会触发 #error。

5根因：尺寸非 4 倍数导致块压缩被引擎跳过

块压缩按 4×4 宏块工作，引擎对"任一维不是 4 的倍数"的纹理直接关闭压缩，与纹理组、压缩设置都无关。

// Engine/Source/Runtime/Engine/Private/Texture.cpp:4124-4133
// Also force uncompressed if size of top mip is not a multiple of 4
if ( (SizeX < 4) || (SizeY < 4) || (SizeX % 4 != 0) || (SizeY % 4 != 0) )
{
    bNoCompression = true;
}

注意 Texture.cpp:4121 调的是 Texture->GetBuiltTextureSize(...)， 即判断用的是构建后的尺寸（已叠加 MaxTextureSize、LODBias、PowerOfTwoMode），不是源图尺寸。

5.1 对照实验

同一批头像框、压缩设置完全相同（都是 TC_BC7），唯一变量是尺寸能否被 4 整除：

分类张数合计真机格式
尺寸非 4 倍数2451117.8 MBPF_B8G8R8A8（未压缩）
尺寸 4 对齐347.5 MBPF_ASTC_6x6（已压缩）

对照组里包含 2016×1676、1428×1032、1024×968 共 17 张 不是 2 的幂但 4 对齐的纹理，全部压缩成功——这直接排除了"必须是 2 的幂"这个常见误解。

门槛是 4 的倍数，不是 2 的幂。 实战中把目标尺寸定成 1024/512 更省事， 是因为它同时满足两个条件，而不是因为 2 的幂本身有硬性要求。

6改尺寸的两种机制：为什么 MaxTextureSize 不可用

MaxTextureSize 的实现是"逐次减半"，会把 2047 变成 1023（仍不是 4 的倍数）；要精确控制必须走 ResizeToSpecificResolution。

// Texture.cpp:4010-4021  —— MaxTextureSize 的实现
if ( MaxTextureSize != 0 )
{
    while( SizeX > MaxTextureSize || SizeY > MaxTextureSize )
    {
        SizeX = FMath::Max(SizeX>>1,1);
        SizeY = FMath::Max(SizeY>>1,1);
    }
}

代入实测值：2047×2040 设 MaxTextureSize=1024 后得到 1023×1020， 1023 % 4 = 3，压缩依旧不会生效。这条路只适合本来就是 2 的幂的纹理（512→256 恰好整除）。

6.1 精确指定尺寸

// Developer/TextureBuildUtilities/Private/TextureBuildUtilities.cpp:335-344
case ETexturePowerOfTwoSetting::ResizeToSpecificResolution:
    if (InResizeDuringBuildX) { TargetTextureSizeX = InResizeDuringBuildX; }
    if (InResizeDuringBuildY) { TargetTextureSizeY = InResizeDuringBuildY; }
    break;

要生效必须同时设三个属性：power_of_two_mode = RESIZE_TO_SPECIFIC_RESOLUTION、 resize_during_build_x、resize_during_build_y。只设后两个不会生效。

6.2 移动端专用旋钮存在但被关闭

本分支在 UTexture 上加了资产级 MoblieMaxTextureSize （Texture.h:1347，拼写如此），用于"只影响移动端"的尺寸上限， 消费点在 TextureLODSettings.cpp:152 与 Texture2D.cpp:1589。

但它受 UsesMobileMaxTextureSize 门控，而项目所有 device profile 都把它设为 False（DefaultDeviceProfiles.ini:1775），所以现在给资产填该值不生效。 开启开关本身是安全的（全项目该值当前均为 0），随后逐资产填值即可只压移动端。

代价提示：MaxTextureSize 与 ResizeToSpecificResolution 都是全平台构建设置，桌面端会一起缩小。

T_BossSKY_Cube_023BP_Rush02_ParentEnvLight_Boss_02_New 等环境光蓝图

前三个合计被 38 个 *_UI 材质引用——它们做的是角色/载具展示界面的环境反射。 大厅只要有 UI 预览，材质一加载，cube 就跟着进来。

9.1 进包为什么和"用不用"无关

/Game/AssetDatas/GeneratePatch/Chunk1_Content 的类名是 PrimaryAssetLabel： 它把资产标签化并框进指定 chunk，cook 阶段按规则强制包含，不看运行时是否需要。 T_BossSKY_Cube_02 只被 2 个环境光蓝图引用却也在包里，原因就在这里。

9.2 为什么一进来就不释放

这 4 张在 TEXTUREGROUP_Skybox 下 Streaming=NO，整张 mip 链常驻，流送系统不会回收。 所以"引用链一旦被拉起"就等于 16 MB/张的固定占用。

9.3 可做的三件事

  1. UI 材质改用共享低精度 cube：38 个材质不需要 512² 的 HDR 环境精度，128² 足够。
  2. 检查 Chunk1_Content 是否必须包含这些资产，能移出则同时减包体与无谓 cook。
  3. T_BossSKY_Cube_02 的蓝图默认值改 soft reference，运行时按需加载。

边界：以上是静态引用图，只能证明"可能被加载"。要确定大厅里具体是哪条链拉起， 需要 LLM 的加载记录或 Memory Insights 的加载栈。

10已验证、未验证与已知坑

资产侧改动已验证到属性与文件层；cooked 结果与真实内存收益尚未验证。

10.1 已验证

  • 516 个资产全部写入成功，0 失败、0 跳过；每个资产在保存前读回 resize_during_build_x/y 与 power_of_two_mode 校验。
  • 文件级：全部 .uasset 的 mtime 落在对应批次窗口内，0 缺失；豁免资产未被触碰。
  • 属性抽查（MCP 实读）：shengdanjie → 1024×1020、T_Sleepcoat_Frame1 → 1024×1024、 LKLS/Blue/kuang → 1024×1024、kuang_2 → 1024×852、11×11 豁免项仍为 mode=NONE。
  • 全部目标尺寸 %4==0 且 ≤1024（Skybox 为 256）。

10.2 未验证

  • cooked 后的真实格式与尺寸：所有"改后 MB"都是按 ASTC 6×6 的 bpp 推算，未经 cook。
  • RSS 的真实下降幅度：受口径重叠、分配器缓存、LODBias 共同影响，预期 1.6～1.8 GB 而非理论 1358 MB。
  • 第 8 章的 LLM 数据是"优化前"状态：那三批资产尚未 cook，所以 1125.1 MB 的 HeadFrame 仍原样在报告里。 LLM 数据验证的是"结构"，不是"收益"。

10.3 已知坑（已写进脚本）

  1. blueprint_get_texture_source_disk_and_memory_size() 返回 (disk, mem)： 源是压缩格式时 disk ≠ mem，反推尺寸必须用 mem（= W×H×4）。
  2. 尺寸反推的搜索中心不能取 isqrt(px)（只适用近方形），要取 sqrt(px × aspect)； 1:2.85 的窄条纹理，真实边长离 sqrt(px) 很远。
  3. execute_python 单批 30 个资产会响应超时（活干完了但拿不到回执），20 个/批稳定。
  4. rhi.DumpMemory 的 stat 行在本包不可信：报 Vertex Buffer 26853 MB（26 GB）， 远超设备 11 GB 总量；同次逐资源 CSV 合计仅 2233.2 MB。以 CSV 为准。
  5. 部分资产的运行尺寸被 LODBias 减半（源 1143×3260、运行时 571×1630）。这类按真实源尺寸对齐， 保持运行时分辨率不变，避免误降画质。
  6. DumpLLM 必须写 -CSV（带横杠）：引擎用 FParse::Param 解析， 写 DumpLLM CSV 只输出 PlainText，没有逗号分隔，脚本无法解析。
  7. Android 上 LLM 不会自动开启：引擎里的"Development 默认开 LLM"定制带 PLATFORM_DESKTOP 条件（LowLevelMemTracker.cpp:2426），Android 不适用。 真机必须在启动命令行加 -LLM。
  8. 加 -LLM 优先用 setprop debug.ue.commandline（追加语义， LaunchAndroid.cpp:520，仅非 Shipping）。不要用 UECommandLine.txt： 它在 LaunchAndroid.cpp:505-508 先 FCommandLine::Set(TEXT("")) 清空原命令行， 文件里没写全 -project / -dpcvars 就会丢掉现场参数。
  9. LLMOverhead 必须扣除：本次实测 288.7 MB。开 LLM 前后的两批数字不可直接比较。
  10. LLM Default Total ≠ RSS：本次 4066.4 vs 2828.07。LLM 也统计 GPU 侧分配， 两者互为补充而非等价。
  11. -llmtagsets=Assets 无效：本分支 LLM_ALLOW_ASSETS_TAGS=0 （LowLevelMemTracker.h:37），加了只有一条警告，看不到逐资产 LLM 排行。

11.2 采集 LLM（分类归因，无需重新出包）

# 1) 追加 -LLM 到已装包的命令行（setprop 是追加语义，仅非 Shipping 生效）
adb shell setprop debug.ue.commandline "-LLM"; adb shell getprop debug.ue.commandline
# 2) 冷启（LLM 只在进程启动时初始化）
adb shell am force-stop com.sarosgame.S1Game
adb shell am start -n com.sarosgame.S1Game/com.epicgames.unreal.SplashActivity
# 3) 验证：日志出现 LLM enabled
adb shell "grep -a 'LLM enabled' .../Saved/Logs/S1Game.log"
# 4) 稳定后按顺序：memreport -full（内部先 GC）→ DumpLLM -CSV（必须带横杠）
python send_cvar.py com.sarosgame.S1Game S1Game -- memreport -full
python send_cvar.py com.sarosgame.S1Game S1Game -- DumpLLM -CSV
# 5) 取数：表头 '[time][frame],TagName,SizeMB,PeakMB,Tracker,PathName'
adb shell "grep -an 'PeakMB,Tracker' .../Saved/Logs/S1Game.log"
# 6) 采完必须清掉，否则后续性能测试一直背着 LLM 开销
adb shell setprop debug.ue.commandline ""
