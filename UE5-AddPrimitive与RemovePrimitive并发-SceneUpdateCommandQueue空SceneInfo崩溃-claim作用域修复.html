UE5 AddPrimitive 与 RemovePrimitive 并发：SceneUpdateCommandQueue 空 SceneInfo 崩溃与 claim 作用域修复

对象：S1Game UE5 fork（release CL 1183280，崩溃版本 build 0.1178669 Development Win64）的 primitive 增删链路。现象：渲染线程在 SceneUpdateCommandQueue.h:531 解引用空 FPrimitiveSceneInfo 崩溃（访问违规，非断言）。根因：异步建代理期间 SceneProxy 先于 SceneInfo 发布，而 RemovePrimitive 只判 proxy 不判 SceneInfo。修复：把 AddPrimitiveClaim 的持有期对齐到 Add 命令入队点，Remove 侧等待其释放。验证：8 小时 43 回合 soak 零异常；故障注入 76,726 次证明前置条件在本负载不成立。

1. 结论：空 SceneInfo 从哪来，怎么修

渲染线程崩在 SceneUpdateCommandQueue.h:531 的 Commands.Emplace(SceneInfo, SceneInfo->GetPersistentIndex())。 这一行是该函数里唯一解引用 SceneInfo 的地方（GetPersistentIndex() 定义见 PrimitiveSceneInfo.h:584，是纯成员读取）。

先定性：是访问违规，不是断言失败。判据是正向的 —— check() 失败必经 AssertionMacros.cpp:372 的 GError->Logf(TEXT("Assertion failed: ..."))，必然写日志；而崩溃日志中 Assertion failed / Critical error / Fatal error / appError / LogOutputDevice: Error / LogWindows: Error 全部 0 次。

注意区分：TAPD 单标题里的 UNREAL_ASSERT_EXCEPTION(0x00004000)，其中 0x4000 是 WindowsPlatformCrashContext.cpp:95 定义的 AssertExceptionCode。 那是另一个断言类崩溃，与本文的访问违规不是同一件事。

空指针来自 BatchAddPrimitivesInternal 内部的发布顺序倒置：

行动作此刻外部可见的状态
RendererScene.cpp:2306CreateSceneProxy()，其内部 PrimitiveComponent.cpp:5788 的 AssignSceneProxy() 已把 proxy 写入 SceneData GetSceneProxy() != nullptr
RendererScene.cpp:2323proxy->PrimitiveSceneInfo = SceneInfo 此前 proxy->GetPrimitiveSceneInfo() == nullptr

FPrimitiveSceneProxy::PrimitiveSceneInfo 的初值是 nullptr（PrimitiveSceneProxy.cpp:747）， 而 BatchRemovePrimitivesInternal 原本只校验 proxy 非空、不校验 SceneInfo，于是把 nullptr 投给渲染线程。

为什么一定是 nullptr 而不是悬垂指针：MallocBinned 的池释放后内存仍映射， 读悬垂指针的 PersistentIndex 不会 fault（只读到垃圾，崩溃会推迟到别处）； 只有 nullptr 偏移后仍落在极小地址，才会在 531 行确定性 fault。

修复方向不是给队列加锁，而是把 claim 的持有期对齐到 Add 命令入队点：渲染命令按入队顺序在 RT 执行， 只要 Add 已入队，后来者的 Delete 必排在它之后，EnqueueAdd 的「Add 必须最先」不变量就自动成立。

2. 两个危险窗口：为什么只堵住一个会换来另一种崩溃

一句话结论：窗口 A 导致空指针崩溃，窗口 B 导致 Add/Delete 入队顺序颠倒； 只处理 A 会把「罕见泄漏」换成「罕见 Dev/Test 断言」。

图 1：修复前 AddPrimitive 的两个危险窗口。窗口 A 导致空指针崩溃，窗口 B 导致 Add/Delete 入队顺序颠倒。

窗口 A：proxy 已发布、SceneInfo 未回填（2306 → 2323）

GT 在此刻 Remove，读到 proxy 非空而 SceneInfo 为空 → 投出 nullptr → 531 行解引用崩溃。 这是线上那次崩溃命中的窗口，跨度亚微秒级。

窗口 B：SceneInfo 已链接、Add 命令未入队（claim 释放 → 2374）

ENQUEUE_RENDER_COMMAND(AddPrimitiveCommand) 在 RendererScene.cpp:2374， 位于整个循环结束之后；而改前 claim 在每次循环迭代末尾就释放。BatchSize=16 下这个窗口是毫秒级， 比窗口 A 大几个数量级。

GT 在此刻 Remove，拿到的是有效 SceneInfo，于是正常入队 Delete —— 但它可能排在 worker 的 Add 之前。 RT 执行到 EnqueueAdd 时会撞上两道断言：

断言位置
check(CommandSlots.Find(SceneInfo) == nullptr)（注释原文：Add should always be the first command）SceneUpdateCommandQueue.h:170
check(!Command.bDeleted)SceneUpdateCommandQueue.h:176
这意味着：如果只在 Remove 侧做判空，窗口 A 的结果从「崩溃」变成「代理泄漏 + 场景残留 primitive」； 而等待若只等到 claim 释放（未覆盖入队），就会必然落进窗口 B，把崩溃从 531 行搬到 EnqueueAdd。 Shipping 下 check 被编掉，同帧 Add+Delete 由引擎既有的同帧增删逻辑正确处理成「删除」，所以该断言只在 Dev/Test 触发。

3. 修复：claim 作用域对齐入队点

一句话结论：把逐 primitive 的 RAII claim 换成批量持有，析构点落在 ENQUEUE_RENDER_COMMAND 之后， Add-before-Delete 不变量由构造保证，不依赖时序运气。

图 2：修复后 claim 作用域覆盖到 ENQUEUE_RENDER_COMMAND，Add-before-Delete 不变量由构造保证。

3.1 Add 侧：FAddPrimitiveClaimScope

// RendererScene.cpp:2250  声明于循环之前，析构于函数退出（入队之后）
struct FAddPrimitiveClaimScope
{
    ~FAddPrimitiveClaimScope()
    {
        for (FThreadSafeCounter* Counter : Claimed)
        {
            Counter->Decrement();
        }
    }

    // 抢到则登记、持有到本作用域结束；没抢到立即归还
    bool TryClaim(FThreadSafeCounter& Counter)
    {
        if (Counter.Increment() == 1)
        {
            Claimed.Add(&Counter);
            return true;
        }
        Counter.Decrement();
        return false;
    }

    TArray<FThreadSafeCounter*, SceneRenderingAllocator> Claimed;
};
顺带修掉的一个真 bug：原版 RAII 构造时无条件 Increment()， 析构却只在 bAcquired 时 Decrement() —— 每次抢占失败都会永久抬高计数， 该 primitive 此后所有 AddPrimitive 都抢不到 claim 并 continue，永久不可见。 新版在 TryClaim 内「抢不到立即归还」，彻底消除。

3.2 Remove 侧：WaitForInFlightAddPrimitive

定义于 RendererScene.cpp:2880，调用点 RendererScene.cpp:2960，在读 proxy 之前：

阶段做法依据
短自旋256 次 FPlatformProcess::Yield()正常窗口（new + 指针回填）亚微秒级
让出时间片转 FPlatformProcess::YieldThread()Yield() 实为 _mm_pause()（GenericPlatformProcess.h:819），不让时间片；持有者被调度走时纯自旋等不到

踩过的坑：首版用 Yield() 做全部等待。它是 CPU 暂停指令，不释放 CPU —— 这是个 「看着对、跑起来也不报错」的写法，日志和跑测都不会暴露，只能靠读 GenericPlatformProcess.h:819 的实现发现。

3.3 判空兜底与现场记录

  • RemovePrimitiveSceneInfo_RenderThread（RendererScene.cpp:2842）入口判空：为空则跳过 EnqueueDelete，止崩。
  • LogMissingSceneInfoOnRemove（RendererScene.cpp:2915）打印 Component / Owner / Proxy / bRegistered / bRenderStateCreated / bRenderStateDirty / AsyncAddInFlight / World。 其中 AsyncAddInFlight 可直接区分「在途」与其它来源。

  • 全部日志为 Warning 级，与 CL 1201185 既有的 [SceneProxy] Concurrent AddPrimitive skipped 一致。

4. FPrimitiveSceneDesc 路径：一个默认关闭的定时炸弹

一句话结论：CL 1201185 新增的二次确认 if (Primitive->GetSceneProxy()) continue; 对 FPrimitiveSceneDesc 路径是误判，会让首次合法 Add 被整个跳过。

FPrimitiveSceneDesc 的 PrimitiveComponentInterface 默认为 nullptr （PrimitiveSceneDesc.h:28），头文件注释明确写着：不提供 ComponentInterface 时， ProxyDesc 必须已由调用方创建并传入。项目侧 S1WeaponAvatarComponent.cpp:1507 正是这种用法 —— 在调用 AddPrimitive 之前就 PrimitiveSceneData->SceneProxy = new FStaticMeshSceneProxy(...)。

于是「proxy 非空」在这条路径上恒成立，二次确认必然命中 → Add 被跳过 → RendererScene.cpp:2323 的回填永不执行 → 卸载时投出空 SceneInfo。

修正方式是按路径区分判据（RendererScene.cpp:2298）：

FPrimitiveSceneProxy* ExistingSceneProxy = Primitive->GetSceneProxy();
const bool bAlreadyAdded = ExistingSceneProxy &&
    (Primitive->GetPrimitiveComponentInterface() != nullptr || ExistingSceneProxy->GetPrimitiveSceneInfo() != nullptr);
路径判据行为
组件首次proxy == null继续（不变）
组件并发 / 已完成proxy != null跳过（不变）
desc 首次proxy 非空但 SceneInfo 为空继续 → 回填 SceneInfo（修复）
desc 重复 Addproxy 与 SceneInfo 都非空跳过（保留原防重复语义）
当前未触发：avatar.weapon.EnableApproxWeaponMesh 默认值为 2 （S1WeaponAvatarComponent.cpp:54），走 StaticMeshComponent 分支；改成 1 才走 desc 路径。 属于「改个 CVar 就必崩」的定时炸弹，无法通过跑测发现，只能靠代码推演。

5. 验证：故障注入与 soak，以及证据的边界

一句话结论：修复的正确性由构造保证且零成本；但「修复前崩 / 修复后不崩」的对照实验给不出来 —— 前置条件在本测试负载下不成立，且这一点已被 76,726 次留痕证明不是仪表故障。

5.1 故障注入：把微秒级巧合变成可复现

新增 r.ZXB.AddPrimitive.InjectDelayMs（默认 0），注入点在 claim 持有期内、Add 入队之前 —— 正是窗口 B 的位置。关键设计：注入点自身必须打日志留痕，否则「等待 0 命中」分不清是仪表坏还是真没发生。

观测项结果

崩溃 / 空 SceneInfo / 原断言0

结论：GT-直接 UnregisterComponent() 去移除一个正在异步添加中的 primitive，在本负载下不发生。 合理解释是 CL 1201185 的 AsyncAddInFlight 已挡住帧末并行（ActorComponent.cpp:2565） 与批量重注册（StaticMeshResources.cpp:152）两条路；而 GT-直接卸载需要「关卡边加载边卸载」， 被 World.cpp:4833 的 FinishAsyncSendAllEndOfFrameUpdates() 与 AddToWorld/RemoveFromWorld 的串行化排除。

7. 排查 Checklist：再遇同类崩溃怎么定位

  1. 先定性：断言还是访问违规。不要靠「栈里有没有 FDebug::AssertFailed」—— 栈可能被截断。 正向判据是 AssertionMacros.cpp:372 保证 check() 必写日志，所以日志里 Assertion failed 为 0 即可排除断言。
  2. PC 落在哪一行要精确到行。本例 PC 在 531（解引用）而非 530（check），这是区分两类故障的唯一线索。
  3. 排除「队列自身不同步」。TRobinHoodHashTable 扩容只重建桶数组，KeyValueData 索引稳定追加； 队列从不 Remove，故 check(CommandSlot == Commands.Num()) 在单线程路径恒成立。
  4. 查发布顺序，而不是只查空指针。双向指针（component→proxy→SceneInfo）中任一侧先发布， 都会制造一个外部可见的不一致窗口。
  5. 加仪表时，仪表自己必须留痕。「0 命中」在仪表未留痕时毫无意义 —— 分不清是坏仪表还是真没发生。
  6. 线程判定不要用 IsInGameThread()。本 fork 中它在 Development 走线程 ID 比较 （ThreadingBase.cpp:257 的 newValue = oldValue）、在 Test 走 IsCurrentTag（ThreadingBase.cpp:227，精确相等而非位测试）。 而 CoreGlobals.h:762 定义 EParallelGameThread = EGameThread | EParallelThread —— 两种配置语义不同。要判「是否真的在 GT」请用 FPlatformTLS::GetCurrentThreadId() != GGameThreadId。
  7. 确认 trace 仪表确实会被记录。SCOPED_NAMED_EVENT 展开含 TRACE_CPUPROFILER_EVENT_SCOPE（PlatformMisc.h:181）， 且 ENABLE_NAMED_EVENTS 定义为 (!UE_BUILD_SHIPPING && 1)（PlatformMisc.h:33）， Test 下启用 —— 但 rush01 这类脚本不含 Trace.Start，trace 不落盘，查不到不等于没发生。

8. 已知问题与技术债

  • 口子 2（desc 路径）只在代码层面修正，无法跑测验证 —— avatar.weapon.EnableApproxWeaponMesh 默认 2 走不到该分支。真正的验收时刻是有人把它改成 1。
  • GT-直接卸载在途组件这条路，AsyncAddInFlight 仍无检查点。 全仓仅两处检查（ActorComponent.cpp:2565、StaticMeshResources.cpp:152）。 本文的 claim 等待是在 Remove 侧兜住它，而非在源头阻止。
  • 50 ms 超时是权衡产物：超时后进入判空分支，意味着放弃等待并接受「代理泄漏 + 场景残留」。 等待更久会拉长 GT 卡顿，等待更短会更早退化。该阈值未经真实命中验证（命中率为 0）。
  • SceneUpdateCommandQueue 的移动构造存在潜伏不一致： SceneUpdateCommandQueue.h:115-121 只搬运 Commands，目标对象的 CommandSlots 为默认空。 目标若被 enqueue，check(CommandSlot == Commands.Num()) 必失败（0 == N）。 当前因目标只读而未暴露 —— 这恰好是会打在 530 行的故障，反向印证本次崩的是 531。
