UE5 Mobile 端 GPU Time 统计口径
——stat unit 的 GPU Time 与 stat gpu 的 [TOTAL] 为什么对不上

同一个静止场景里，stat unit 显示 GPU Time ≈ 23.8 ms，stat gpu 的 [TOTAL] 只有 12.7 ms。本文说明这两个数各自量的是什么、差异从哪来、以及移动端特有的精度限制。

0一页结论

这两个数不是同一个量的两种算法，而是两个不同的量。stat unit 报的是 GPU 帧跨度，stat gpu 报的是 被插桩 pass 的净工作量。差值 ≈ GPU 空转时间 + 未被插桩的 GPU 工作。

项目stat unit → GPU Timestat gpu → [TOTAL]
量的口径帧跨度（wall-clock span）插桩 pass 的独占耗时之和
含 GPU 空转含不含
含未插桩的 GPU 工作含不含
时间戳落点整帧两个点（帧首 / 帧末）每个 GPU scope 一对点
平滑0.9×上次 + 0.1×本次（EMA）stat 系统自身窗口平均
典型偏差方向偏大（被空转撑高）偏小（漏掉未插桩工作）
三个必须知道的前提
  1. 这套 fork 编的是旧 profiler（RHI.Build.cs:16 → RHI_NEW_GPU_PROFILER=0）。新版 profiler 里两者同源、本该相等；旧版里走两条独立通路，必然分家。
  2. Android 上这套默认关闭（r.Android.SupportsTimestampQueries 默认 0）；且本项目包体的 DeviceProfile 把名字拼错成 r.Vulkan.，等于从来没生效过。
  3. TB(D)R 让 render pass 内部的 timestamp 不可靠 —— 这是移动端独有的，会让 stat gpu 的 per-pass 数字抖动、甚至出现负值。

1全景：两条独立的数据通路

一句话结论：同一个硬件时间戳来源，在引擎里分成两条互不相干的加工通路，最后变成屏幕上的两个数字。

图 1 · 从同一个硬件时间戳分叉出的两条独立通路

2通路 A：stat unit 的 GPU Time

一句话结论：stat unit 的 GPU Time 是「这一帧 GPU 从开始到结束跨了多久」——一条时间轴上的两个点之差，中间的 GPU 空转照样计入。

2.1 数据链路

// 1) stat unit 取值：读全局量，不做任何 pass 级聚合
const uint32 GPUCycles = RHIGetGPUFrameCycles(GPUIndex);            // UnrealClient.cpp:392
RawGPUFrameTime[GPUIndex] = FPlatformTime::ToMilliseconds(GPUCycles); // UnrealClient.cpp:393
GPUFrameTime[GPUIndex]   = 0.9 * GPUFrameTime[GPUIndex]
                         + 0.1 * RawGPUFrameTime[GPUIndex];           // UnrealClient.cpp:394  EMA 平滑

// 2) RHIGetGPUFrameCycles 就是返回全局量
return GGPUFrameTime;                                               // VulkanCommands.cpp:1369

// 3) 全局量怎么来的：一次「帧首 → 帧末」的时间戳之差
if (GSupportsTimestampRenderQueries && FrameTiming)               // VulkanQuery.cpp:394
    Delta = FrameTiming->GetTiming(false);                           // VulkanQuery.cpp:405
GGPUFrameTime = TruncToInt(Delta / Frequency / SecondsPerCycle);      // VulkanQuery.cpp:410

2.2 这条时间轴包住了什么

帧首 / 帧末两个时间戳的落点（都在 VulkanRHI.cpp 里）：

471:  WriteBeginTimestamp(CommandBufferManager->GetActiveCmdBuffer());   // 帧首戳
...
1263: WriteEndTimestamp(CmdBuffer);                                      // 帧末戳（present 之前）
1265: Viewport->Present(...);
1273: WriteBeginTimestamp(CommandBufferManager->GetActiveCmdBuffer());   // 下一帧帧首
图 2 · stat unit 的 GPU Time 是一条时间轴上的跨度，中间的空转不扣除
为什么它「看起来总等于帧时间」
因为帧首戳每帧都重新打一次，所以这个跨度天然被帧周期框住了上限；而 CPU 瓶颈时 GPU 大部分时间在等，跨度又被撑到接近上限。「贴着 Frame time」是这个机制的结果，不是它拿 Frame time 算出来的。

2.3 一个容易忽略的门控

// UnrealClient.cpp:502 — 没有有效数据时，这一行直接不打数字
bHaveGPUData[GPUIndex] = RawGPUFrameTime[GPUIndex] > 0;

// UnrealClient.cpp:678 — 屏幕上那一行的行标题
DrawRowTitle(GPURowId++, GPUColumnCount, TEXT("GPU Time"), ...);

所以 r.Android.SupportsTimestampQueries=0 时，屏幕上是 GPU Time: 后面空白，而不是 0。这一点在实测中被用作「开关是否真的生效」的判据（见 §7）。

3通路 B：stat gpu 的 [TOTAL]

一句话结论：stat gpu 的 [TOTAL] 是「所有被插桩 GPU 事件的独占耗时之和」——它只统计引擎打了 scope 的地方，pass 之间的空隙和没插桩的工作一概不算。

3.1 [TOTAL] 是谁

// GPUProfiler.cpp:22 — [TOTAL] 就是一个普通 stat
DECLARE_FLOAT_COUNTER_STAT(TEXT("[TOTAL]"), Stat_GPU_Total, STATGROUP_GPU);

// GPUProfiler.cpp:33 — 它的唯一写入口
FThreadStats::AddMessage(GET_STATFNAME(Stat_GPU_Total), EStatOperation::Set, TotalMs);

3.2 这个数怎么算出来

// RealtimeGPUProfiler.cpp:473-515 — 遍历本帧所有 GPU 事件
uint64 TotalUs = 0llu;
for (int32 Idx = 1; Idx < NextEventIdx; ++Idx)
{
    TotalUs += IncExcTime.ExclusiveTimeUs;        // RealtimeGPUProfiler.cpp:488  无条件累加「独占」时间
}
RHISetGPUStatTotals(bCsvStatsEnabled, TotalUs / 1000.0);   // RealtimeGPUProfiler.cpp:515

而「独占」是减法算出来的：

// RealtimeGPUProfiler.cpp:451-461 — 先取 inclusive，再减掉所有子节点的 inclusive
Aggregate.InclusiveTimeUs = Event.GetResultUs(0);                                  // RealtimeGPUProfiler.cpp:451
Aggregate.ExclusiveTimeUs = Aggregate.InclusiveTimeUs;                             // RealtimeGPUProfiler.cpp:452
...
EventAggregates[ParentIdx].ExclusiveTimeUs -= EventAggregates[EventIdx].InclusiveTimeUs;  // RealtimeGPUProfiler.cpp:461

// RealtimeGPUProfiler.cpp:133-143 — 单事件耗时就是两点之差
if (StartResultMicroseconds[GPUIndex] > EndResultMicroseconds[GPUIndex])
    return 0llu;                                        // RealtimeGPUProfiler.cpp:137-140  时间戳失序 → 直接返 0
return EndResultMicroseconds[GPUIndex] - StartResultMicroseconds[GPUIndex];  // RealtimeGPUProfiler.cpp:142

r.GPUStatsChildTimesIncluded 只改每一行 pass 显示 inclusive 还是 exclusive（RealtimeGPUProfiler.cpp:487）；它不改 [TOTAL]——:488 那句累加 exclusive 是无条件的。

4对照：两者为什么不相等

一句话结论：差异由三个独立成因叠加，其中前两个是结构性的（换场景也在），第三个是移动端特有的（只在 TB(D)R 上出现）。

#成因作用方向证据等级
1 口径差：stat unit 是帧跨度（含空转），stat gpu 是插桩工作量 把 stat unit 推高 源码逐行验证
2 覆盖差：未插桩的 GPU 工作在 stat gpu 里完全不存在 把 TOTAL 压低 源码逐行验证
3 TB(D)R 时间戳失序：render pass 内部的时间戳不可靠，破坏 exclusive 减法 让 stat gpu 抖动 / 出负值 社区共识 + 实测吻合，未做对照实验

4.1 为什么这个 fork 上「本该相等」也做不到

新版 GPU profiler 里，两个数取自同一个中间量：

// GPUProfiler.cpp:1359-1370 —— 但这段代码在 RHI_NEW_GPU_PROFILER != 0 的分支里
uint64 WholeFrameUnion = FTimestampStream::ComputeUnion(StreamPointers);              // GPUProfiler.cpp:1365
GGPUFrameTime = TruncToInt(ToSeconds64(WholeFrameUnion) / GetSecondsPerCycle());      // GPUProfiler.cpp:1368  给 stat unit
RHISetGPUStatTotals(bCsvStatsEnabled, ToMilliseconds64(WholeFrameUnion));             // GPUProfiler.cpp:1370  给 stat gpu

而本 fork 编的是旧 profiler，Vulkan 侧的新路径根本没有实现：

// RHI.Build.cs:16
PublicDefinitions.Add("RHI_NEW_GPU_PROFILER=0");

// VulkanContext.h:303-309 —— 开成 1 时的分支是没写完的 stub
#if RHI_NEW_GPU_PROFILER
    void RegisterGPUWork(uint32 NumPrimitives = 0, uint32 NumVertices = 0) { checkNoEntry(); }  // VulkanContext.h:304
    void RegisterGPUDispatch(FIntVector GroupCount)                        { checkNoEntry(); }  // VulkanContext.h:305
#else
    FVulkanGPUProfiler  GpuProfiler;
    FVulkanGPUTiming*   FrameTiming;
#endif
所以「切新 profiler 让两个数同源」这条路在 Android Vulkan 上走不通
RegisterGPUWork / RegisterGPUDispatch 是渲染器每帧、每次 draw/dispatch 都调的，开成 1 会直接 checkNoEntry() 崩。旁证：VulkanRHI 目录里 FRHIBreadcrumbAllocator / FTimestampStream 零命中——新 profiler 赖以工作的 breadcrumb 时间戳管线在 Vulkan 上不存在。
要做成，得自己给 Vulkan 实现整条管线，属引擎级开发。

5Android 特有：开关门控与拼错名的坑

一句话结论：Android 上这两条通路默认都是关的；而且本项目包体的 DeviceProfile 把开关名字拼错了，等于配置一直以为开着、实际从没生效。

5.1 开关在哪

// AndroidApplication.cpp:19 —— 默认 0 = 关
TAutoConsoleVariable<bool> CVarAndroidSupportsTimestampQueries(
    TEXT("r.Android.SupportsTimestampQueries"), 0, ...);

// VulkanAndroidPlatform.cpp —— Vulkan 平台读它决定要不要开
return CVarAndroidSupportsTimestampQueries != nullptr &&
       CVarAndroidSupportsTimestampQueries->GetBool();

// VulkanUtil.cpp:44 —— 还要硬件真的支持
bool bSupportsTimestamps = (Limits.timestampComputeAndGraphics == VK_TRUE);   // VulkanUtil.cpp:44
SetTimingFrequency((uint64)((1000.0 * 1000.0 * 1000.0) / Limits.timestampPeriod));  // VulkanUtil.cpp:50
GIsSupported = true;                                                        // VulkanUtil.cpp:53
必须走启动期 -dpcvars=，运行期下发无效
GSupportsTimestampRenderQueries 只在 RHI 初始化时赋值一次。运行期用 send_cvar 把 CVar 改成 1，CVar 的值会变，但全局量不会重算，stat gpu 依然没数。
参数形式：-dpcvars=r.Android.SupportsTimestampQueries=1（由 DeviceProfileManager 在引擎早期预应用，早于 RHI 初始化）。

5.2 拼错名会静默变成 dummy 变量

// ConfigUtilities.cpp:375-378 —— 对不存在的 CVar 名，引擎不报错，只造一个替身
IConsoleManager::Get().RegisterConsoleVariable(Key, Value, TEXT("IAmNoRealVariable"),
    (uint32)ECVF_Unregistered | ...);                                            // ConfigUtilities.cpp:375
UE_LOG(LogConfig, Log, TEXT("CVar [[%s:%s]] deferred - dummy variable created"), Key, Value);  // ConfigUtilities.cpp:378

日志里两种形态必须分清：

日志含义
Setting CommandLine Device Profile CVar: [[X:1]]✅ 变量存在，值已写入
Creating unregistered Device Profile CVar: [[X:1]]❌ 变量不存在，只造了替身

实测（S1Game / 2026-09-29，小米 12S）：设备包体的 DeviceProfile 写的是 r.Vulkan.SupportsTimestampQueries（应为 r.Android.）：

LogDeviceProfileManager: Creating unregistered Device Profile CVar: [[r.Vulkan.SupportsTimestampQueries:1]]
LogConfig: CVar [[r.Vulkan.SupportsTimestampQueries:1]] deferred - dummy variable created
r.Android.SupportsTimestampQueries = "false"     LastSetBy: DeviceProfile   ← 真名一直是 false

该次启动共 7 处 dummy（另有 r.Vulkan.DescriptorSetLayoutMode、r.Mobile.FSR.Enabled、r.Landscape.LODDistanceScale、r.HZB.TestUseComputerShader 等）——每一处都是「设了等于没设」。

6移动端特有的精度限制：TB(D)R

一句话结论：Android GPU 是分块延迟渲染（TB(D)R），draw call 不是一段连续执行；把时间戳打在 render pass 内部时读数不可靠。最小可信的测量粒度是「一个 RenderPass」，不是单个 pass / draw。

图 4 · IMR 与 TB(D)R 上时间戳行为的差异（右图的机制为社区共识，非规范条文）

对本项目而言，这一条正好对上观测到的现象：Mobile Scene Render 是包住整个 Mobile 渲染的父 scope，其下的 pass 嵌套在 render pass 里；一旦父子时间戳失序，Exclusive = Inclusive − Σ子项 就会减出负数（见图 3 底部）。

7实测证据

一句话结论：开关的因果关系用启动 A/B 测出来了；stat gpu 的稳定性用同场景三次连采测出来了——小项可信、大项和 [TOTAL] 不可信。

验证过程中我曾把启动日志里的 LogVulkanRHI: Display: - Max Descriptor Sets Bound 7, Timestamps 1 当成「timestamp 已打开」的铁证。翻改动前的 backup 日志比对后发现那行改动前也是 1——它是 Vulkan device limits 的字段，与这个 CVar 无关。判据被 A/B 推翻了。

规律：越小的项越稳，越大的 / 父级的项越不可信。叶子 pass 是「两点之差」直接测得；父级是「减法算出来的」，一旦子项之和超过父项就出负数。

7.3 内部自洽性（说明「汇总」环节没错）

同一张表里各 pass 行的 Average 之和 = 10.99 ms，[TOTAL] = 11.00 ms，差 0.01 ms（四舍五入）。说明 [TOTAL] = Σ exclusive 是如实求和的（含那个负值贡献）——错不在汇总，在上游的父项测量本身。
