一、核心结论速览

图 1 · 跨平台统一开发的技术全景与两条优化主线。左侧为 CPU / 内存场景侧，右侧为 GPU / 渲染侧，各自四项抓手。

两条主线

  • CPU / 内存（场景侧）：高性能场景管线 → 资源重组合批 → PVS 可见性预计算 → SAGC 主动调频
  • GPU / 渲染（渲染侧）：LiteHDR 单 Pass 管线 → Tile Memory Heap → VRS → DFP
  • 两条线互不重叠：前者解决「内存里不该装的东西」，后者解决「Tile 外不该搬的数据」

一句话底层逻辑

  • GPU 优化不只是简单地 Cut Down 算力，更来自对已 Shader 像素的复用
  • 利用帧间的 Temporal（时间）& Spatial（空间）连贯性，以像素复用换取 GPU 算力与 Tile 带宽
  • 移动端开发本质是在硬件 Limit 下做动态资源分配 —— 把 Shader 算力喂给视觉焦点，在人眼钝感区做隐蔽优化
总体取舍
《三角洲行动》的移动端优化路线不是「砍画质换帧率」，而是从资产生产管线（子关卡切分规范、合批规范）与渲染架构（单物理 Pass、片上内存复用）两头同时重做。单纯降低分辨率、简化材质或关闭实时光照等通用手段，无法同时满足 PC 级视觉品质与高帧率竞技要求。

二、背景：跨平台统一开发的技术全景

作为跨 PC、iOS、Android 及主机平台的 F2P 战术第一人称射击游戏，《三角洲行动》需要移动端在保留 PC 级高密度资产与游戏复杂度的同时，维持极高的竞技帧率与功耗表现。本次技术实践基于高通 Snapdragon 8 Elite Gen 5 平台（第三代 Oryon CPU、Adreno GPU 及 18MB 独立高速内存）展开。

PC 与移动端统一开发的架构设计中，项目重构并共享了一套跨四大模块的技术栈：

三、优化前：场景复杂度的现实

在 PC 与移动端双端统一开发的流程中，最先面临的硬阻碍是PC 级高密度场景与移动端有限硬件资源之间的矛盾。以典型地图「潮汐」为例：为在移动端呈现与 PC 版不相上下的画面细节，地图不仅在水平方向摆放了大量建筑、掩体和道具，垂直高度上同样叠加了极高精度的资产。

四、CPU 与内存 · 场景侧优化

4.1 高性能场景管线：子关卡分层切分

关键不在运行时，而在资产制作阶段就做细粒度分类：这样运行时系统就能根据物件的体量与重要度，采用不同的加载（Streaming）策略，实现按需加载。若对整个关卡全量加载，RAM 与 VRAM 会迅速触发 OOM；若仅按简单距离阈值「一刀切」式流送，则会导致远景几何体严重穿帮（POP-in），或近景高频小物件盲目驻留内存。

项目组将地图资产划分为独立的功能层级与尺寸分组，每个分组在构建管线中均配置了明确的流送距离与子关卡切分尺寸：

图 3 · 子关卡切分尺寸与流送距离的三档分层规范。上排为切分尺寸，下排为流送距离，横轴单位为米。

规范化的三个核心环节：子关卡切分与层级划分、组件级与网格体性能优化，以及基于 PVS 的可见性数据准备。

架构层面核心思路
单一资产源的弹性流送（Elastic Streaming）：维持一套统一的场景资产源，运行时依据分层规则进行细粒度解耦与按需加载。
跨端硬件 Scalability 适配：PC 端与高端移动设备可动态调高各层级的 Stream-In 距离以还原极致画质；低端设备则收紧小物件的流送半径，平滑 CPU Component 遍历开销，防止卡顿（Stuttering）。

4.2 资源重组合批（Batching）

以一个典型场景为例，仅静态场景每个单元就有 320 次绘制调用（DrawCall）；算上角色、武器和 UI 还会更高。DrawCall 越多，CPU 提交开销越大 —— 这是移动端发热降频的主要根源。

图 4 · 资源重组合批的三条并行路径：纹理图集、材质合批、模型合批，以及各自的约束与代价。
代价与前提
重组合批需要团队紧密配合 —— 如果美术提交的资源不标准，合批效果就会大打折扣。同时，合批虽然能有效减少 DrawCall，但会带来顶点开销的增加，还需警惕材质变体激增导致包体和内存占用反弹。

4.4 场景可见性预计算：反向利用 PVS 推导子关卡可见性

完成资源重组与合批之后，场景仍面临两项核心瓶颈：其一，组件（Component）总量依然偏高，渲染管线每一帧仍需进行大量遍历与计算；其二，静态网格与纹理资源体量庞大，导致移动端 RAM 与 VRAM 居高不下。

项目组的目标是完全不削减美术资产细节、不损害视觉质量的前提下进行优化。分析发现：虽然玩家身处关卡中能观测到较远景象，但视野之外存在大量处于遮挡或不可见的子关卡资源，这些资产盲目驻留内存造成极大开销。由于传统远距离剔除（Distance Culling）与感知区域加载机制在此类高密度大地图中难以落地，核心优化方向明确为：从内存中主动卸载不可见的子关卡。

为什么经典 Portal 方案（Room Loader）不适用

最初尝试的 Room Loader 以「房间」这一独立物理封闭空间为最小单位管理流送：将室内几何体、遮挡剔除边界及该空间专属资产包绑定至特定关卡，由美术在门窗、走廊或出入口摆放触发体积，玩家靠近时加载、离开时卸载。该范式在传统室内场景中非常经典，但在本项目的高密度大地图中失效：

  • 适用性低且规范苛刻：开放世界场景包含大量半开放建筑与复杂结构，对美术搭建规范要求极严苛，触发体积很难摆放在最优检测位置
  • OOM 风险高：室内外资产依赖关系复杂，玩家频繁跨越触发区时资产难以平滑增量加载与卸载，即使数据经过高压缩，内存占用仍会剧烈膨胀
  • 缺少增量更新机制：缺乏对动态流送的 Incremental Streaming 能力，无法满足大地图实时平滑流送需求

本质上，Room Loader 是图形学中经典的 Portal 渲染技术（Portal Rendering / Sector-Portal System）在资源流送上的延伸 —— 属于「上一代室内优化方案」。而基于 PVS 可见性关联的数据聚类，才是应对现代跨平台大地图的更好方案。

空间错配：按固定几何空间切分的三大缺陷

传统子关卡按物理几何空间尺寸（如 64m × 64m 固定 AABB）强制切割，忽视了资产在实际视角下的视线遮挡关联性。当 PVS 精准记录「从某一视点不可见的组件 ID 列表」时，项目组尝试将规则反转：在任意给定位置，推导哪些子关卡内部的所有组件均处于不可见状态 —— 若某子关卡内全部组件均不可见，则判定该子关卡可被安全卸载。

图 5 · 空间错配：按固定几何空间切分子关卡的三大缺陷 —— 室内外混杂、垂直楼层不清、运行时集成受阻。

解法：基于 PVS 关联数据的子关卡聚类重构

回归 PVS 底层的数据本质 —— 组件之间的可见性关联。位于同一物理空间（如同一房间）内的组件，对同一组视点的可见状态具有高度相似性。据此放弃按几何空间死板切分的方式，利用 PVS 数据按「可见性相似度」进行算法聚类，把真正处于同一视角遮挡区域内的组件自动合并为新的子关卡。

4.5 SAGC：用硬件主动调频消除卡顿

场景资产流式加载粒度变精细后，带来的新挑战是资产卸载与加载的频率显著提升。频繁的磁盘 / 内存 IO 操作、生成实体（SpawnActor）、UI 界面打开以及垃圾回收（GC），极易导致 CPU 出现瞬时负载过高，进而引发帧率下降与画面卡顿（Jank / Stuttering）。

移动端出于功耗与散热控制，CPU 通常不会时刻运行在最高主频，而由操作系统的 DVFS（动态电压频率调整）策略根据负载平缓调节。当发生关卡流送、大量 Actor 动态生成或 GC 时，CPU 负载会在毫秒级内出现剧烈峰值 —— 由于操作系统响应调频存在滞后，CPU 无法及时提升主频消化突发开销，该帧耗时大幅拉长，表现为卡顿。

项目组引入高通的 SAGC（Smart Adaptive Game Control）架构，改变了以往「等待系统被动检测负载再升频」的模式，赋予游戏引擎主动通知硬件提频的能力：

  • 重载任务感知：引擎在执行卡顿高发操作（GC、关卡流送、打开复杂 UI、生成 Actor）之前，提前识别即将到来的 CPU 负载峰值
  • 主动硬件干预：在重载逻辑触发前，通过 QAPE API 调用 CPU 提频接口，并传入预设的提频比例与持续时间
  • 消除瞬时瓶颈：CPU 硬件提前升至高主频运行，顺畅消化突发计算任务，完成后恢复正常调度
图 7 · SAGC 主动调频链路（GameApp → QAPE → SAGC → Device PerfHints → Perf-HAL → QEGA-HAL）与被动 / 主动调频的时序对比。
收益
通过将细粒度流送、GC 逻辑与 SAGC 主动调频深度结合，在不增加整体设备功耗和发热的前提下，有效压制了重载操作引发的帧率波动，保障了移动端高密度场景下的运行流畅度。

五、GPU 与渲染 · 渲染侧优化

5.1 移动端渲染的挑战

PC 端的经典延迟渲染管线基于 DirectX 12 等高算力 API，依托显存带宽与 GPU 算力，将渲染过程划分为 6 个核心阶段：

阶段内容
1. 场景设置深度预通过（Depth Pre-Pass）与 HZB（Hierarchical Z-Buffer）构建，提前剔除不可见几何体；处理 Shadow Pass，生成多层级 Shadow Map。
2. 表面与 G-Buffer渲染贴图与材质属性至 G-Buffer（含 D-Buffer 贴花、自定义深度与材质参数），为后续光照计算准备空间几何与材质数据。
3. 光照与复杂效果屏空间反射与环境光遮蔽（SSR / SSAO）、屏幕空间弯曲法线（SSRN）、半透明渲染、重阴影（Re-Shadow）、体积光 / 体积雾、探针全局光照（PRTGI）及各类精确光源计算。
4. 反射与高级特效SSR 高阶反射、环境与天空光照（Sky / Environment Lighting）、高精度半透明混合。
5. 后处理TAA（时间序列抗锯齿）、色调映射（Tone Mapping）与屏幕空间特效。
6. UI 与呈现绘制 UI 元素并提交至最终显示缓冲区。

移动端受限于无主动散热风扇与电池供电的物理条件，GPU 渲染优化必须优先将功耗控制（Thermal Budget）置于首位。重负载下长时间运行易触发热降频，导致 GPU 被限制频率、帧率大幅波动。

剪刀差趋势
处理器算力（FLOPS）的增长速度远超系统内存带宽（Memory Bandwidth），二者差距持续扩大。因此，昂贵的系统带宽与受限的 GPU 算力构成移动端渲染优化的两大核心瓶颈：
① TBDR 架构与带宽限制 —— 频繁读写 G-Buffer 和多路 Render Target 会产生海量 DRAM 与 Tile Memory 之间的读写交互，内存带宽压力激增，引发剧烈发热并触发降频；
② 算力与功耗预算受限 —— PC 端依赖高功耗 GPU 完成的体积光、SSR 与高频光照计算，在移动端严格限制下无法平稳运行。

5.2 LiteHDR 渲染管线

面对昂贵的带宽与有限的 GPU 算力，项目组从底层重构渲染管线：最大化利用 Tile Memory（片元内存）、引入硬件级特性降低带宽、重构着色与帧预测逻辑。LiteHDR 的核心理念是在极致节省带宽的前提下，完整保留 PC 级的 HDR 高动态范围视觉品质。

核心改进是场景渲染 Pass 深度合并：传统 PC 延迟渲染把管线拆成多个独立 Render Pass（写 G-Buffer → 切 Pass 读显存做光照 → 半透明 → 后处理），每次切换都引发海量 DRAM 读写。而移动端（TBDR 架构）的 One-Pass Deferred 依托 Tile Memory 硬件特性（Vulkan Subpass / Subpass Load 或 GLES Framebuffer Fetch），把原本多个 Pass 的数据传递限制在 GPU 内部高速的 Tile Memory（On-Chip SRAM）中。

图 8 · 传统 PC 延迟渲染的多 Pass 往返 vs LiteHDR 的单物理 Render Pass 结构对照。

具体而言，LiteHDR 将场景渲染至后处理的全部环节合并至单个 Render Pass：

  • Pass 1 · 深度与贴花优化：移除独立的 Depth Pre-Pass，改用硬件级 Early-Z / LRZ（Low-Resolution Z）；墙面灰尘等静态细节在资源重组阶段提前处理，动态细节（弹痕、涂鸦）以 Subpass Load / Framebuffer Fetch 结合深度扩展直接在 Tile Memory 内部绘制
  • Pass 2 · 光照与半透明合并：将 Lightmap、预烘焙 AO / GI、实时光照以及半透明几何体完全统一在同一个 Fragment Shader 中并行解算，无需额外通道切换
  • Pass 3 · 后处理 Screen Mesh 替代传统后期：受击、受伤等全屏叠加特效采用紧随场景渲染的 Screen Mesh（全屏网格）在 Tone Mapping 前同通道绘制，避免全屏读写系统内存
  • Pass 4 · 蒙特卡洛随机采样的自动曝光（见下）
  • Pass 5 · 色调映射 Tonemap 的渲染通道合并：将 Tonemap、自动曝光与 UI 作为 BasePass 的后续 Subpass 组合，用 Subpass Load 读取场景色彩，在写回 DRAM 之前完成 HDR 到 SDR 的转换

G-Buffer 压缩与材质分类

HDR / SDR 动态曲线编码

精度冲突：游戏场景在高动态范围（HDR）下渲染，太阳光或金属高光反射的亮度非常高（数值可能达到 4.0 到 9.0 甚至更大）；但为节省移动端显存带宽，画面被直接画在标准动态范围（SDR）的缓冲区里，最高只能存 1.0。若把大于 1.0 的 HDR 数值强行写入，超过部分会被全部截断为 1.0 —— 太阳、火焰和高光处丢失所有层次细节，白茫茫一片。行业常用的 RGBM 或对数编码方案，要么计算太耗 GPU，要么容易出现色彩断层（色带）。

项目组采用了一套极轻量的压缩曲线公式：

C_encoded = C_linear × K / (1 + C_linear × K)
  • 压缩存储（先编码）：场景渲染时用该公式把任意大的 HDR 亮度值（如 4.0 或 9.0）平滑压缩映射到 0 ~ 1 区间，安全存入 SDR 缓冲区
  • 还原绘制（后解码）：在色调映射（Tonemap）之前用反向公式还原真实亮度信息，完全避免高光被裁切破坏

动态 K 值调控：K 是系统根据「屏幕平均亮度」动态计算出的缩放杠杆 ——

  • 亮场景 → 平均亮度高 → K 变大 → 压紧高光，抬高并保住暗部
  • 暗场景 → 平均亮度低 → K 变小 → 放平曲线，保住高光层次
已知瑕疵与未给出项
用极简单的加乘指令代替了复杂的对数 / 指数运算，既不增加显存带宽负担，又保住了高光与暗部细节。但由于数值在存储前经过非线性曲线压缩，此期间若进行 Alpha 半透明混合，计算出的混合颜色会有轻微偏差。
另需说明：原文未给出 K 的具体取值范围与计算细节，此处不予推测。

自动曝光：从全屏逐像素采样到蒙特卡洛随机降采样

人眼从暗处走到亮处有一个适应过程，游戏中需要「自动曝光」模拟该效果。传统做法是每帧对全屏像素做全量读取（以 1080p 为例超过 200 万像素）计算平均亮度 —— 巨大的显存读写开销与带宽负担。

项目组的解法是抽样调查：其实不需要算得绝对精准，只要知道「大概有多亮」就够了。

  • 把画面切成一个个 16×16 的小格子，每个格子里随机只选 1 个像素
  • 采样数据量瞬间缩减到原来的 1/256，直接写入一个极小的缓冲区
  • 算平均亮度时，直接借用上一帧算好的平均值进行平滑过渡 —— 人眼本身适应光线就需要时间，这种微小延时在视觉上不仅毫无违和感，反而非常自然

Tonemap：单通道（One-Pass）解算

传统流程是将场景渲染结果写回显存（DRAM），后处理阶段再从显存读取图像数据做 Tonemap 并重新写回，导致显存被多次重复读写。LiteHDR 借由 API 提供的 SubpassLoad（Vulkan）或 Framebuffer Fetch（OpenGL ES），在 Tile Memory 内部完成场景着色后紧接着作为后续 Subpass 执行 Tonemap，并把 UI Pass 同样合并为该渲染通道的最后一个 Subpass。

整条链路从「场景渲染 → 显存写入 → 显存读取 → Tonemap → UI 绘制 → 输出」的多通道流程，重构为「Tile 内场景计算 → Tile 内 Tonemap → 叠加 UI → 写出至屏幕」的单通道流程。

5.3 Tile Memory Heap：异构分辨率下的片上复用

最理想的技术路线是将场景渲染、Tonemap 和 UI 绘制合并在单个 Render Pass 中。但在旗舰机等大屏设备上，经常出现后台缓冲区（Back Buffer）分辨率与场景渲染分辨率不一致的情况 —— 例如场景按 0.8 动态分辨率渲染以节省 GPU 算力，而 UI 必须以 1080p 或 2K 原生分辨率渲染以保持文字清晰度。

这种分辨率差异打破了单通道合并的物理前提：UI Pass 无法再作为 BasePass 的 Subpass 直接并入，系统必须先将 Tonemap 处理后的场景颜色写出到 DRAM，再由 UI 通道重新读取该画面进行叠加 ——「Tonemap 写出 → UI 通道读取」带来的二次显存读写成为新的带宽消耗瓶颈。

图 10 · 异构分辨率下的两种路径对照：传统写回 DRAM 再读出 vs Tile Memory Heap 片上重映射。

从「固定 Framebuffer 绑定」到「片上虚拟内存堆」

  • 传统 GMEM 模式：Tile Memory 被当成一个固定的、与 Render Pass / Framebuffer 强绑定的临时 Buffer。只要 Pass 分辨率改变，GPU 就必须清空并重新初始化 GMEM 布局，因此中间数据必须写回 DRAM
  • Tile Memory Heap 模式：高通在驱动与硬件层面将 Tile Memory 抽象成一块物理驻留在 GPU 芯片内部（On-Chip）的通用内存堆（Memory Heap）。场景 Pass（0.8 分辨率）渲染完成后，其 Render Target 并不执行写回 DRAM（设置 STORE_OP_DONT_CARE），而是将这段物理 SRAM 空间直接保留在 Tile Memory Heap 中；随后启动的 UI Pass（1080p）不需要重新分配 DRAM，而是通过 API 直接将自己的 Texture 绑定（Aliasing 重映射）到刚才场景使用的同一块片上 SRAM 内存地址上

坐标与采样：分辨率不同如何「对应上」

分辨率不一致时，不再依赖硬件默认的 1:1 像素对应（如 Subpass Load），而是改用片上纹理采样器进行 UV 坐标插值：

  • 片上纹理化（On-Chip Texture Access）：通过 VK_QCOM_tile_memory 扩展，留在 Tile Memory Heap 里的场景画面（0.8 分辨率）在 UI Pass 看来变成了一张可以直接被 Texture Unit 采样的纹理（VkImage）
  • UV 坐标映射与缩放（Bilinear Scaling）：UI Pass 在 1080p 屏幕空间绘制全屏四边形时，Pixel Shader 传入归一化 UV (u, v) ∈ [0, 1]；硬件采样器自动根据场景实际分辨率（如 1536 × 864）映射回正确位置 ScenePixel = (u × 1536, v × 864)，并配合硬件双线性过滤实时计算出插值后的颜色

  • 片上极速采样（On-Chip Sample / Fetch）：UI Pass 启动时直接从同一块 Tile Memory Heap 中零延时读取 Tonemap 后的场景像素，与原生分辨率的 UI 顶点进行混合绘制
  • 最终单次写出：只有在 UI 混合完毕后，最终包含画面与 UI 的完整帧才会被一次性写回主显存的 Present Buffer

5.4 VRS：动态自适应的可变着色率

除了系统内存带宽，GPU 本身的高频着色计算（Pixel Shading）也是设备发热和功耗上升的主要来源。在许多场景中（例如角色置身于室外环境时），金属容器表面、天空、远处的大坝等区域，小范围内的像素颜色非常接近甚至完全相同。VRS（Variable Rate Shading）允许 GPU 对多个相邻像素仅执行一次片元着色计算，并将结果直接复用到整个像素块中。

着色率档位含义
1×1标准着色，每个像素单独计算 1 次
1×2 / 2×1每 2 个像素执行 1 次着色
2×2每 4 个像素执行 1 次着色（着色算力压减 75%）
2×4 / 4×2 / 4×4低精度粗粒度着色，如 4×4 表示 16 个像素共享 1 次着色计算

实施 VRS 的核心技术难点在于：如何精准、快速地识别出画面中视觉相似的区域，避免在图像边缘、高频纹理或复杂光影处误用低着色率而导致画质失真。

方案的核心思路是利用上一帧的历史亮度数据与当前帧的空间颜色方差，以极低的计算开销（毫秒级）动态生成 VRS 控制图：屏幕划分为基础小块并归并为更大的宏处理单元（如 2×2 组合），实时缓存各 Tile 上一帧的平均亮度，当前帧逐块计算片元间的局部颜色方差（Color Variance）。方差低于阈值的平坦区应用 2×2 甚至 4×4 粗粒度着色率；方差大的细节区（几何边缘、细线条、高频纹理）维持 1×1。对于远距离渲染对象，按其 LOD 层级强制追加更激进的 VRS 降级。

图 11 · VRS 基于亮度方差的平坦区识别：左侧方差 Debug 视图，右侧着色率映射策略与执行流程。

5.5 DFP：动态帧预测

把视角从「单帧渲染」切换到「连续的游戏过程」：玩家面前的建筑、道路和地形每一帧都在重新渲染，但这些场景元素本身并没有发生物理移动，改变的仅仅是玩家视角的移动与平移。这意味着帧与帧之间的画面存在极高的时间相关性（Temporal Coherence）。

为什么不用传统的「补帧 / 插帧」

  • 插值（Interpolation）：需要等待后续帧渲染完成后再插入中间帧，会带来明显的操作延迟（Input Latency）
  • 外推（Extrapolation）：在视角快速转动或剧烈运动时，极易产生严重的画面伪影与撕裂（Artifacts）

对于追求毫秒级响应、极致高刷与精准枪感的竞技射击游戏（FPS），任何额外的输入延迟与画面伪影都是不可接受的。

为了在「零额外延迟」的前提下实现像素复用，项目组引入硬件级动态帧预测（DFP），将优化下沉至 GPU 渲染管线的计算阶段：

图 12 · DFP 动态帧预测的动静分离与 Unocclusion 补缝机制，以及 VRS × DFP 的时空双维协同。
  • 第一步：追踪像素运动轨迹 —— 利用 GPU 的深度缓冲区与运动矢量（Motion Vectors），精准计算出当前帧（第 N+1 帧）屏幕上的某个点在上一帧（第 N 帧）的位置
  • 第二步：动静分离与选择性片元着色 —— 房子、道路、远景等仅因相机移动而位置改变、几何与光影未变的大块静态像素，直接继承上一帧的着色结果，彻底免除昂贵的片元着色器（ALU）计算；敌人、队友、手持武器、枪口火光、UI 元素以及发生剧烈光影变化的区域完全不复用，仍按正常管线逐像素重新着色
  • 第三步：边缘缺失自动补缝（Unocclusion） —— 玩家快速甩头或剧烈旋转视角时，屏幕边缘会露出一块上一帧镜头没拍到的「全新未知区域」，管线自动识别这些没有历史数据的空白像素，仅对其触发全量片元着色进行补画，避免画面边缘出现黑边、拉伸或断层
收益与画质平衡
相比传统插帧补帧，DFP 纯粹是在渲染端做算力「瘦身」，完全不破坏原生的操作响应速度，保持了 FPS 游戏所需的极低输入延迟；大幅降低片元着色器 ALU 计算量与显存带宽占用，有效缓解 1080p / 120fps 等高画质高帧率模式下的发热降频问题。
补充：这套动静分离的帧预测在《暗区突围》中也有类似应用。

六、关键启示与未来方向

底层逻辑
概括来说，《三角洲行动》移动端 GPU 优化的底层逻辑是：利用 Frame 间的 Temporal & Spatial 连贯性，以像素复用换取 GPU 算力与 Tile 带宽。
GPU 优化不只是简单的 Cut Down 算力，更来自于对已 Shader 像素的复用。移动端开发本质上是在硬件 Limit 下做动态资源分配（Resource Budget Allocation）—— 按玩法需求把 Shader 算力喂给视觉焦点，在人眼钝感区做隐蔽优化，这是渲染架构设计的核心。

对移动端渲染团队

  1. 优化要从资产生产管线入手：子关卡切分规范与合批规范定不下来，运行时怎么调都是补丁。300m × 300m 装 300 个子关卡、80,430 个 Actor 的原始关卡，靠运行时剔除救不回来
  2. PVS 数据可以反向用：它不只服务绘制剔除，也能作为「内存侧整块卸载」的聚类特征 —— 从组件级粒度提升到关卡级粒度
  3. 卡顿要用硬件前置解决：与其让系统被动检测负载再升频，不如让引擎把即将到来的峰值提前告诉硬件（SAGC）
  4. 借力硬件特性：Tile Memory Heap / VRS / DFP 都是片上能力，先把带宽与算力瓶颈吃透，再谈画质提升

未来方向（120fps 成为竞技刚需的当下）

  1. 渲染品质进化：实现更真实的光影 Transport、更具沉浸感的 Reflection 效果与更精细的 Mesh / Geometry 细节
  2. 场景动态交互：引入更多 Physics-based 场景破坏与环境互动
  3. 硬件深度挖掘：立足「Know Your Hardware」，通过更聪明的 Scalability 策略，让不同平台与层级的移动 GPU 都能稳帧输出竞技级画质

核心课题是：如何在有限的帧率预算内做技术演进。
