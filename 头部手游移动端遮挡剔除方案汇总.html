一、核心结论：手游为什么要另起炉灶

① 静态为主 → PVS

  • 离线烘焙可见性，运行时仅查表
  • 零渲染线程开销，最稳
  • 缺点：不支持动态物体、数据量大、烘焙慢

② 动态复杂 → SOC

  • CPU 软光栅低分辨率深度图
  • 支持动态对象、包体小
  • 《明日之后》iPhone 6s 仅 ~0.4ms

③ 慎用硬件查询

  • 回读延迟、查询上限（高通 510 次）
  • 移动 GPU 上往往得不偿失
  • UE 移动端常配合距离剔除替代
总体取舍
端游可以"用 GPU 算可见性"，手游必须"省着用 GPU、把可见性算在 CPU 或离线"。核心原因：移动 GPU 多为 TBDR（Tile-Based Deferred Rendering）架构，对带宽和回读极其敏感；硬件遮挡查询的 GPU→CPU 回读会打断管线、引入帧延迟。因此头部手游的主流答案是：静态场景 PVS 预计算 + 动态场景轻量 SOC + 距离/视锥剔除兜底。

二、四类剔除与开销排序

UE 把可见性计算分为四级，开销从低到高。手游优化的精髓是：尽量用便宜的级别先把物体筛掉，把昂贵的遮挡判断留给少数物体。

视锥内的真相
在城市 / 森林等复杂场景里，相机视锥内的物体通常只有约 10% 真正可见，其余约 90% 被遮挡。如果不剔除，GPU 仍会跑顶点着色器并做昂贵的 Z-Test。这就是遮挡剔除（解决"被挡住看不见"）相比 LOD（解决"太远看不清"）的独立价值。

三、端游方案在手机上为什么失效

硬件遮挡查询 HOQ

  • CPU 让 GPU 画不可见包围盒，回读像素数判断是否遮挡
  • 回读延迟：GPU→CPU 同步打断管线，常引入 1 帧延迟
  • 查询上限：UE4 对高通设备限制最大 510 次查询（其他设备 4000），超出直接放弃 → 剔除失效
  • 大量动态物体时，查询本身就是巨大 DC 开销

GPU HZB（层级 Z-Buffer）

  • 用 Mip 化的 SceneDepth 检测包围盒，比 HOQ 保守（剔得少）
  • 移动端实测：动态物体场景 HZB 性能优于硬件查询
  • 机型差异巨大：OPPO R15 表现好，R17 仍有 4~6ms 回读开销
  • 依赖 Compute / 特定硬件支持，老机型未必可用
微软 HoloLens / 移动端官方建议
"移动设备上 GPU 遮挡查询很慢。一般你希望 GPU 专注于渲染。如果觉得遮挡有帮助，试试软件遮挡剔除（Support Software Occlusion Culling），让 CPU 干这活、避免 GPU 查询。" —— 但注意：如果你已经被大量 DC 拖成 CPU bound，开软件遮挡反而更糟。这正是手游要用"轻量 SOC"而非"标准 SOC"的原因。

四、SOC 软光栅遮挡剔除（明日之后 GDC2023 深度拆解）

网易《明日之后》是移动端 SOC 的标杆案例。需求很苛刻：同时支持静态 + 动态对象、包体小、还得在 iPhone 6s 这种低端机上跑得飞快。传统 Intel MSOC（PC/主机主流）针对 AVX 优化、在手机上太慢，所以他们做了一套轻量 SOC。方案由三部分组成：剔除算法 + 优化管线 + 离线遮挡网格生成器。

4.1 轻量 SOC 剔除算法（相比 Intel MSOC 的改动）

SIMD：Arm Neon 代替 AVX

MSOC 针对 x86 AVX 优化，移动端改用 Arm Neon 实现 SIMD（单指令多数据），适配手机 CPU。

低分辨率分层深度缓冲：256×160

整个 buffer 分 4 个 bin，每 bin 80 个 tile，每 tile 含 4 子 tile（8×4 像素块），一个 tile 共享一个深度值。128 像素对应一个 __m128i，4 个深度值对应一个 __m128。

Reversed-Z + 改投影矩阵

深度值只用于 Z 测试，重要的是相对大小。用 反向 Z 提升精度；进一步把远平面投影设为 0，让投影矩阵只剩 4 个非零项（比原矩阵少 1 个），投影更快，配合 SIMD 提速明显。

简化光栅化流程

遮挡物光栅化阶段：不做背面剔除、优化顶点排序、楔形(wedge)收集阶段加预排序；保留边缘填充光栅化做覆盖检测，但去掉 MSOC 的"启发式丢弃"，深度更新回落到简单写入。每三角形只存 1 个最远、最保守的深度值。

Early Out 提前退出

被遮挡物可见性查询前加一个 Early Out 步骤，绕过近 50% 被遮挡物，显著降低查询成本。

算法性能数据（公开演讲）
遮挡物光栅化：每三角形约 0.4 微秒；可见性查询：每被遮挡物约 0.56 微秒。Early Out 跳过近 50% 被遮挡物。

4.2 优化剔除管线

  • 数据与指令分离存放：方便访问数据、面向对象组织指令 → 提升约 0.5ms
  • 不同数组存不同类型遮挡物信息，调用特定通知函数
  • 可见性过滤器级联：逻辑设置 → 视锥剔除 → SOC，多级过滤；用"可见性锥体"标记，视角在锥体外则按尺寸阈值判不可见，约 50% 遮挡三角形跳过光栅化（需光栅化三角形从 1539 降到 874）
  • 多线程：iPhone 6s 上整体从 1.5ms 降到约 0.4ms

4.3 离线高质量遮挡网格生成器

  • SOC 结果严重依赖遮挡网格质量。离线生成极简遮挡网格，面数可降至原始模型的约 5%
  • 必须保守（不能比原物体大），否则会误剔可见物体
  • 美术因此可以放心堆复杂场景，性能由 SOC 兜底

五、PVS 预计算可见性：移动端最稳的选择

PVS（UE 中称 Precomputed Visibility System）把可见性算到离线，运行时只查表，省掉硬件查询的渲染线程时间——这正是移动端最看重的。

UE PVS 工作流程

  1. 将场景划分为若干 cell（格子）
  2. 离线计算相机位于每个 cell 时，场景中各物体的可见性，烘焙数据。数据大小 = cell 数 × 物体数 / 8（一物体一 bit）
  3. 运行时根据相机所在 cell 查表，得到可见性，再叠加一次视锥剔除

烘焙数据有大量重复 0/1，可用压缩算法压缩。放置 Precomputed Visibility Volume 包裹玩家可达区域即可。

PVS 优点

  • 运行时极高效（仅查表），无 GPU 回读
  • 省渲染线程时间，移动端友好
  • 适合中小型 / 房间走廊式场景

PVS 缺点

  • 不支持动态物体：墙塌了、门开了就失效
  • 开放世界数据量巨大
  • 改地图要重烘焙，可能几小时
  • 增加运行时内存与光照构建时间
常规组合拳
头部手游很少单用一种：静态建筑/地形用 PVS，动态角色/可破坏物用 SOC 或距离剔除，植被用距离剔除 + Imposter。常规场景下综合剔除率可超 60%，SOC 在 1ms 内减少约 65% 的 DC（公开案例数据）。

软件遮挡剔除Support Software Occlusion Culling移动端推荐，CPU 算、避免 GPU 查询

移动端取舍铁律
① 移动端动态遮挡（GPU 查询）默认很慢，优先 PVS + Cull Distance Volume；② Cull Distance Volume 只剔静态物体，动态物体需自己处理或用 SOC；③ 若已是 CPU bound（DC 太多），盲目开软件遮挡会更糟 —— 先降 DC 再谈遮挡。

八、避坑清单

方案选型坑

  • 直接照搬端游硬件查询：手机回读慢、有查询上限，大概率反向劣化
  • PVS 用在动态/可破坏场景：墙塌门开后剔除错误，露馅穿帮
  • CPU bound 时硬开软件遮挡：剔除本身的 CPU 开销雪上加霜
  • 遮挡网格做太大/不保守 → 误剔可见物体，出现"物体突然消失"

参数 / 工程坑

  • Cull Distance Volume 不剔 Movable 物体，动态物体白配
  • 遮挡单元(cell)大小与物体尺寸不匹配 → 剔除精度差
  • Smallest Occluder 设太大 → 小遮挡物失效；设太小 → 烘焙慢、数据爆
  • 编辑器看不到剔除效果，必须切游戏视图(G 键)实测
  • HZB 机型差异大，不能一刀切，要按目标机型分档实测

九、落地 Checklist 与定位工具

选型决策树

  1. 1 先上距离剔除 + 视锥剔除（必做、最便宜）
  2. 2 静态场景为主 → PVS 预计算
  3. 3 大量动态/可破坏 → 轻量 SOC（CPU 软光栅）
  4. 4 开放世界 → 布局大遮挡物 + 植被距离剔除 + Imposter
  5. 5 慎用硬件查询；HZB 按机型实测决定
  6. 6 离线生成保守的低面遮挡网格

定位工具

  • UE：stat InitViews（看可见性/剔除耗时）、FreezeRendering、r.VisualizeOccludedPrimitives、Unreal Insights
  • Unity：Occlusion Culling 窗口 Visualization 模式、Frame Debugger、Stats 浮层
  • 通用：RenderDoc 看 Overdraw；Snapdragon Profiler（Android）；关注 InitViews 线程占比
验收标准
城市/森林复杂场景，遮挡剔除应能剔掉视锥内 50%~90% 不可见物体；剔除本身单帧耗时应控制在 毫秒级（SOC 标杆 iPhone 6s ~0.4ms）。若剔除耗时 > 收益（DC/Overdraw 下降），说明方案选错或场景不适合遮挡剔除。
