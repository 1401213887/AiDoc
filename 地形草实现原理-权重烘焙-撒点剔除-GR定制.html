UE5 地形草（Landscape Grass）实现原理
GR / 三角洲分叉源码考古 · 权重烘焙 · 撒点算法 · 剔除定制

仓库 C:\GR_main · 引擎 UE5EA（UE 5.5.4 分叉）· 每条结论均附 文件:行号 证据
一句话结论：地形草不是"美术摆出来的实例"，而是一套 材质权重 → GPU 烘焙 → 扁平权重表 → CPU 概率撒点 → 后台线程建剔除树 → 运行时动态 HISM 上屏 的程序化系统。整套链路的重心全在引擎侧，游戏工程几乎不碰它。

0. 先纠一个概念 —— 你 session 里的"转 ISM"重点

项目配置里确实有 foliage.ForceISM=1（DefaultEngine.ini:268），CVar 定义在 WorldPartitionLevelHelper.cpp:95-100，帮助文本写着 "all FoliageInstancedStaticMeshComponent will be replaced with InstancedStaticMeshComponent during cooking"。 但它管不到地形草，两条独立的理由： 1. 类型不匹配：转换用 IFA->ForEachComponent<UFoliageInstancedStaticMeshComponent>(...)（WorldPartitionLevelHelper.cpp:1760）筛选，只遍历 InstancedFoliageActor 上手动摆放的植被。地形草的组件类型是 UGrassInstancedStaticMeshComponent（GrassInstancedStaticMeshComponent.h:10，继承 UHierarchicalInstancedStaticMeshComponent），不在筛选范围内。 2. 时机不匹配：转换发生在 cook 期的关卡 Actor 上（WorldPartitionLevelHelper.cpp:1758）。而地形草组件是 ALandscapeProxy 在 运行时用 NewObject<UGrassInstancedStaticMeshComponent>(this, NAME_None, RF_Transient) 动态造出来的（LandscapeGrass.cpp:3000），cook 期根本不存在，没有可转换的对象。
结论：foliage.ForceISM 是"植被 Foliage → 平铺 ISM"的 cook 期优化，与地形草是两条完全独立的链路。地形草的实例承载组件至今仍是 HISM，靠自建 ClusterTree 做剔除。

3. 数据：一张"高度 + 权重"的扁平表

地形草不缓存任何实例变换。每个 ULandscapeComponent 持有一份 FLandscapeComponentGrassData（LandscapeComponent.h:203），内部就是一块连续内存：

图 2 · FLandscapeComponentGrassData 内存布局

打包逻辑在 LandscapeGrass.cpp:1544-1579（InitializeFrom）：先把高度 memcpy 进去，再按 GrassType 逐个追加权重段并记录偏移。读取时 GetWeight(x,y) = WeightData[x + Stride*y] / 255.f（LandscapeGrass.cpp:1879），Stride = ComponentSizeQuads + 1（LandscapeGrass.cpp:1865）。

序列化有明确的版本演进（LandscapeGrass.cpp:1634-1731）：关键分水岭是 LandscapeGrassSingleArray（LandscapeGrass.cpp:1674）—— 在此之前高度与权重是分开的两个容器，之后才统一成 NumElements / WeightOffsets / HeightWeightData 三件套；另一条是 LandscapeSupportPerComponentGrassTypes（LandscapeGrass.cpp:1642），把旧的 MaterialStateIds 换成单一 GenerationHash。

4. 权重从哪来：材质节点 → GPU 烘焙 → 回读

4.1 材质侧

地形材质里的 LandscapeGrassOutput 节点，每个输入是一个 FGrassInput（MaterialExpressionLandscapeGrassOutput.h:17），持有 Name / GrassType / Input，节点上限 32 个草类型（MaterialExpressionLandscapeGrassOutput.h:46）。编译时把引脚透传到自定义输出槽，未连线则恒为 0（LandscapeGrass.cpp:1191-1201）。

4.2 GPU 烘焙

由 FLandscapeGrassMapsBuilder（LandscapeGrassMapsBuilder.h:37，由 ULandscapeSubsystem 持有）驱动，每个 component 走一个六态状态机（LandscapeGrassMapsBuilder.h:91-99）：

Pending → NotReady → TextureStreaming → Rendering → AsyncFetch → GrassMapsPopulated

渲染采用一整条横向长条 RT（不是每 variety 一张纹理）：

  • 目标格式 PF_B8G8R8A8（LandscapeGrassWeightExporter.cpp:519），无块压缩、无持久 UTexture，纯 RDG 临时资源，回读后丢弃。
  • 分辨率 = 一个地形顶点一个纹素：ComponentSizeVerts = ComponentSizeQuads + 1（LandscapeGrassWeightExporter.cpp:565），例如 63 quads → 64×64。
  • 高度占用 2 个通道，故每 pass 净装 4 个权重：NumPasses = ceil((2 + NumGrassMaps) / 4)（LandscapeGrassWeightExporter.h:64）；pass 0 的 RG 存高度、BA 存权重 0/1（LandscapeGrassWeight.usf:82-96）。
  • 整条 RT 宽度 = 所有 component × pass 横向拼接（LandscapeGrassWeightExporter.cpp:586-588），正交俯视、强制 LOD 0（LandscapeGrassWeightExporter.cpp:501）。

回读后 FetchResults（LandscapeGrassWeightExporter.cpp:763-779）做解交织：高度按 R<<8|G 还原成 uint16，权重按 stride 4 的字节视图取（LandscapeGrassWeightExporter.cpp:814-815），最终 InitializeFrom(..., bStripEmptyWeights = true)（LandscapeGrassWeightExporter.cpp:898）写入 Component->GrassData（LandscapeGrassWeightExporter.cpp:924）。

移动端关键限制：Grass weight 导出 shader 要求 SM5（LandscapeGrassWeightExporter.cpp:54、:97、:124）。即移动端（ES3_1）不能在运行时生成 grassmap，只能用烘焙进包的数据 —— 这决定了移动端草的密度是"策划期定死的"。

5. 撒点算法：权重当概率用

核心在 FAsyncGrassBuilder::Build()（LandscapeGrass.cpp:2173），跑在后台线程。候选点数量由密度反推网格边长：

SqrtMaxInstances = CeilToInt32(Sqrt(|Extent.X * Extent.Y * GrassDensity / 1000.0f / 1000.0f|))

—— LandscapeGrass.cpp:1837。Extent 单位为 cm（LandscapeGrass.cpp:1829-1831）。

量纲警示（实测踩点）：GrassDensity 的注释写 "Instances per 10 square meters"（LandscapeGrassType.h:44），但公式除的是 1e6。在 cm² 量纲下 1e6 cm² = 100 m²，与注释声称的 10 m² 差一个数量级。调密度时以公式实测为准，不要按注释心算。（本条为源码字面差异，未找到其他说明。）

两条撒点路径，保留判据完全一致：

路径触发位置说明
Halton 序列bUseGrid == falseLandscapeGrass.cpp:2181-2239Halton(idx + BaseIndex, 2) / (..., 3) 生成 XY，低差异、无网格感
抖动网格bUseGrid == true（默认）LandscapeGrass.cpp:2240-2374规则网格 + 两个独立随机数做 jitter（LandscapeGrass.cpp:2271-2273）
Instance.bKeep = (Weight > AllowedDensityRange.Min)
              && (Weight <= AllowedDensityRange.Max)
              && (Weight >= RandomStream.GetFraction())   // ← 权重即概率
              && !IsExcluded(Instance.Pos);

—— Halton 分支 LandscapeGrass.cpp:2205-2207；网格分支 LandscapeGrass.cpp:2285-2287。

这是整个系统最优雅的一点：权重不是"数量"，而是"生存概率"。权重 0.5 意味着该候选点约 50% 概率长出一棵草。所以策划刷权重直接控制疏密，而实例数天然随权重线性缩放，无需额外的数量映射表。

权重采样是双线性插值（取周围 4 个顶点），高度按四边形三角剖分做重心坐标还原（LandscapeGrass.cpp:2409-2468）。朝向计算有两种：

  • AlignToSurface 开启时，网格分支用相邻采样点叉乘求法线（LandscapeGrass.cpp:2327-2334）
  • 分叉自研的修正路径见 §8

6. 调度：按相机距离摊帧

入口 ALandscapeProxy::UpdateGrass(const TArray<FVector>& Cameras, ...)（LandscapeGrass.cpp:2673 / :2680），三层距离门限：

门限公式位置
开始创建MustHaveDistance = GuardBandMultiplier(1.3) × EndCullDistance × CullDistanceScaleLandscapeGrass.cpp:2844
丢弃回收DiscardDistance = GuardBandDiscardMultiplier(1.4) × EndCullDistance × CullDistanceScaleLandscapeGrass.cpp:2845

两个 guard band 的差值（1.4 vs 1.3）正是迟滞带：进入用 1.3、退出用 1.4，避免相机在边界抖动导致反复建/删。外围还有：

  • 每帧限额：grass.MaxCreatePerFrame（默认 1）个组件、grass.MaxAsyncTasks（默认 4）个后台任务（LandscapeGrass.cpp:2963）。
  • 优先级排序：GrassCreationPrioritized 时按相机距离升序排，先建近的（LandscapeGrass.cpp:2784）。
  • 超大批切分：SqrtSubsections = Clamp(Ceil(√MaxInstances / √MaxInstancesPerComponent), 1, 16)（LandscapeGrass.cpp:2858），受 grass.MaxInstancesPerComponent（默认 65536，LandscapeGrass.cpp:129）控制。
  • 防抖回收：grass.MinTimeToKeepGrass（5 秒）且 grass.MinFramesToKeepGrass（30 帧）双条件同时满足才回收（LandscapeGrass.cpp:3141-3155），且每帧只删一个（LandscapeGrass.cpp:3199-3201）。

7. 实例分组粒度 —— draw call 的真正来源

分组键 FCachedLandscapeFoliage::FGrassCompKey（LandscapeProxy.h:259-297）是个八元组：

(LandscapeComponent, GrassType, SqrtSubsections, CachedMaxInstancesPerComponent,
 SubsectionX, SubsectionY, NumVarieties, VarietyIndex)
不是"每种草一个 HISM"，也不是"每个 component 一个"，而是每个 (LandscapeComponent × GrassType × VarietyIndex × 子分块) 各一个 UGrassInstancedStaticMeshComponent（键填充 LandscapeGrass.cpp:2914-2922，创建 LandscapeGrass.cpp:2997-3000）。

这就是 draw call 的来源：地形 component 数 × 草类型数 × 子分块数。默认参数下（component 63 quads ≈ 63m、密度 400）单个 component 约 1.6 万实例，远低于 65536 阈值，所以 SqrtSubsections = 1 —— 但一旦地形 component 尺寸或密度上去，切分就会触发，组件数按平方增长。

8. 上屏与剔除：异步建树 + 自研开关

8.1 独立于基类的异步路径

草完全不使用基类 HISM 的 BuildTreeAsync() / ApplyBuildTreeAsync()。它走自己的路：

  1. 后台线程：FAsyncGrassBuilder::Build() 末尾调 BuildTreeAnyThread(...)（LandscapeGrass.cpp:2383），后者是纯函数，内部构造 FClusterBuilder 并 BuildTree()（InstancedGrass.cpp:18-44）。
  2. 主线程：ProcessAsyncGrassInstanceTasks（LandscapeGrass.cpp:3211）轮询完成，调 AcceptPrebuiltTree(ClusterTree, ..., &InstanceBuffer)（LandscapeGrass.cpp:3246）整体接收。

为保证"不碰基类状态机"，构造函数里显式把实例数据管理器切成外部模式（InstancedGrass.cpp:13），并在 BuildComponentInstanceData 里用一串 check() 断言源数据恒空（InstancedGrass.cpp:100-129）。旧的 AcceptPrebuiltTree 重载被直接 check(false) 禁死（InstancedGrass.cpp:46-49）。

8.2 实例位置跨平台一致

随机种子是 GrassType名 + Component名 + SubX + SubY + VarietyIndex 的 CRC32（LandscapeGrass.cpp:2987），写进 InstancingRandomSeed（LandscapeGrass.cpp:3024）—— 保证不同平台/不同机器上草的位置完全一致，这对联机射击游戏很关键。

8.4 剔除增强（分叉自研）

草实例的 GPU 剔除在 NaniteCullingCommon.ush 里被扩展了两个函数（同文件同时服务 HISM / Nanite 剔除管线）：

  • 蓝圈剔除 BlueCircleCulling()（NaniteCullingCommon.ush:307-327）：以玩家为中心画半径圆，圈外实例整体剔除。半径硬编码多留 1500 单位，源码注释直白写着 // Why? Ask @wanmuxin（NaniteCullingCommon.ush:320）。草组件无条件开启（GrassInstancedStaticMeshComponent.cpp:37）。
  • 概率剔除 ProbabilisticInstanceCulling()（NaniteCullingCommon.ush:330-354）：用 Hash31(InstancePosition) 给每个实例生成稳定随机值，与随距离插值的阈值比较，实现按距离概率抽稀而非硬裁切 —— 远处草渐次消失而非整片突变。
概率剔除当前是"实现了但没开"的状态：总开关 grass.ProbabilisticCulling.Enable 默认 false（GrassInstancedStaticMeshComponent.cpp:17-24），三个参数 CVar（BeginCullingDistance / EndCullingDistance / EndCullingPercent，定义在 LandscapeGrass.cpp:836-855）在 S1Game/Config 下无任何覆盖。这是现成的一个优化抓手，可直接试。

9. 移动端

实测结论：草实例化链路对移动端没有任何分支。在 LandscapeGrass.cpp / InstancedGrass.cpp / GrassInstancedStaticMeshComponent.cpp 三个文件里，PLATFORM_ANDROID、IsMobilePlatform、ES3_1、[GR Mobile] 全部未找到。FeatureLevel 只作为参数透传（LandscapeGrass.cpp:1810、:1939、:3102），不参与任何条件判断。

11. 已知风险点

① UpdateGrassTypes() 的 CRC 短路被注释掉了（LandscapeGrass.cpp:946-953，带 @wanmuxin TODO）。后果：编辑器里每次调用都无条件 SetGrassTypes 并置 bChanged = true，使得 grassmap builder 里 UpdateGrassTypes() 的检查恒为真 —— 每次 Build 都会强制重建所有 component 并 MarkPackageDirty()。编辑大关卡时这是实打实的开销。
② BuildTreeAnyThread 里硬编码了两个常量（InstancedGrass.cpp:34-35）：DensityScaling = 1.0f、InstancingRandomSeed = 1，旁边还留着作者的存疑注释 // do grass need this?（InstancedGrass.cpp:33）。当前因为 InGenerateInstanceScalingRange = false（LandscapeGrass.cpp:2383）该 seed 不参与抽样，暂时无害；但一旦将来启用密度裁剪，所有草块会共享同一裁剪模式（组件真实的 seed 是 FolSeed，LandscapeGrass.cpp:3024，两者不一致）。
③ shader binding 规避会静默丢绘制：ZXB 那段校验（LandscapeGrassWeightExporter.cpp:358-364）在材质代理过期时直接跳过 MeshBatch，不报错。若排查"某些 component 的草权重图莫名缺失"，这是第一嫌疑点。

13. 一页总结

  1. 它是程序化系统，不是资产：材质权重 → GPU 烘焙 → 扁平权重表 → CPU 概率撒点 → 动态组件上屏。没有任何一处"存实例变换"的持久化数据。
  2. 权重即概率（LandscapeGrass.cpp:2285-2287）：Weight ≥ rand() 决定该候选点是否长草。这是整个设计最优雅的一点。
  3. 一切为了不卡帧：后台线程撒点 + 建树，主线程只做 AcceptPrebuiltTree；每帧限量 1 组件/4 任务；双 guard band 迟滞；5 秒+30 帧双条件防抖回收；对象池复用组件。
  4. draw call = 地形 component × 草类型 × 子分块（LandscapeProxy.h:259-297）。这是移动端草开销的结构性来源。
  5. 移动端没有专属分支，所有移动端差异来自：① grassmap 烘焙的 SM5 限制（不能运行时生成）；② AndroidScalability.ini 的 0.1~0.6 密度缩放；③ 项目侧两处 CVar 动态调参。
  6. 改动的重心全在引擎：@wanmuxin 的 LandscapeBridge 贴地对齐 + WeightScale + 蓝圈剔除、ZXB 的降帧补偿 + tick bug 修复 + shader binding 崩溃规避、yinnhaowang 的概率剔除、qiuzijian 的对象池。游戏工程只有 2 处 CVar 驱动。
  7. foliage.ForceISM 与地形草无关：它只转换 cook 期 InstancedFoliageActor 上的 UFoliageInstancedStaticMeshComponent，而草的组件是运行时 RF_Transient 动态创建的，cook 期不存在。
