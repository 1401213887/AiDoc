01本版修订要点

项v1.0 / v1.1v1.2（本版）
内存上限依据自推系数：实测峰值 × 1.15官方权威源：iOS jetsam 硬上限 / Android Play Vitals 官方阈值
iOS 口径存疑，"两平台不可比"已确认：PerfDog iOS = phys_footprint = jetsam 判决口径 → 对比成立
Android 口径未定义已确认：PerfDog Android = PSS；与 Play Vitals 的 RssAnon+VmSwap 不同口径
结论方向"低配反而预算高"（反向）反向消失——改用硬上限后，各档余量口径统一
撤回项引用了 UWA 0.5~0.6 倍规则、微信小游戏数值均已核验并撤回（见 §8）
本版最实质的变化
v1.1 给 iOS 高配（A13 / iPhone 11）的预算是 2500 MB。改用 jetsam 硬上限后，该机型的系统硬上限是 2068 MB—— 实测峰值 2150 MB 已经超过它，v1.1 给的 2500 MB 预算等于允许超上限 21%。这是必须修正的错误。

02口径定义与可比性

2.1 采集口径（已确认）

平台 / 来源指标名实际口径获取方式
PerfDog · iOSMemoryphys_footprinttask_info(TASK_VM_INFO)
PerfDog · AndroidMemoryPSS与 Android Java API / Meminfo 一致
iOS jetsam 判决per-process-limitphys_footprint内核 Memorystatus，日志字段 pageSize × rpages
Google Play VitalsMemory usageRssAnon + VmSwap28 天 P90
iOS：对比成立 ✓
PerfDog 采的 phys_footprint 就是 jetsam 判定 OOM 用的同一个指标。因此"实测峰值 vs jetsam 上限"是同一口径下的直接比较， v1.0/v1.1 里"两平台口径不同、不可比"的警告，对 iOS 侧解除。
Android：口径不同，但方向保守 ⚠
PerfDog 是 PSS（含 file-backed 页的按比例分摊），Play Vitals 是 RssAnon + VmSwap（不含 file-backed）。 游戏的大量资源正是 file-backed，所以 PerfDog 的数值通常大于 Vitals 判定的那个数。
方向上这是偏保守的（实测 < 阈值 ⇒ Vitals 口径必然更小），但不能当精确余量看——要精确卡线需另测 RssAnon + VmSwap。

2.2 两平台"上限"的性质不同（勿混为一谈）

平台上限性质超出的后果
iOS系统硬上限（进程被杀线）被内核 SIGKILL 强杀，用户侧表现为闪退
Android商店合规线（非运行时硬阈值）影响 Google Play 商店可见度（2027-02 起），不会直接杀进程

Android 运行时既无硬阈值也无固定比例——LMK 按进程重要性评分（oom_adj）决策，Android 17 起改用 cgroup v2 动态限额。Play Vitals 阈值是当前唯一官方按运存分档的定量参考。

iOS 三档里两档已无余量
  • 高配（iPhone 11）实测 2150 MB > 硬上限 2068 MB——超出 82 MB（4%）。同口径比较，不是口径错觉。
  • 中配（iPhone XS）1828 / 2040 = 90%，余量仅 212 MB。而 jetsam 在全局内存紧张时会更早杀（用户后台挂着微信等应用时，实际可用余量比这个还小）。
  • 低配（iPhone 8P）的判定取决于该机型真实上限：若为 2048 → 75%（安全）；若落在 iPhone X 那样的 1400 → 1526 超 9%。两种情形结论相反，见 §9。
为什么"104%"不等于"测试时必崩"
2068 MB 是 iOS 13.1.3（2019 年）时点的记录，而 jetsam 上限随 iOS 版本变化。测试机跑的系统版本新得多，上限可能已放宽， 所以当时没崩是合理的。但余量为零或已转负这一事实不变——真实上限需要看目标机型、目标系统版本上的实际 ActiveHard 值， 这属于必须闭环的 P0 项（§9）。

08撤回与更正

本版逐条核验了 v1.0 / v1.1 引用的外部数据，结果如下。

#v1.0 / v1.1 的说法核验结果处理
1 UWA：内存峰值「PSS ≤ 物理内存 0.5~0.6 倍」；2GB→<1GB、3GB→<1.5GB 原文中不存在这条规则。UWA 那篇内存标准是极老的标准（还在讨论 iPhone 4、512MB 安卓，PSS ≤200MB / Reserved Total 150MB 的世代），与 UE5 手游量级差一个数量级；文中仅给出两例（红米4X 纹理 <140MB、小米8 纹理 <280MB） 撤回
2 微信小游戏：Android 低档 <1.2G / 中高档 <1.5G；iOS 低档 <1G / 中高档 <1.4G 原文的内存阈值以图片形式呈现，文本不可提取，数字无法证实；且该标准面向 WebGL 轻量小游戏，本就不适用于 UE5 原生手游 撤回
3 Overboard 指南的 jetsamctl 数值（8G=7490 / 6G=5490 / 4G=3490 / 3G=2490）可作为系统默认上限 原文明确是越狱工具手动抬高上限的操作参数（SSH 进越狱设备执行 jetsamctl -l，iOS 16+ 还需循环重施），不是系统默认 per-process-limit 已纠正（v1.0/1.1 已标注，本版确认）
4 「iOS 与 Android 内存口径不同，不可跨平台比较」 iOS 侧解除：PerfDog iOS = phys_footprint = jetsam 判决口径，同口径可比。
Android 侧仍成立（PSS vs RssAnon+VmSwap）		 部分更正
5 iOS 高配（iPhone 11）预算 2500 MB 错误。该机型 jetsam 硬上限为 2068 MB，2500 MB 等于允许超上限 21% 更正为 2068
6 4GB 机型 jetsam 上限 ≈ 2040~2098 MB 证实并细化到逐机型：iPhone XS 2040 / XS Max 2039 / iPhone 11 2068 / 11 Pro Max 2067 / iPhone 12 2098 升级为硬数据

09待确认

#事项影响优先级
1 iPhone 11 在当前 iOS 版本上的真实 jetsam 上限（本文引用的 2068 MB 记录于 iOS 13.1.3） 决定高配档是"已超标必须压"还是"仅需观察"。方法：目标机型上跑一次高负载场景，取 jetsam 日志的 ActiveHard 值（pageSize × rpages） P0
2 iPhone 8 Plus（3GB）的 jetsam 上限——3GB 机型离散极大（X 1400 / XR 1792 / 7 Plus 2048），本文的 ~2048 是推断值（依据：8P 与 7 Plus 同为标准 3072MB 报法，而 iPhone X 因实报 2816MB 掉到 1400 组） 低配档判定完全相反：上限 2048 → 75% 安全；上限 1400 → 1526 超 9% P0
3 iPhone 7 的余量仅 41 MB——它是全表最低绝对值，且已跑最低画质 五档机型的内容增长容忍度几乎为零，建议单独设冻结门禁 P0
4 Android 实测需补 RssAnon + VmSwap 口径——现用 PSS，与 Play Vitals 阈值跨口径，占用比只能作方向判读 中配红米 K30 的 92% 是保守估计，真实余量可能更大；需实测确认 P1
5 iOS 8GB 机型（iPhone 14 Pro / 16）无 jetsam 上限数据，一档无法判定 一档预算暂缺 P1
6 Play Vitals 的 0–4GB 档无阈值；若产品要覆盖 3GB 安卓设备，官方不提供保护 需自设低端安卓标准 P1
7 jetsam 硬上限记录于 iOS 12/13 时点，需按当前系统版本重新取样 全表 iOS 上限可能整体偏低（偏保守） P1
8 源表缺口沿用 v1.0/v1.1：高通系分档表「内存」整列空白；美术制作规范仅覆盖武器 档位定义与美术侧卡口不完整 P2
